# 「话题群入口」与「扫码入口」的隔离约定（业务负责人 2026-10-08 定）

> 她的原话：「关于话题群，我们先**不删**，但是**也不迭代**了。不过需要你把我们的话题群入口和扫码入口**隔离开来**，
> 也就是说，它们要属于**没有相互关联的两个入口**」

## 一、两个入口的定位

| 入口 | 状态 | 谁在用 |
| --- | --- | --- |
| **话题群入口**（飞书群/话题里说话 + 卡片） | **保留、冻结**：不删、**不再加新功能**（只修 bug） | 现有习惯；扫码不方便时的兜底 |
| **扫码入口**（手机扫二维码 → 页面操作） | **新建、主力**：销售建单 / 查库存 / 补货报单 / 到货验收 | 日常操作 |

## 二、隔离规则（**什么共享、什么绝不共享**）

### ✅ 允许共享（必须共享）——**只有业务处理层**
销售入账 / 收款 / 履约 / 售后 / 采购 / 库存 / 幂等：`salesOrderService` · `salesProgressService` ·
`salesDeliveryService` · `afterSalesService` · `purchaseWebhookService` · `inventoryService` · 契约与配置。
⇒ 理由：**同一笔业务事实只能有一套写入口径**，两套会各写一本账。

### 🔴 绝不共享（各自独立）
| 维度 | 话题群入口 | 扫码入口 |
| --- | --- | --- |
| **输入解析** | 群消息 → AI 解析（`doubaoService` / `larkMvpService`） | 扫码页 HTTP 请求 + 页面表单 |
| **会话/草稿状态** | 本地任务记录 `server/data/lark_mvp_tasks/` | **自己的**会话记录（独立目录/前缀，例如 `server/data/scan_sessions/`） |
| **状态机** | 草稿状态机（`received/parsing/ready_to_confirm/posting/posted…`） | **自己的**会话状态（例如 `scanning/submitting/done`）—— **不许复用**草稿状态机 |
| **出口** | 回那条话题 / patch 那张卡片 | 扫码页响应（＋需要跟进时飞书待办/群卡） |
| **失败与重试** | 自己的重试与告警 | 自己的重试与告警（**一个入口出问题不许影响另一个**） |
| **文案** | 各自 config 段 | 各自 config 段 |

## 三、⚠️ 关于 ADR-004「产出与群聊解析**同形**」的正确解释

**"同形"指的是"交给业务层的入参形状一致"**（同一个 `salesOrderService.post(...)` 的字段），
**不是**"共用同一份草稿、同一个状态机、同一个任务记录"。
⇒ 实现扫码入口时：**复用业务层的函数与入参**，**新建自己的会话记录与出口**，**不碰 `lark_mvp_tasks`**。

## 四、验收（做扫码页时逐条对照）

1. 扫码建单**不写** `server/data/lark_mvp_tasks/`，话题群任务记录**不因扫码而变化**（用例钉住）；
2. 群聊入口的行为**逐字不变**（既有测试全绿，且给出"零 diff / 仅新增"证据）；
3. 扫码页的失败**只影响扫码页**（不许改群聊的重试/告警配置）；
4. 两个入口对同一张表/同一笔业务写入**走同一个业务函数**（不许在扫码侧另写一套写库逻辑）。
