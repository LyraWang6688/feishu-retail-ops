## 二、逻辑问题（按严重程度）

### 🔴 P0-1 「今日」的两个 0 是错的

真实（按流水「创建时间」的上海日期）：
2026-10-08 → 采购增加 15 双 / 销售减少 20 双 / 现货（换货出货）1 / 退货（回库）1 / 门盒转样品 3 条。
两个 0 与真实不符。最可能是**「今日」的过滤条件写坏了**（页面代码在 iframe 里，
我拿不到那段取数逻辑）——常见三种写法都会静默变 0：引用了**表里已不存在的字段**、
时间戳**单位/时区**弄错、拿**字符串日期**去比时间戳。需要她把页面的取数配置给我，我指到具体那一行。

### 🔴 P0-2 「按库存方向汇总」是错的映射（不只是 0 的问题）

页面把**库存方向 = 增加** 全算成「今日采购增加」、**减少** 全算成「今日销售减少」。
但「行为管理」19 条里：

- 方向 = **增加** 的行为有 **4 条**：入库（PURCHASE_IN）、**退货回库**（SALE_RETURN）、
  采购增加（STOCK_PURCHASE_INCREASE）、**手工调增**（STOCK_MANUAL_INCREASE）；
- 方向 = **减少** 的行为有 **7 条**：采购退货（PURCHASE_RETURN）、现货（SALE_CASH）、
  预定（SALE_PREPAID）、**赔货**（SALE_COMPENSATION）、销售减少（STOCK_SALE_DECREASE）、
  **手工调减**（STOCK_MANUAL_DECREASE）、采购退货·采购减少（STOCK_PURCHASE_DECREASE）。

⇒ 今天就有 **1 双退货回库被算进「采购增加」**、**1 双换货出货被算进「销售减少」**；
以后的手工盘点、赔货、采购退货也都会串到这两个数里。

正确口径只能是**按行为编码**认（`STOCK_PURCHASE_INCREASE` / `STOCK_SALE_DECREASE`），
不能按「库存方向」认。

### 🟠 P1-1 数量口径：流水不是"一行一双"

实时库存是**一双一条**（条数 = 双数，这点没问题）。
但**库存流水一条可以代表 N 双 —— 看「变动数量」列**：

- 2026-10-08 有一条 `采购增加 变动数量=2`（14 条流水合计 15 双）；
- 2026-10-05 有 **274 条流水合计 299 双**（一次性初始化性质）；
- 2026-09-25 有 10 条「销售减少」的**「变动数量」是空的** ⇒ 直接 `SUM` 会算成 0。

⇒ 「今日增加/减少」必须 `SUM(变动数量)`、并容错空值（`COALESCE(...,0)` 或按空行特殊处理），
**不能数行数**。

### 🟠 P1-2 「创建时间」不等于"业务发生日"

「库存流水」现在 **11 个字段，没有「发生时间」**（业务负责人 2026-10-05 亲手删掉的那一列），
只剩飞书自动的「创建时间」（type=1001）。后果：

- 她一夜里录单会**跨午夜**：2026-10-07 21:00–23:59 有 50 条流水，**2026-10-08 00:00–01:30 又有 40 条**
  —— 同一晚的生意被切成两个"日"；
- 批量补录 / 幂等重放的流水，会整体算到**写入那天**（10-05 那 274 条就是例子）。

⇒ 要"业务日"就得在「库存流水」加一列业务日期（或接受"写入日"这个口径并写进说明）。

### 🟠 P1-3 顶部「库存总量」名不副实

「库存总量」显示的是**全部**（1342），而描述里写的是"仓库状态的总数量"（真实 10）。
两个数差 133 倍，她拿去对账必然对不上。要么改名成「在库总量（含样品/门盒/仓库）」，
要么把三个状态分开列。

### 🟡 P2-1 历史脏数据会让"按方向汇总"静默漏

56 条流水挂在「**销售收入（SALE_INCOME）**」上，它的**库存方向是空的**（19 条行为里唯一一条空方向）；
另有两条第名字都叫「**退货**」（一个方向减少=采购退货、一个方向增加=销售退货），
按名字展示会撞车。按方向汇总时这 56 条会被静默丢掉。

### 🟡 P2-2 分组口径可以更稳

- 页面按「颜色」分组，要跨 **3 跳**（实时库存.编号 → 货品信息.编号 → 货品信息.颜色 → 颜色管理.颜色）；
  而**实时库存自带的「库存键」公式列已经含 颜色+尺码**（`货号|颜色|类别|尺码`），
  直接读它少两级失败点。
- 货品信息 561 条里有 **92 种颜色关联**（鞋店这个量级说明颜色命名有同义/重复，如 白 / 白兰 / 白兰色 / 白灰），
  按颜色分组会裂成很多小组。
- 实时库存有 **1 条没关联编号、1 条没尺码**（共 2 条）⇒ 任何按编号/尺码分组的页面都会**静默丢掉**它们。

### 关于「模糊搜索」（业务负责人 2026-10-08 问）

**是"包含匹配"，但要盯住一件事：在哪个字段上匹配。**

- ⚠️ 「实时库存」的「编号」是**关联字段**（SingleLink → 货品信息），**不是文本列**。
  直接对关联字段做"包含"通常不生效、或行为不可预期（时好时坏）——这是最容易翻车的点。
- ✅ 正确做法二选一：
  1. 在「**货品信息**」的「编号」**文本列**上做包含匹配 → 拿到命中的货品记录 → 再回「实时库存」按关联取数；
