## 说明

### 只记录【已部署】的版本

- 这一栏是**上线对账表**：一行 = 一次真实部署。**没部署的版本不要写进来**（先留在分支 / PR 上）。
- **部署时间**：⚠️ `b75139a` 那一行的时间是**按 commit 时间推定的**（代码在 2026-10-07 23:52 合入 main，
  当晚部署），**不是从服务器 `/health` 读回来的** —— 想变准确就在服务器上跑一次
  `bash server/scripts/deploy_run.sh --check-only`，它会把 `/health` 上的
  `version` / `commit` / `deployed_at` 打出来，再回来订正这一格。
  ⭐ 新的一行请直接抄部署时 `/health` 回报的 `deployed_at`（那是服务器本地时间，已是 +8）。

### 版本号怎么涨

`tag_release.sh` 只做 **patch + 1**（例：`v0.3.0` → `v0.3.1`）。
**主 / 次**号要人工决定（不兼容的结构变更 / 新增功能），改法：人工 `git tag -a v0.4.0 <commit> -m "..."`，
之后脚本会接着从 `v0.4.0` 往上涨。

### ⚠️ 这一版只打了 tag，**没有**改 `package.json`

- 业务负责人的口径是「就是打个 tag」⇒ **刻意不动 `package.json` 的 `version`**，
  免得为了打一个 tag 多出一笔提交。
- ⇒ ⚠️ **两处版本号会不一致**：`server/package.json` 仍写着 `0.3.0`，而这一版是 `v0.3.1`。
  按口径**以 tag 为准**（`/health` 的 `version` 走的是 `deploy_run.sh` 算出来的 `APP_VERSION`，不是 `package.json`）。
  `package.json` 里的那个数字现在只在「没有 tag、没有 `APP_VERSION` 环境变量」时兜底。
- ⇒ **副作用（要知情）**：`v0.3.0` 那个 tag 停在 2026-10-07 00:14 的 `f0a2f3f` 上，
  而线上跑的是到 `b75139a` 为止的代码 —— 在本次 `v0.3.1` 推送**之前**，
  服务器上 `git describe --tags --abbrev=0` 仍会算出 `v0.3.0`，
  所以 `/health` 的 `version` 会报成旧版次（commit 是对的）。
  **下次部署**时它才会算出 `v0.3.1`。

### v0.3.1 那一版是什么（`f0a2f3f..b75139a`，合入 172 个提交）

按业务负责人口径的三块：

1. **到货卡片可见性** —— 「核对卡片改成在当前话题发新卡」：
   此前日志说"卡片已更新"、她那边一张都没有（PR #251）。
2. **确认成交不再假成交** —— 点【确认成交】不再在"货没到 / 钱没收齐"时记成成交，
   并给卡面自愈（PR #249 / #244）。
3. **采购侧那批** —— 采购退货解析并入报货那条路线、到货落点搬到「报货批次」那一行、
   报货批次号改由代码生成、表改名与时间字段同步等（PR #239 ~ #248 及 #241/#242/#243/#245）。

更细的逐版说明在根目录 `CHANGELOG.md`（那一份是散文式版本记录，写到 `v0.2.0` 为止）；
本文件是**上线对账用的一行一版表**，两者不冲突。

### 怎么加一行

```bash
# 部署之后（拿到业务负责人的当次命令才部署）
bash server/scripts/tag_release.sh HEAD "一句话说明这一版改了什么"
# 再把 /health 回报的 deployed_at + tag 名 + commit 补一行到上面的表里
```

## 约定：**部署前先打 tag**（2026-10-08 业务负责人拍板）

`deploy_run.sh` 的版本自检用 `git describe --tags --abbrev=0` 取版本 ⇒ **先打 tag 再部署**，
`/health` 的 `version` 才会与 tag 一致。
⚠️ 反例（本仓库真实发生过）：先部署（01:35:08）后打 tag（01:35:56）⇒ `/health` 报的是**上一个** tag（v0.3.1），
而 commit 是对的。业务负责人的处置口径：**不动它**，下次部署自然就对了 —— 但**以后一律先打 tag 再部署**。
