# 设计：颜色由 **A 环节**定死，B 只是拿它去查库存（业务负责人 2026-10-07 拍板）

> 她的原话（逐字）：
> 「**我觉得 A 一定要有选颜色的机制。也就是说在 A 环节，要完成这三件事：**
>  **1. 判断货号有没有、有几个颜色**
>  **2. 如果有多个颜色，一定要让用户去选择**
>  **3. 看这个货号所在的信息是不是齐全的**
>  **拿到这个确定性的信息之后再去跑 B。B 应该是拿着 A 环节用户选的那个颜色，
>  然后再去找库存，这样子的话，这个流程其实三个类型都是要这样走的，
>  只不过对于预付来说，它不会再走 B 了**」
>
> ⚠️ **部分已更新（同日后续口径）**：本文里"**候选上标『有货 / 无货』**"（下一节第 3 / 7 条、
>   以及"候选标签不重读""失败不下有货 / 无货结论"那两条）**已被业务负责人「甲 去掉」取代** ——
>   **候选只显示颜色名**，选完颜色之后才查库存、才定现货 / 预定；配置键也随之下线。

## 链路（三种交易类型一致）

```
【A】货品信息解析（三种类型都跑）——产出【确定性信息】
   1. 货号在不在「货品信息」里（不在 ⇒ 缺项，见「货品建档守卫」那条）
   2. 有几个颜色：
        · 1 个 → 直接定下来
        · 多个 → **出候选让用户选颜色**（选颜色是 A 的职责）
   3. 该货号的信息是否齐全（飞书公式「缺失信息说明」）→ 缺什么（只提示、不拦单）
   ⇒ 产出：货品记录 id + 颜色（用户选定的）+ 缺项清单

【B】库存解析（只有 现货 / 未付 跑）
   · 输入：A 定下来的【颜色】+ 尺码
   ⇒ 拿着这个颜色去找「实时库存」那一双；缺货 → 拦（"库存里没有…"）

【预付】不跑 B（货没到、要调货）；A 的结果照样落到销售明细上
```

## ⚠️ 一个已知的、有意的行为变化

「货号有多个颜色、但那个尺码只有其中一色有货」这种情况：
- 旧（其实是 bug 导致的偶然行为）：B 按货号+尺码唯一定位 → **直接被给到正确颜色、不问**
- 新：**先问用户选颜色**（因为货品信息里确实是多个颜色）→ 更严谨、明细一定挂对货品
- 她 2026-10-07 明确选择"要问"（本文件即其口径）

## 实现（2026-10-07 第三刀）—— 验收标准（先写、后做、逐条对照）

> 写在动手**之前**（`AGENTS.md` 协作纪律第 2 条：先写"应该是什么样"再跑）。

1. **多颜色 + 未选颜色 ⇒ B 一次都不跑**：`resolveStockAvailabilityForSale` 的调用次数为 **0**；
   确认卡片上给出 `choose_sale_color` 候选按钮（三种交易类型一致）。
2. **选定颜色之后**：该条明细的 `product_record_id` / `color` 用**她点中的那条候选**；
   **这时才跑 B**（调用次数 1），且 B 的输入**带上这个颜色**；缺货提示发生在 B **之后**。
3. **现货（跑 B 的类型）的候选标「有货 / 无货」**：例如 `黑色（有货）`、`白色（无货）`；
   判断只用**录单时已经读进来的**实时库存索引（`LiveInventoryIndex`），**零新增远端请求**；
   全都无货时每个候选都标「无货」（边界）。
4. **单颜色货号不问她**，A 直接定下来（现货 / 未付 / 预付三种类型都一样）。
5. **预付：选完颜色之后 B 仍然不跑**（`salesTradeTypePolicy` 里 `stock: false`）。
6. **未付：与现货同样**「多颜色 → 先让她选」。
7. **配置先行**：候选上的"有货 / 无货"文案走 `config/salesColorChoice`；
   "这一步跑不跑 B"仍然只由 `salesTradeTypePolicy` 决定；**不出现散落的 `=== '预付'`**。

### 有意改掉的旧行为（不是放宽）

| 旧行为 | 新行为 | 为什么 |
| --- | --- | --- |
| 现货/未付：B 的结论**整体覆盖** A（颜色、记录 id、候选全换） | **颜色 / 记录 id 以 A 为准**；B 只回答"这个颜色在这个尺码有没有货" | 本文件的口径：颜色由 A 定死，B 只拿选定颜色去查库存 |
| 现货/未付：A 给出**单一颜色**、B 认得出另一个颜色时，以 B 为准 | 同上：A 那个颜色去 B 里找；找不到 ⇒ 走"库存里没有…" | 同上（旧的"B 覆盖 A"正是本刀要拿掉的东西） |
| 多颜色时 B 直接把候选连同库存摆出来，不问用户 | A 出候选、**先问用户**，选完才跑 B | 她逐字要求："如果有多个颜色，一定要让用户去选择" |

### 两个实现上的取舍（如实记下）

- **选色后的 B 要重读一次「实时库存」**：颜色是在卡片点击那一次请求里才定下来的，
  那一侧没有录单时读进来的索引 ⇒ `choose_sale_color` 里重新 `loadLiveInventoryIndex()`。
  （卡片动作走 `setImmediate` 异步处理、同步 toast 早就返回了，所以不会顶到飞书的回调超时。）
  ⚠️ **候选上的"有货 / 无货"标签不重读** —— 它只用录单时那次已经读进来的索引，零新增请求。
- **选到无货的颜色**：回一句 `库存里没有…，请核实～`（与录单时同一条话），
  **候选保留、任务留在 `ready_to_confirm`** —— 她可以在同一张卡片上换一个颜色，
  不必重发整条销售信息；「全都无货」时也不会把她留在一个点不动、走不了的死状态里。
- **选色后那一次库存读表失败**：**不下"有货 / 无货"的结论**（`AGENTS.md` 第 17 条），
  回一句可配的「暂时读不到库存，请再点一次颜色～」（`SALES_COLOR_STOCK_LOOKUP_FAILED_TEXT`），
  候选保留让她重试。⚠️ 只把**远端读表**这一步当可重试；纯函数里的编程错误照旧抛出，不被吞掉。
