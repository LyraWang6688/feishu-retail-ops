## 2. 她的原始需求（页面里那段对话，逐字）

> 需要你依据这两张数据表，帮我做个销售查询的页面，支持按照日或者区间，
> 显示的内容有销售的数量，销售的金额，支付方式维度，品类维度还有类别维度，
> 销售时间看**更新时间**，销售的数量看**销售明细里的履约状态为交付的**，
> 按照品类和类别进行分类，销售金额看**到收款时间为已收款的**，且按照支付方式分类

引用的两张表：**销售明细**、**收款明细**。

## 3. 页面自己声明的口径

| 口径项 | 页面怎么算 |
| --- | --- |
| 时间筛选 | 单日 / 自定义区间 |
| 销售**数量** | 「销售明细」中**履约状态 = 已交付**的记录，按**更新时间**筛；按 品类 / 类别 分组 |
| 销售**金额** | 「收款明细」中**收款状态 = 已收款**的记录，按**收款时间**筛；按支付方式分组 |
| 品类 / 类别 | 销售明细 →（关联）→ 货品信息 → 品类（关联「品类管理」）/ 类别（A 男鞋 · B 女鞋） |
| 支付方式 | 收款明细 →（关联）→ 收款方式管理 |
| 概览 | 已交付总数量 · 已收款总金额 · 覆盖品类数 · 支付方式数 |
| 趋势 | 双轴折线：每日数量 + 每日金额 |

页面自述「数据会随 Base 实时同步更新，刷新页面即可看到最新统计」。

## 4. 与我们系统（已删除 UI 的 `getSalesReport`）的口径对照

| 项 | 页面 | 我们系统 `v1WorkbenchService.getSalesReport` |
| --- | --- | --- |
| 数量载体 | 销售明细.履约状态 = 已交付 | 销售明细（**不过滤履约状态**） |
| 数量时间基准 | **更新时间** | **销售日**（`salesDetail.soldAt`，缺失才回落主表时间） |
| 数量 | 一条明细 = 1 双 | `quantity` **恒为 1** |
| 金额来源 | **收款明细.收款金额**（实收） | **销售明细.成交金额**（应收） |
| 金额时间基准 | **收款时间** | 明细的销售日 |
| 金额过滤 | 收款状态 = 已收款 | 主表「资金状态」已入账 |
| 支付方式 | 收款明细 → 收款方式管理 | 同（整单拼接，空则「未收款」） |
| 品类 / 类别 | ✅ 有关联分组 | ❌ **没有**，只有 货号 / 颜色 |
| 趋势图 | ✅ 有 | ❌ 没有 |

## 5. 🔴 从代码里核出来的三条真实差异（不是猜的）

### ① 退款记录会被算进「销售金额」（最要紧）

`services/afterSalesService.js` 的 `settleCash`（约 `:680`）：

- 售后走现金时写一条**收款明细**，字段是：
  `status = '已收款'`（`config/afterSales.cashPaymentStatus`）、
  `amount = Math.abs(差价)`（**正数**）、
  `tradeDirection = '退回'`（或 `'收入'`）、
  `receivedAt = 本次售后时间`、
  `salesEntry` 指向**售后新建的那条主表**（不是原单）。

⇒ 页面的金额口径只写了「收款状态 = 已收款 + 按收款时间筛」，
**如果它没有同时排除 `交易方向 = 退回`，退款会被当成一笔正的销售金额加进去**。
退得越多，那个区间的金额虚高越多；而同一笔货在「数量」那一侧
（履约状态已变「已退货」）是**被剔除**的 —— 两边会更不一致。

⭐ **必须实测核对**：取一个「已退货且钱已退」的区间，看页面金额是否比实际多。
（我读不到页面代码，只能核到这个程度；这一条**不能替她下结论**。）

### ② 数量与金额不是一个集合，不能相除

数量锚在「明细交付那一瞬间（更新时间）」，金额锚在「钱到账那一瞬间（收款时间）」：

- 上月交的货、本月收到尾款 → 本月**金额有、数量没有**；
- 本月交的货、尾款还没收 → 本月**数量有、金额没有**；
- 团购券「待平台结算」的收款行**状态不是已收款** ⇒ 金额侧**不计入**。

⇒ 页面上的「金额 ÷ 数量」**不是客单价**，别拿它当客单价用。

### ③ 品类 / 类别为空时会静默归堆

品类来自「货品信息 → 品类管理」的关联、类别是「货品信息.类别」（A / B）。
某货品的这两列为空（建档时缺资料）时，那几双会落到"未分类"一堆里 ——
总数量对得上，但**按品类 / 类别看会少**。

## 6.5 业务负责人 2026-10-08 的拍板（她逐字）

1. **退款那条的收款状态是「已退款」** ——
   原话：「对的，如果我们退款的话，**收款状态它是已退款**呀」。
   ⇒ 若为真，页面的「收款状态 = 已收款」筛法**天然把退款排除在外**，第 5 节 ① 的风险不成立。
   🔴 **但代码写的是「已收款」**：`config/afterSales.cashPaymentStatus = '已收款'`，
   `afterSalesService.settleCash` 原样写它（只把方向写成「退回」）。
   ⇒ 中间**一定还有一道**在把退款行改成「已退款」（她在 Base 里手工改，或 Base 自动化流程改）。
   ⚠️ 这道"谁在改"必须查清（只读核真表）：它不是可选项——
   哪天那道手工/自动化漏了，页面金额就**静默虚高**。
2. **数量锚「交付」、金额锚「到账」是她有意为之** ——
   原话：「**数量就是锚定交付（证明我真的卖出去了），金额就是我真的收到账了，没关系**」。
   ⇒ 第 5 节 ② **不是缺陷**，是设计。**唯一约束**：页面上/别处**不许用「金额 ÷ 数量」当客单价**。
3. **品类 / 类别为空不管** —— 原话：「品类和类别为空的就没事，那我们**后续慢慢完善**就行」。
   ⇒ 第 5 节 ③ 降级为"以后再说"，不阻塞。
4. **定位 = 最小 MVP，之后迭代** —— 原话：「我们把它作为一个**最小 MVP 进行迭代**，对吧？
   目前大的思路是没有问题的，对不对？」。
   ⇒ 「销售查询」页面**就是 MVP**；工作台只负责挂链接（`links.js`），
   **不自建查询接口 / 页面**，不在本地重算业务事实。
5. 她**已给「销售查询」的 URL**（并已按它改配置，PR #266）；**库存查询的 URL 稍后给**。
   （第一轮她那条消息里正文没带上链接字符串，她随后**重发了** —— 以重发那条为准。）

## 6.6 「退款那条写的是不是『已退款』」——代码核查结论（2026-10-08）

她要求「**需要你实际看下代码**」。核完全仓，结论是：**代码从来没有写过「已退款」**。

| 证据 | 内容 |
| --- | --- |
| `grep -rn "已退款"`（全仓 `*.js/*.md/*.json`，排除 `node_modules`） | **0 命中**（只有本文档自己那几行） |
| `server/src/config/afterSales.js:231` | `cashPaymentStatus: '已收款'` |
| `server/src/services/afterSalesService.js:708` | 退款/收款那条：`status: this.config.cashPaymentStatus`（= 「已收款」），方向另写 `tradeDirection` |
| `server/src/services/paymentService.js:42` | 写入前**硬校验**：`收款状态` 只允许 `['已收款','未收款','待平台结算']` —— **不在这三个里直接抛错** |
| `server/src/services/salesProgressService.js:34` | 读取侧另认历史值 `已收清` / `已结清`（只是**读**，代码不写它们） |
| `server/src/services/secondDeliveryService.js` | 「成交」那条只做 `未收款 → 已收款` |

⇒ **写「收款状态」的取值集合就是三个：`已收款` / `未收款` / `待平台结算`。**
所以那条退款记录能显示成「已退款」，**只能来自代码之外**。

### ✅ 6.6.1 她 2026-10-08 当场给的答案：**是她自己加的选项**

> 「收款状态那个我**增加了两个字段**：
>  1. **已退款**：别人来退货，我们把钱退给对方了。
>  2. **已留存**：别人来退货，但是把钱留在我们这里。」

⇒ 所以「已退款」**不是**自动化流程改的、也不是别的表 —— **是她在生产表里新增的选项**
（她用的是"字段"这个词，实际是**单选字段的选项**）。

⚠️ **这一下就把第 5 节 ① 的"风险"变成了"必须马上同步的差距"**：页面那边的担心（退款被算成收入）
现在**取决于代码什么时候跟上**，而不是取决于"哪道人工会不会漏"。两件事：

1. **口径不一致（要改代码）**：售后的**收 / 退两条腿现在都写「已收款」**
   （`config/afterSales.js:231` + `services/afterSalesService.js:708`），
   只有「交易方向」写「退回」。她的新口径是：**少收（要退给对方）→ 「已退款」**。
2. 🔴 **读取侧会直接抛错（更要紧）**：`services/salesProgressService.js:35`
   对**不认识**的收款状态**直接 `throw new Error('未知收款状态：…')`**，
   而它被**六条链路**用着（录单 / 成交 / **9 点待处理单候选** / 群话题推进 / 追问补收 / 交付）。
   ⇒ 一旦某条收款明细是「已退款」或「已留存」：
   - **9 点推送**那条会 `catch` 掉并**静默跳过该单**（只留一条 warn）；
   - **群话题 / 卡片**那条不 catch ⇒ **用户看到操作失败**。

**完整口径 + 4 处代码差距 + 影响面 + 要她定的 3 件事**，另立文档：
`docs/refund-status-options-and-cost-difference-2026-10-08.md`。

⚠️ **页面金额那侧的结论也要跟着改**：她新增选项之后，退款行**会**是「已退款」⇒
页面的「收款状态 = 已收款」筛选**天然把退款排除**，**金额不会被虚高**（这条是好消息）；
但**前提是我们代码真的按新口径去写**（否则退款行会留在「已收款」上，页面就会虚高）。
