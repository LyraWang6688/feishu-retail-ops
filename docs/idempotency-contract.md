# 采购与库存的幂等契约（远端幂等键）

> 目的：把「本地记录丢失 / 飞书写入结果未知」这两种情况，从「可能重复写一笔业务事实」变成「可以安全重试，或者停下来人工核对」。

## 1. 要解决的问题

飞书写入是远端调用，本地日志覆盖不了它的全部结果：

```text
飞书 create 已成功
      ↓
进程崩溃 / 响应丢失 / 本地落盘失败
      ↓
本地不知道已经写过
      ↓
用户重试
      ↓
再 create 一次 → 重复的采购申请 / 重复的实时库存
```

这类窗口在本地查不出来，只能让远端自己带一个稳定标识，重试前先按标识回查。
本地任务记录（`posting_plan` / `posting_progress` / `created_live_record_ids`）仍然保留，
但它负责「让恢复更快」，不负责「证明没有写重」。

## 2. 三个远端标识

| 表 | 字段 | 值格式 | 生成规则 |
|---|---|---|---|
| 报货批次 | 幂等键 | `purchase_batch:<taskId>` | 每个采购确认任务一个，随任务持久化 |
| 采购申请 | 幂等键 | `purchase_request:<taskId>:<index>` | 每条明细一个，`index` 来自已持久化的 Posting Plan |
| 实时库存 | 库存操作键 | `<inventory_operation_id>:<sequence>` | 每一双一个，`sequence` 从 1 开始 |

`index` 与 `sequence` 都来自已经落盘的清单，不是临时数组下标——重试时顺序变化不会换键。

## 3. 写入规则

任何一次创建都必须按这个顺序：

```text
按幂等键回查远端
  ├─ 命中 1 条 → 复用这条记录（上一次已经写好的）
  ├─ 命中 0 条 → 才允许 create
  └─ 命中 >1 条 → 数据已经重复，停止自动处理，要求人工核对
```

`create` 抛错时按错误性质分流：

- 结构化拒绝（飞书返回 `code != 0`，例如字段不存在）：请求被处理并明确失败，
  直接抛出原始错误，保留可诊断的信息。
- 结果未知（超时、连接重置、5xx）：不重发 create，只在 read-after-write 窗口内按幂等键回查；
  查得到就复用，查不到就抛「创建结果未知，请人工核对」并停止。

原则：宁愿停下来让人核对，也不因为「不确定」再写一笔采购事实。

## 4. 需要在多维表格里手工新增的字段

以下字段代码不会自动创建。缺失时 schema-check 直接失败，部署门槛会拦住部署。

| 表 | 字段名 | 字段类型 |
|---|---|---|
| 报货批次 | 幂等键 | 文本 |
| 采购申请 | 幂等键 | 文本 |
| 实时库存 | 库存操作键 | 文本 |

迁移清单：

1. 在测试 Base 的三张表里各新增上述字段（必须是文本，不能是数字或关联）。
2. 运行 `pnpm run v1:schema-check:purchase` 和 `pnpm run v1:schema-check:inventory`，两者都要通过。
3. 在测试 Base 跑一遍采购确认与到货入库，确认「采购申请.幂等键」「实时库存.库存操作键」有值。
4. 确认无误后，在生产 Base 做同样的字段新增，再让部署门槛通过。
5. 字段是后加的，历史记录不会有值——恢复逻辑只在值存在时用它校验，
   历史记录仍按货品 + 尺码 + 状态核对。

## 5. 状态机（采购卡片确认）

```text
awaiting_confirmation
      ↓ 用户点击确认（先落 posting，再写远端）
   posting           ← 可恢复：重进流程会按已持久化的进度继续
      ↓
   posted
```

`posting` 不是终态：同一任务再次收到确认时会继续（复用已写入的批次 / 采购申请），
而不是回到「处理中，请勿重复点击」。失败时卡片变成红色的「未完成」并带上原因。

同一 `taskId` 的确认 / 取消由 `KeyedSerialQueue` 串行执行，锁内重新读取任务状态；
并发点击不会走两遍副作用。卡片上的「处理中」只是 UX，正确性由后端保证。
