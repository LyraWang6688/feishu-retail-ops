# worktree / 分支清理规矩（Lead 每轮必做 · 2026-10-16 定）

> **起因**：业务负责人 2026-10-16 追问「**为什么会存在这些 worktree 呢？不应该是合并完，这些 worktree 也需要一并清理吗**」
> ⇒ 我核完后的诚实结论：**规矩本来就有（`AGENTS.md` §14 收尾六步）✓，错在把它当成了"以后再说"** ✗

## 🔴 责任与动作（**谁合谁清**）

- ⭐ **Lead 在【合并那一轮】顺手清** ✓ —— **不再留给执行者** ✗
  （执行者的活是"只开 PR 不合并"✓ ⇒ 交活即退出 ✓ ⇒ "合并后清理"这一步**没人会做** ✗ —— 这就是积压的根因 ✓）
- ⭐ **每轮核 PR 时当作固定动作** ✓（不是收尾时才想起来 ✗）

## 🔴 判据（**不许用祖先关系** ✗）

```bash
git cherry origin/main <分支>
```
- `-` ⇒ 该提交的改动**已在 main**（按 **patch-id** 认 ✓ 对 **squash 合并有效** ✓）
- `+` ⇒ **真的没合** ⇒ 🔴 **不删** ✗
- ⚠️ **不许用** `git merge-base --is-ancestor` / `git branch --merged` ✗ ——
  本仓用 **`--squash` 合并**✓ ⇒ 分支提交**换了身份**、永远不是 main 的祖先 ✗ ⇒ 那些判据**永久拒绝** ✓
  （2026-10-16 我因此两次得出**无效结论** ✗ 如实记录 ✓）
- ⚠️ **不许用** `git diff main..branch` 当"有没有未合内容"的判据 ✗ ——
  分支停在旧提交时它会显示**上万行"删除"** ✗（那是 main 后来长出来的 ✓ 不是分支压着东西 ✓）

## 🔴 底线（一条都不许破）

1. 有 `+`（真没合）⇒ **不删** ✗（先判定"废稿 / 未完成"✓ 报 Lead ✓）
2. 有**未提交** ⇒ 先 `git status` **逐行看一眼** ✓（是成品 ⇒ 留 ✗；是便条/复现脚本 ⇒ 可弃 ✓）
3. **绝不用 `--force`** 于"有 `+`"的目录 ✗ · 不 `stash` · 不 `reset --hard` · 不动别人的目录 ✗
4. 要清"有 `+`"的 ⇒ **先把每个未合提交的 diff 留档到 `docs/`** ✓ 再清 ✓（**绝不无声丢代码** ✗）

   `push -f` 把分支**覆盖成了 main** ⇒ 那份"待合并的留档"**没能入库** ✗（丢的是冗余存档，不是代码 ✓ 但仍是我的错 ✗）
