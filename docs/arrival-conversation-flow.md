  （她删掉了「采购到货」表上的「类型」「识别状态」「识别失败原因」三个字段）。
  代码侧对应实现在 `feat/purchase-return` 的「到货『拍照识别』链路整体退场」一处删除：

- **【业务负责人原话】** 新方式：在**群话题**里用**自然语言**核对到货情况，
  **机器人不主动追问**。
- **【业务负责人原话】** 目标是「**在这个基准上去校准实际到货**」——

## 2. 新链路（逐步）

```
① 业务负责人提交报货表单（「供应商对接」）→ 机器人渲染「采购申请单」图
   → 发到采购群（PURCHASE_CHAT_ID）→ 群里就这张单形成一个话题
② 话题里的交流都关于那张对应的采购申请单
   · 可以一次说完，也可以分多次说完
   · 机器人只记录这些说法 —— 此时不入库
③ 用户说一句表示「这次核对完了」的话
   · ⚠️ 字眼不固定（「复核完了」「核对完了」「就这样吧」都算）
   · ⇒ 靠 AI 理解意图（不是关键词匹配）
④ 机器人发确认卡片：「本次到货核对完毕，确认入库吗？」
⑤ ⭐ 用户点「是」→ 这是最终入库的点 → 四张表一起变
```

以上五步的**业务语义**均出自【业务负责人原话】（她今天亲口定的），
只有实现手段（用什么模型、卡片长什么样、回调叫什么名字）属于待定/工程细节。

其中这四条是**必须守住**的边界，任何实现不得退化成"攒到最后一条消息再统一解析"
或"命中关键词才算核对完毕"：

1. **可以一次说完，也可以分多次说完**（②）——【业务负责人原话】
2. **表示"核对完了"的字眼不固定**（③）——【业务负责人原话】
3. **靠 AI 理解意图，不是关键词匹配**（③）——【业务负责人原话】
4. **用户点「是」才是最终入库的点**（⑤）——【业务负责人原话】

## 3. 入库要变的东西（四张表，逐条）

| # | 表 | 变化 | 出处 |
|---|---|---|---|
| ① | **采购到货** | **把用户的原话归集进去** ＋ 记「**到货日**」（= 说话那天）＋ 记「**验收原话**」（= 那句话） | 【业务负责人原话】 |
| ② | **采购入库** | **要变**：按**实际**到的数量写入库行 | 【业务负责人原话】 |
| ③ | **库存流水** | **要变**：按实际数 | 【业务负责人原话】 |
| ④ | **实时库存** | **要变**：按实际数 | 【业务负责人原话】 |
| ✗ | **采购申请表**（现表名「**单据信息**」） | **不动** | 【业务负责人原话】 |

**为什么采购申请不动**——【业务负责人原话】：

> 「**采购申请表已经是一个历史数据了**。我们只是要**在这个基准上去校准实际到货**，
> 所以在采购申请表的基础上校对后，**按实际数量入库即可，不需要改表本身**」

**后续也按实际数**——【业务负责人原话】：

> ⭐「**后续的库存流水和实时库存，也都按实际数来记录**」

## 4. 实现要点：接在哪、复用谁

### 4.1 群聊那一半**已经有了**【代码事实】

2026-10-06 上线的「群聊采购」已经把这一半做完了，**新流程不要再写一遍**：

| 能力 | 现状 | 位置 |
|---|---|---|
| 机器人把采购单发进群 | 已上线：按供应商出图 → 发 `PURCHASE_CHAT_ID` → 写回附件 | `PurchaseWebhookService.deliverSupplierImagesInner`（`server/src/services/purchaseWebhookService.js`） |
| 话题里**免 @** 也理 | 已上线：准入**先判 `thread_id`**，话题里的消息不要求 @机器人；空 `thread_id`（主群）才要求 `mentions` 含机器人 open_id | `LarkMvpService.acceptMessage`（`server/src/services/larkMvpService.js`） |
| 按 `thread_id` 定位是哪一批 | 已上线：`thread_id` → `parent_id` → 正文批次号，四条路**都不猜** | `PurchaseBatchLocator.resolve` · `rememberGroupMessage` · `bindThreadToRecord`（`server/src/services/purchaseBatchLocator.js`） |
| 群消息的入口分发 | 已上线：定位成功只记日志、不回消息；认不出才回一句问清楚 | `GroupPurchaseFlowService.handleGroupPurchaseMessage`（`server/src/services/groupPurchaseFlowService.js`） |
| 配置项（配置先行） | `PURCHASE_CHAT_ID`（无默认值，缺则不发群）· `LARK_BOT_OPEN_ID`（无默认值，缺则群消息一律不处理）· `LARK_ACK_REACTION`（有默认值 `OneSecond`） | `server/src/config/groupPurchase.js` |

**映射落在哪**【代码事实】：`message_id` / `thread_id` ↔ 批次的映射写在**本地任务记录**
`server/data/purchase_group_messages/`，**不写业务表**（这是机器人的路由信息，不是经营事实）。
新流程要用的是映射里的 `batch_no` / `requestIds`。

### 4.2 ⚠️ 缺的那一段：话题消息 → 入库

**【业务负责人原话】** 缺的是这条路：

```
话题里说「核对完了」 → 发确认卡片 → 点「是」 → 入库
```

**入库那个零件还在**【代码事实】：

- `PurchaseWebhookService.confirmArrival(taskId, task, operatorOpenId)`
  → `confirmArrivalLocked`（`server/src/services/purchaseWebhookService.js`）
- 它**原来的入口**是「点卡片确认」（`handleCardAction` 里的到货卡片动作）；
  卡片随拍照识别一起退了，所以它**现在没有调用方**——孤儿能力，
  代码注释里写明「刻意保留，等『对话到货』接」。
- 它内部已经做对的：写「采购入库」行（按 `draft.actual` 的**实际数**）→
  调 `inventory.applyPurchase`（写「库存流水」+ 改「实时库存」）→ 回写状态；
  幂等三道（`inbound_created` 落盘 + 远端回查 + `confirmationQueue` 串行）。

**⇒ 要接的是**【实现要求，非她的口径】：

| 步 | 要新增/接线的东西 | 建议落点 |
|---|---|---|
| 话题消息进来到业务 | 定位到批次后，把这一句**记下来**（此时**不入库**、不发卡片） | `GroupPurchaseFlowService.handleGroupPurchaseMessage` 的 `matched` 分支（今天只记日志就返回） |
| **AI 判「核对完毕」** | 用**文字模型**判意图，**不是关键词匹配**；判据、提示词、模型调用要可配 | 新增独立 service（不要塞进 `PurchaseWebhookService`——它已经够大，且要守「一个 service 只干一件事」） |
| 发确认卡片 | 往**话题里**发「本次到货核对完毕，确认入库吗？」 | `GroupPurchaseFlowService` 已预留 `sendText` 注入位（`sendText` 今天无调用点） |
| 卡片回调 | 新增卡片动作（如 `confirm_purchase_arrival`，**名字沿用被删的那个或另起，实施时定**）→ 路由到服务 | `LarkMvpService.handleCardAction` 已有分派点，相邻有 `confirm_purchase_delivery` 等先例 |
| 调入库 | 卡片回调 → 保证 `task.draft.arrival_record_id` 与 `draft.actual` 已就位 → `confirmArrival` | `PurchaseWebhookService` |

**⚠️ 待改 1（与新口径直接冲突，必须处理）**【代码事实】：
`confirmArrivalLocked` 目前会**回写采购申请行**：

```js
await this.gateway.update('purchaseRequest', request.record_id, { arrivalStatus: status }); // 到货状态：未到货/部分到货/全部到货/超额到货
```

这与第 3 节「⚠️ 采购申请表（单据信息）**不动**」相冲突。
实施新流程时，这条回写要**移除或改到别处**——**具体怎么处理 ⚠️ 未定**（见第 6 节）。

**⚠️ 待改 2（新流程必须新建的那一行）**【代码事实】：
「采购到货」行的**创建代码已经被删光了**——全仓已无 `create('purchaseArrival', …)`
（`processArrival` 是它唯一的创建者）。而 `confirmArrivalLocked` 需要
`draft.arrival_record_id` 才能入库（它建「采购入库」行时用 `batch: relation(arrival.arrival_record_id)`，
并最后 `update('purchaseArrival', arrival.arrival_record_id, { confirmStatus: '已确认' })`）。
⇒ 新流程必须在入话题核对时**先建/找到那一条到货记录**，并往草稿里写
`draft.actual`（实际到货明细，形状与 `processArrival` 原先落的草稿一致）、
`draft.requests`、`draft.arrival_record_id`。

**⚠️ 待改 3（未知字段）**：「到货日」「验收原话」两个字段已有映射
（`v1BitableSchema.js` 的 `purchaseArrival.fields.arrivalAt` / `.acceptanceText`），
但「**把用户的原话归集进去**」里的「归集」落**哪个字段**——
现有字段只有单值的「验收原话」，没有「多句原话」的容器。
⚠️ **未定**：是覆盖成最后那句、还是拼接、还是由她加一列。**不要替她决定。**

## 5. 验收标准（跑之前先看这一节）

> 规矩来自业务负责人：**跑之前先看验收标准**。
> 勾选口径：每一条都是**在目标 Base 上可观察的事实**（表里的行、群里的卡片），
> 不是「代码看起来对」。

### 5.1 核对期间（还没点「是」）

|  | 检查项 | 出处 |
|---|---|---|
| □ | 「**采购到货**」表**还没有新行 / 没有被改**（先不入库） | 【业务负责人原话】此时不入库 |
| □ | 「**采购入库**」表**一个字都没变** | 【业务负责人原话】 |
| □ | 「**库存流水**」表**一个字都没变** | 【业务负责人原话】 |
| □ | 「**实时库存**」表**一个字都没变** | 【业务负责人原话】 |
| □ | 群里**没有**出现确认卡片（她还没说「核对完了」） | 链路 ③④ |

### 5.2 点「是」之后

|  | 检查项 | 判据（可核对的具体值） | 出处 |
|---|---|---|---|
| ① | 「**采购到货**」表：新增/更新 **1 行** | 含「**到货日**」（= 核对那天）＋「**验收原话**」（= 那句话）＋ 归集进去的原话 ＋ 「确认状态」= 已确认 | 【业务负责人原话】 |
| ② | 「**采购入库**」表：按**实际**到的数量写入库行 | 行的「数量」= **实际数**（不是申请数）；「采购行为」= 采购入库；「采购到货批次」关联到 ① 那行 | 【业务负责人原话】 |
| ③ | 「**库存流水**」表：新增行数 = **尺码数** | **一个尺码一行**；「变动数量」= 该尺码**实际双数**；「库存行为」= **采购增加**；「关联采购」指向 ② 的入库行 | 【业务负责人原话】＋【代码事实】粒度与既有「入库」实现一致（`inventory.applyPurchase` → `STOCK_MOVEMENTS['STOCK_PURCHASE_INCREASE']`，`direction: '增加'`） |
| ④ | 「**实时库存**」表：按**实际数**增加 | 已有该（货品+尺码+状态）行则改数量；**新尺码会新增行** | 【业务负责人原话】 |
| ⑤ | 「**采购申请**」表（现表名「**单据信息**」）**一个字都没变** | 特别看「到货状态」列 **不可被改写** | 【业务负责人原话】＋⚠️ 现存代码会写它（见 4.2 待改 1） |
| ⑥ | 群里那张确认卡片变成「**已入库**」状态（或给出明确反馈） | 不给「明确反馈」= 她以为卡住了 | 【业务负责人原话】「明确反馈」（后半句为工程要求） |

### 5.3 异常（⚠️ 这几条**尚未定**，先标为待定）
