## 二、团购券那块的金额怎么取（2026-10-08 实测确认）

- 金额口径（她的）：**券的「平台结算款」**。
- 定位链路：收款明细.**交易方式**（关联「收款方式管理.收款方式」，名字里带价，如 `抖音代金券（89.9）`）
  → 按名字里的价匹配「团购券管理.**售价**」→ 取该券的**平台结算款**（89.9 → 85.4；49.9 → 47.4）。
- ⚠️ 解析不到券时**退回「收款金额」**并记一条日志（**不静默**、也不编数）。
- 实测：`XSD-20260927-0143`｜交易方式 `抖音代金券（89.9）`｜收款金额 85.4｜券表结算款 85.4 ⇒ 一致（她当天已把这条改对）。

## 三、三个「先按这个做」的默认（她没反对就照此实现）

1. **逾期**：⭐ 她 2026-10-08 明确「**逾期未点的要展示**」，并给出展示维度：
   「**展示的维度是按照结算日**，比如今天应该结算多少，昨天应该结算多少，这样算的」
   ⇒ **一行 = 一个结算日**（今天 / 昨天 / 更早），**所有结算日 ≤ 今天且还没确认的都要出现**；
   结算日 < 今天的那行再标 **「逾期 N 天」**（这条是我加的提示，她不要就说一声）。
   理由（实测）：现存那笔核销日 09-27 ⇒ 结算日 **10-02**，只显示"今天该结算"会让它**再也不会出现**（漏账）。
2. **「确认到账」的语义**：把那**一个结算日**（同一批核销日）的全部「待平台结算」→ **已收款**，
   并写 **「收款时间」= 点击那一刻**；**幂等**（点两次不重复写）；只在**群**里可用（沿用私聊已移除的口径）。
3. **一单多件**：【预定】按**明细逐件一行**（她说的是"销售明细里的记录"）；
   【现货待收】按**收款明细**一行，文字里并列它关联销售单的货号/颜色/尺码。

## 六、第二步设计（Lead 调研，2026-10-08）：【团购券待结算】块 + 「确认到账」按钮

### 取数与显示
- **候选**：「收款明细」里 `收款状态 = 待平台结算` 的**全部**记录（含逾期未确认的）。
- **分组**：**一行 = 一个「结算日」**；`结算日 = 核销日 + 5 个自然日`，`核销日 = 收款明细.创建时间` 的**上海自然日**。
- **出现范围**：`结算日 ≤ 今天` 的全部（今天 / 昨天 / 更早）。
- **左栏**：`{结算日} 应结算 ¥{总额}`；结算日 < 今天时再附 **`（逾期 N 天）`**。
- **右栏**：按钮 **「确认到账」**。
- **金额**：逐笔取「券的平台结算款」——
  `收款明细.交易方式`（关联「收款方式管理.收款方式」，名字里带价，如 `抖音代金券（89.9）`）
  → 按价匹配「团购券管理.售价」→ 该券的 **平台结算款**（89.9 → 85.4；49.9 → 47.4）。
  ⚠️ 解析不到券 ⇒ **退回该笔「收款金额」**并记一条日志（不静默、不编数）。

### 按钮机制（已核代码）
- 按钮：`behaviors: [{ type: 'callback', value: { action: '<新动作常量>', settle_day: '2026-10-02' } }]`
  （**只带结算日，不带名单** —— 服务端按结算日**重新查**，不信任卡片上的旧数据）。
- 回调入口：`server/src/routes/larkEvents.js:49`（`card.action.trigger`）→ `larkMvpService`
  按 `value.action` 分发；已有串行队列 `cardActionQueue` 保证同一对象的动作**保序**。
- 新增：一个动作常量（放 `config/`，配置先行）+ **一个新的小 service**（一个 service 干一件事）：
  `confirmSettlementDay(settleDay)`：
  1. 重新查「该结算日全部 `待平台结算`」的收款明细；
  2. 逐条 `update`：`收款状态 = 已收款`、**`收款时间` = 点击那一刻**
     （⚠️ 这是全仓**唯一**允许代码写的时间列，与既有口径一致）；
  3. **幂等**：写之前回查状态；若已无「待平台结算」⇒ 回「这一批已经确认过了」，**不重复写**；
  4. 回一句人话：「已确认 N 笔、共 ¥X」；失败回原因（**不静默**）。

### 风险与纪律
- ⚠️ 这是本项目**第一次**用卡片按钮**改业务数据** ⇒ 按她定的流程：**先写"应该长什么样"（验收标准）→ 再实现 → 逐条对照**；
  并且要**幂等测试**（连点两次只写一次）+ **只在群里可用**（私聊链路已移除）。
- 三个默认（她未反对即照此做）：① 逾期行标「（逾期 N 天）」；② 点完**回一句结果**；③ 「收款时间」**覆盖**为点击时刻。

⇒ **服务端两次都成功**、业务数据**没有重复写**（幂等是好的）；问题在"她看不到变化"。
三种可能（都要修掉）：① 客户端没刷新；② 卡面变化不显眼；③ patch 打的那条**不是她正在看的那条**。

### 验收标准
1. **点完立刻醒目地变**：标题 + header 颜色 + **按钮整块消失**（不是只改一行状态字）。
2. **patch 打她点的那一条**：用回调事件里的 `open_message_id`（不只用本地存的 `card_message_id`）。
3. **点了先锁**：按钮变「处理中…」或先去掉；**重复点击**只回 toast「这一单已经确认过了」，不再重复 patch。
4. **加交易方式**：
   - 卡片上给「收款方式」选项（第一笔）；
   - **对还会有第二笔收款（未收齐）的单，在确认时把第二笔的方式一并给到**（两排按钮：第一笔方式 / 尾款方式），并写进「收款明细」；
   - 她原话里已经说过的方式 ⇒ 预选/高亮；**不许默认微信**（全仓没有这个默认值，AI 提示词里的 `method:"微信"` 只是举例，要防它被当成默认）。
5. **不静默**：点完回一句人话（成功写进什么、还差什么）。
