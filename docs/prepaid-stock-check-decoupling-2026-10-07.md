# 设计：按交易类型「拆开」销售录单里的两个解析（业务负责人 2026-10-07 确认）

> 她的原话（逐字）：
> 「**预付的原因是因为库存里没有，所以需要调货。既然已经判断为预付，
>  系统实际上就不应该再去库存里面找了。**」
> 「**因为它实际上还是要写销售明细的，所以这个时候需要提供颜色信息，
>  也就是要以这个货号去找它的颜色，然后只不过是它就不需要再去实时库存里面查有没有这个库存了。**」
> 「**如果是预付的话，其中一个链路它应该是要把它给解除掉的。**」
> 「**注意不要影响其他已经跑通的流程。**」
> 她逐字确认了下面的设计（「**我觉得这个思路很好**」）。

## 起因（真机，2026-10-07 16:30）

她发：「`26002-52 37 码，定金微信交了 100 元，下次欠 128 元`」
- 解析**完全正确**：`trade_type=预付` · `payments=[{100,微信}]` · `agreed_total=228` · `owed=128`
- 但缺项判定报了**两条**、把她拦住（没有确认卡片）：
  1. 🔴 「请明确已经收到的定金金额」← **误报**（她已说、也已解析出来）
  2. 🔴 「库存里没有 26002-52 37码（这个货号现在一双都没有）」← **预付本来就没货（要调货）**

## 设计（**要落地的形状**）

### ① 把两个解析**拆开**，各管一件事
| | 解析 | 读哪张表 | 谁要跑 |
|---|---|---|---|
| **A** | `resolveProductInfo(item_no)` → 颜色 / 类别 / 商品记录 id | 「货品信息」 | **所有交易类型都要**（保证销售明细能写全） |
| **B** | `resolveStockAvailability(item_no, size)` → 门盒/样品/仓库 数量 | 「实时库存」 | **只有需要库存的交易类型** |

### ② **配置先行**：用配置声明"哪种交易类型要哪些检查"
新增 `server/src/config/salesTradeTypePolicy.js`（名字可调整，但要**一处可配**）：
```
现货 → 要库存
未付 → 要库存
预付 → 不要库存（货还没到、要调货）
```
⇒ 以后再加/改交易类型的规则，**只改配置、不改逻辑**。

### ③ **解除的只有 B**（不是整步跳过）
- 🔴 **A、收款、建单、确认卡片、销售明细写入 —— 全部保留**。
- 🔴 交付/扣库存逻辑（`shouldDeliverFor` 等）**不动**（预付 → 不交付，是既有行为）。
- 🔴 **不影响已经跑通的流程**：现货 / 未付 的"没库存就拦"**必须原样保留**。

## 同时要修的另一个 bug
「请明确已经收到的定金金额」**误报**：她已经说了、解析也对 → 缺项判定必须看 `payments`，
**说清了就不问**；她**没说**收多少 → **仍然要问**（这条不许放宽）。

## 验收（实现方必须逐条给证据）
1. 她说「定金微信交了 100，下次欠 128」→ **无缺项**、直接出确认卡片，
   `payments=[{100,微信}]` / `agreed_total=228` / `owed=128` 三个值都对。
2. 只说"欠"、没说收到多少 → **仍然要求补充**（不放宽）。
3. **预付 + 该货号完全没库存** → 能出卡片；且**颜色/类别照样解析出来**（销售明细能写全）。
4. **现货 + 没库存 → 仍然被拦**（既有行为不许破）。
5. **未付 + 没库存 → 仍然被拦**。
6. A/B 是**两个独立函数**（不是"一个大步骤里加个 if"）；配置是**唯一**的判据来源
   （逻辑里不许再出现 `=== '预付'` 之类的散落判断）。
