> 她的原话（逐字）：
> 我问：「扫码页第 2 步填的整单付款，你想让它**当场就写进表**吗？（甲）当场写 …（乙）只填不写 …」
> 她回：「**当然啊，可以写也可以不写啊**」

## 一、口径（**可写可不写** ✓）
```
⭐ 第 2 步**填了** ⇒ **当场写进「收款明细」** ✓（提交/保存那一刻入账 ✓）
⭐ 第 2 步**不填 / 跳过** ⇒ **不写** ✓，这一单记成「**待补充的信息单**」✓（**不是失败** ✗ 不报错 ✗）
⭐ 两者都不阻塞她继续录下一单 ✓
```

## 二、写入必须走**既有那条路**（不许新造钱路 ✗）
```
· 复用工作台「订单列表 → 补记收款」的同一条：`followup.addPayment({ salesEntryRecordId, method, amount, requestId, operatorOpenId })`
  （实现见 `routes/workbench.js:215` 一带 ✓ 写的是同一张「收款明细」表 ✓ ⇒ **不会出现两套账** ✓）
· ⚠️ 付款方式的候选**仍然读「收款方式」表** ✓（与 PR #475 / PR-B 同一条真源 ✓ 不许回落旧清单 ✗）
```

## 三、三条诚实红线（**不许撒谎** ✗）
```
1. 🔴 **写成功** ⇒ 才允许显示"已收款 / 已付" ✓；**写失败** ⇒ **明说失败 + 人话**（不许假装成功 ✗）
2. 🔴 **跳过** ⇒ 明确记成「待补充的信息单」✓（不许显示"已收" ✗，也不许显示"失败"✗）
3. 🔴 **幂等**：同一次提交不许重复入账 ✓（沿用既有 requestId / 幂等键机制 ✓ **不许自造** ✗）
```

## 四、验收标准（实现时钉住）
```
· `第 2 步填了付款 ⇒ 「收款明细」真的多一行，金额/方式逐字一致` ✓
· ⭐ `第 2 步跳过 ⇒ 「收款明细」零新增，单子标记为待补充` ✓
· ⭐ `写失败 ⇒ 页面明确报错（人话 + 可重试），且**不显示**已收款` ✓

```
