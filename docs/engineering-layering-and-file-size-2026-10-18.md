# 工程分层与文件大小门禁（2026-10-18）

> **一句话**：入口只做 plan/steps，规则进 `config/`，写入进小模块，大 service 只做 facade；
> 文件大小用**棘轮**（baseline 只降不升）+ CI 门禁挡住"越写越大"，每个 PR 顺手拆一小块（≤200 行）。
>
> 本页是**工程写法约定**，不改任何业务口径。业务口径仍以 `AGENTS.md` 与 `docs/README.md` 的「现行事实」为准。

## 0. 为什么要立这条规矩

2026-10-18 用脚本盘了当前 `main`：

| 范围 | 文件数 | 超限文件 | 上限 | 最大文件 |
| --- | --- | --- | --- | --- |
| `server/src/**/*.js` | 213 | 16 | 800 行 | `services/inventoryService.js` 2280 行 |
| `server/test/**/*.js` | 369 | 7 | 1200 行 | `test/scanSaleE2E.test.js` 2443 行 |

大文件本身不是罪，问题在**继续变大**：一处功能改动要在大文件里找一个插入点，评审看不见边界，
合并冲突、同名方法静默覆盖、回滚困难都从这里长出来。所以做两件事：

1. **不再变大** —— 存量超限文件登记进 `size-baseline.json`，之后任何增长直接红；
2. **新代码按分层写** —— 从下一次改动起，新逻辑默认落到正确的层，而不是最近的大文件。

## 1. 默认分层（四层）

| 层 | 位置 | 只做 | 不要做 |
| --- | --- | --- | --- |
| 入口层 | `routes/**`、`controllers/**` | **plan / steps**：解析请求 → 生成计划 → 调用模块 → 渲染反馈 | 业务规则、字段映射、写库细节、数值阈值 |
| 规则层 | `config/**` | 阈值、开关、字段映射、行为编码、文案 | 写库、发请求、判断"这次该怎么算" |
| 写入层 | `services/**` 的小模块 | 一个 service 只干一件事：一次写入 / 一条链路的一段 | 顺手把另一条链路的逻辑也塞进来 |
| 编排层（facade） | 历史大 service（如 `scanWriteService`、`purchaseWebhookService`、`scanPageService`） | 编排、兼容旧调用、把 plan 交给小模块 | 新增业务分支、继续堆 if-else 和字段处理 |

### 1.1 入口只留 plan/steps

```js
// routes/xxx.js —— 入口只做四步，别在这里算账
const plan = buildXxxPlan(input);      // 纯函数：解析 + 校验 + 生成计划（可单测）
const result = await xxxService.execute(plan); // 小模块执行写入
renderXxxPage(result);                 // 渲染 / 反馈
```

判断法：**"这段逻辑能不能脱离 HTTP 请求单独测？"**
能 ⇒ 它属于计划层或小模块，不属于路由。

### 1.2 规则进 `config/`

阈值、开关、字段名、行为编码、用户可见文案**一律可配**。开关必须是**显式布尔**，
不要写 `process.env.X || fallback`（清空变量会回退默认值 ⇒ 关不掉，见 `AGENTS.md`
「配置先行」）。

判断法：**"换一个数字 / 名字 / 开关，需要改代码吗？"** 需要 = 没做到配置先行。

### 1.3 写入进小模块

新写入逻辑先问：**"这段属于哪个已有小模块？"**
- 有 ⇒ 放进去（它 ≤800 行、职责单一）；
- 没有 ⇒ **新建小模块**，并在入口/facade 里接线；
- 只有"这条链路的编排顺序"才放进历史大 service。

反例：往 2000 行的 service 里再加一个 `if (type === 'xxx')` 分支 —— 这就是门禁要挡的形状。

### 1.4 大 service 只做 facade

存量超限文件（见 `server/scripts/size-baseline.json`）继续可用，但**只做编排/兼容**：
新规则、新字段处理、新分支都进小模块，大文件里只留一句调用。
拆的时候按"一次搬一块能独立测的逻辑"做，不要为了降行数做纯格式化搬迁。

## 2. 文件大小门禁

### 2.1 规则

- 源码 `server/src/**/*.js`：单文件 **≤ 800 行**；
- 测试 `server/test/**/*.js`：单文件 **≤ 1200 行**；
- `server/scripts/size-baseline.json` 是**存量超限白名单**，登记每个文件当前行数；
- **白名单只允许变小**：文件比基线多 1 行就红；新文件 / 新超限不在白名单 ⇒ 红；
- 既有文件（base 里存在）**净增 > 100 行** ⇒ 红；新增文件不计净增（只受上限约束，
  鼓励把新逻辑写成小模块，而不是塞进老文件）。

### 2.2 怎么跑

```bash
cd server
pnpm run size:check                 # 门禁（0 绿 / 1 红）
pnpm run size:baseline              # 生成 / 下调 baseline（只许变小，拒绝上调）
node scripts/check-file-size.mjs --base <ref>   # 指定「净增」比较基线
```

> 不想经过 pnpm（独立 worktree / 没有安装依赖的环境）时直接用
> `node scripts/check-file-size.mjs`，与 `pnpm run size:check` 等价。

- CI：`.github/workflows/server-tests.yml` 的 **`file-size`** job（与 test job 分开，
  `fetch-depth: 0` 以便和 base 提交做 diff）；
- 本地跑没有 git 基线时，只跳过「净增」这一条（会打印提示，不假装通过），棘轮始终生效；
- 输出会逐条给出：文件、当前行数、基线/上限、判红原因。

### 2.3 baseline 的语义

| 情况 | 结果 |
| --- | --- |
| 白名单文件行数 ≤ 登记值 | 绿（提示可下调基线） |
| 白名单文件行数 > 登记值 | **红**（基线只允许变小） |
| 文件缩到上限以内 | 绿 + 提示可以从白名单移除 |
| 新文件超过上限 | **红**（不允许自动登记） |
| 既有文件净增 > 100 行 | **红**（要求拆小） |

更新 baseline 用 `pnpm run size:baseline`：它**只会下调或移除**条目，遇到"比登记值更大"
会直接拒绝写入 —— 不要手改 JSON 上调数字。

### 2.4 误报 / 豁免规则

- **不允许**通过改阈值、删白名单条目、关 CI 来过关（门禁的价值就在于它不商量）。
- 唯一合法豁免：**一次性大迁移**（整文件搬迁、批量改名、大块代码移动）。
  做法：PR 描述写清「为什么必须一次做」+ 拆分计划 + 负责人确认；由维护者在同一 PR 跑
  `pnpm run size:baseline` 登记**新条目**（已有条目仍然只降不升）。
- 生成代码 / 第三方代码不在扫描范围（`src/`、`test/` 只收手写 JS）；
  自动生成的文件如果必须入库，放扫描范围外，不要塞进 `src/`。
- 「净增」误报（例如整文件 rename）：把 `--base` 指到搬迁起点，或在 PR 里说明；
  不要为此关掉门禁。
- 拆分产生的**新文件**不受「净增 > 100 行」限制 —— 这正是鼓励的方向；它只受 800/1200 上限。

### 2.5 PR 模板里的两条必答

`.github/pull_request_template.md` 要求每个 PR 回答：

1. **这个新逻辑为什么放在这个文件？** 能不能落到已有模块 / 新模块？
2. **本 PR 是否让某个文件净增 > 100 行？** 如果是，拆分计划是什么？

答不上来 ⇒ 说明改动还没想清楚，先分层再写代码。

## 3. 顺手拆一小块（≤200 行预算）

- 每个功能 PR **允许顺便拆一块 ≤200 行**：把本次正好碰到的一小段逻辑抽成独立模块，
  和功能在同一个 PR 提交；
- 拆出的模块要有**单一职责**，原文件只留调用 / facade；
- 既有测试保持绿；新模块至少有**一条测试直接覆盖**（没有就补最小单测）；
- **不追求一次拆完大文件**：门禁只要求"不变大"，每次顺手拆一点，存量会自然收敛；
- 一块拆出来仍 >200 行 ⇒ 说明切得不够小，继续切。

## 4. 测试分层

- **E2E 按场景拆文件**：一条链路 / 一个场景一个文件，不要在一个文件里塞多条链路
  （单文件大了之后，失败定位、并发修复、评审都会一起变差）；
- **共享 fixture / 替身进 `server/test/helpers/`**：例如 `pendingPushTestData.js`；
  跨用例的表 ID / env 基建进 `server/test/support/`；
- 测试文件同样受 **1200 行**上限与 baseline 棘轮约束；
- 真实 Base 用例走独立入口 `test/realbase/`（见 `AGENTS.md`「本地自动化测试」），
  不混进默认 `pnpm test`。

## 5. PR 自检清单

- [ ] 新逻辑落在正确的层（不是随手加进最大的那个文件）
- [ ] 阈值 / 开关 / 字段映射在 `config/`，没有硬编码
- [ ] `cd server && pnpm run size:check` 绿
- [ ] 某个文件净增 > 100 行？→ 已有拆分计划（或已拆）
- [ ] 新测试按场景拆文件，共享 fixture 进 `test/helpers/`
- [ ] 顺手拆了一小块（≤200 行）—— 推荐，不是硬性
- [ ] 没有为了过门禁去改阈值 / 删白名单 / 关 CI
