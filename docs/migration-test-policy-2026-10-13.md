# 架构/入口迁移时，自动化测试怎么改（业务负责人 2026-10-13：「自动化测试的你记得改一下～」）

> 背景：我们正在把扫码页的能力（验收 / 标签打印 / 上新 …）逐个搬到工作台，
> 并把扫码页的「工作台」tab 换成「上新」等。入口一变，**测试必然有要改的地方** ——
> 这份文件把"**哪类必须改、哪类一个字都不许改**"钉死，避免迁移时把护栏改松 ✗。

## 一、🔴 不许改（必须一直全绿）
**锁"钱货账 + 状态机"的行为测试**，与"入口在哪一页"无关：
- 幂等（同一次提交不重复入账 / `submit_key` / `posted_keys`）
- **现货 ⇒ 提交即交付 + 扣库存**（`SalesDeliveryService.deliver` 唯一通路）
- **预订 ⇒ 提交不交付**（等货到再交付、那时才扣库存）
- 库存流水 / 实时库存 / 到货状态=已到货 的写入结果
- **信息没填全 ⇒ 同步到工作台的既有逻辑与状态口径**
- 串行队列 / 顺序（先前置再入库）
⇒ 迁移期间这些断言**一个字都不许动** ✗（动了就是"把护栏改松" ✗）

## 二、随架构改（只改"在哪看"，不放宽"对不对"）
**锁"页面长什么样 / 走哪个路由"的测试**：
- 「这个页面 HTML 里有这个按钮」「这个路径 200/302」「tab 文案与顺序」
- 「某个入口在扫码页 / 在工作台」
⇒ 迁移时**必须改** ✓ 但：
1. ⭐ **只改断言的"位置/来源"**，**不许**放宽断言、不许加 `retry`、不许删断言 ✗
2. ⭐ 改之前先让**新入口的测试先红后绿** ✓（证明它测真行为）
3. ⭐ **新旧同时绿**才算迁移安全 ✓（老测试先不动 ✓）

## 三、必须新增的三类哨兵（迁移的核心保障）
1. ⭐ **两条入口等价**：`从工作台做一次 X ⇒ 结果与从扫码页做【逐字相同】`
   （到货状态 / 库存流水 / 实时库存 / 收款 / 明细 ✓）
2. ⭐ **旧入口下线哨兵**：迁移完成后 `旧路径不可达` ✓
   （防止两套并存、各处行为不一致 ✗）
3. ⭐ **单一来源 / 不许漂移**：
   · URL（如「货品上新」表单）只能有一份来源 ✓ 两边必须逐字一致 ✓
   · `MAIN_TABS` 的顺序/文案唯一来源 ✓ · AppLink 与扫码页**同源** ✓

## 四、执行顺序（每次迁移照抄）
```
1. 新入口：先写 AC（先红后绿）
2. 老测试：先不动 ⇒ 新老同时绿 = 迁移没破坏任何东西
3. 真页面 / 真机证据
4. 她确认真机可用 ⇒ **才**下线旧入口 + 把"页面形状"类断言改到新入口
5. 全量 0 失败 + 旧入口哨兵 + 等价哨兵
```

## 五、自检三问
1. 我改的是"**在哪看**"还是"**对不对**"？（后者 ⇒ 停手 ✗）
2. 我的改动有没有**放宽**任何断言？（有 ⇒ 停手 ✗）
3. 我有没有加"**等价 + 下线 + 单一来源**"三类哨兵？（没有 ⇒ 不算迁完 ✗）
