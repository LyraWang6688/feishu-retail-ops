# 售后（退货 / 换货）逻辑定稿（2026-10-29）

> 来源：业务负责人 2026-10-29 多轮逐字口径 + 生产表只读核对（她的飞书 CLI，只读）。
> 本文是**对完口径后沉淀**的版本；实现前以本文为准。赔货本次**只做前端占位、不开发**。

## 0. 总原则

1. **售后是衍生单**：必须先有一笔正常销售，才谈得上售后。
2. **销售主表不新建记录**：在原销售主表上"字段丰富"（售后类型多选累加 + 售后次数 +1）；
   「销售明细 / 收款明细 / 库存流水」是双向关联列，新记录带上关联后自动回显。
3. **货怎么走 / 钱怎么走 分开考虑**，两者可独立。
4. **异步**：用户点确认 → 立即 toast「数据提交成功」→ 后台写库；
   API 临时失败自动重试（3 次），最终失败 **弹失败 toast**（不假成功）。
5. **交易明细类型**（业务负责人 2026-10-29 定稿）：`收款 / 退款 / 留存`；
   交易明细ID 格式 = `{销售单号}-{类型}-{两位序号}`，例：
   `XSD-20261028-0005-收款-01` → `XSD-20261028-0005-退款-02` → `XSD-20261028-0005-留存-03`
   （**序号 = 这一单所有交易明细的最大序号 +1**，收款/退款/留存共用）。

## 1. 退货

### 1.1 前端交互（弹窗，参照交割单页付款弹窗）

- 点卡片（一张卡 = 一双）上的「退货」→ 居中弹窗：
  - 商品信息（货号 / 颜色 / 尺码）只读；
  - **金额只读** = 这双鞋在「销售明细」里的金额（不看收款行；一双多支付方式也按明细金额）；
  - 两个操作按钮：**退款** / **留存**；
    - 选「退款」→ 再选**退款方式**（选项来自「支付方式管理」配置表，必选）；
    - 选「留存」→ 不出现退款方式；
  - 确认 → 提交（异步）。
- 退回的鞋**固定回门盒**，不再让用户选样品/门盒。

### 1.2 货

| 步骤 | 落点 | 写什么 |
|---|---|---|
| ① 原销售明细 | 履约状态 | **已退货** |
| ② 库存流水（新增 1 行） | 库存流水 | 库存行为 = **销售增加**（生产行为编码 `STOCK_SALE_INCREASE`，方向=增加；只读核对过） |
| ③ 实时库存 | 同一双 +1 | **门盒** |

### 1.3 钱（两种都是**新建一条 S交易明细**，不改原行）

| 字段 | 退款 | 留存 |
|---|---|---|
| 交易明细ID | `{单号}-退款-NN` | `{单号}-留存-NN` |
| 金额 | 这双鞋的销售明细金额 | 同左 |
| 支付方式 | **她选的退款方式**（来自配置表） | **不填** |
| 收支方向 | **退回**（生产选项只有 收入/退回） | **不填** |
| 钱款状态 | **已退款** | **已留存** |
| 收付日 | **点击当天**（服务端时间） | 同左 |
| 关联销售单 | 原销售主表 | 同左 |

### 1.4 原销售主表

- 「售后类型」多选：**累加「退货」**（生产选项：退货 / 换货 / 赔货；多选 `multiple=true`）；
- 「售后次数」：**+1**。

### 1.5 配置表复用（退款方式）

- 读「支付方式管理」**只用项目现有统一配置逻辑**：
  `services/configTableCache.getConfigRows()`（TTL 30 分钟 + lastGood + record_changed 失效）
  ＋ `services/paymentMethodsService.list()/listWithVouchers()`（已按「出现顺序」排序、去重）。
- **不新增缓存、不写死选项**；写库前用同一服务校验她选的方式仍存在。

## 2. 换货

> 换货 = **一次退货（货流）** + **一次新的购买（货流）** +（换款式时）**差价（钱）**。

### 2.1 场景

- **换尺码**：同款换另一个尺码；新尺码从**库存已有尺码**里选（复用库存尺码查询接口）；**没有差价**。
- **换款式**：走**扫一扫**（同销售页扫货品）→ 拿新货品 → 让她选尺码；**可能有差价**。

### 2.2 货（两种场景相同）

| 步骤 | 落点 | 写什么 |
|---|---|---|
| ① 原销售明细 | 履约状态 | **已退货** |
| ② 新增一条销售明细 | 销售明细 | 新鞋：**履约状态=已交付**、销售单号=原单（关联） |
| ③ 库存流水 **两条** | 库存流水 | **销售增加**（旧鞋回门盒）+ **销售减少**（新鞋出门盒） |
| ④ 实时库存 | 实时库存 | 旧鞋 **+1**（门盒）、新鞋 **−1**（门盒） |

- 新明细「实收金额」：换尺码 = 原明细金额；换款式 = 新货品「单价」。
- 新明细「销售明细ID」沿用同单号连续排号（`salesRecordIds` 规则）。

### 2.3 换款式的交互（复用销售扫码的**货品页**）

1. 售后页点「换货」→ 选「换款式」→ **起扫一扫**扫新鞋的货品码；
2. **跳转到销售扫码的货品页**（复用同一个页面/同一套选货逻辑），带上售后上下文
   （原销售单、原明细、原明细金额、售后 requestId）；
   - ⚠️ 该页提交时走**售后接口**，**不建销售单**（售后是衍生单）；
   - ⚠️ `scanWriteService.js` 是冻结件：**不修改它**，在它外面挂售后上下文分支；
3. 货品页选新鞋**尺码**（换货固定 **1 双**）→ 点提交；
4. 系统计算：**新鞋金额（货品「单价」）− 原明细金额 = 差价**；
5. 差价 ≠ 0 → 让她选**差价方式**（补差价=收款方式 / 退差价=退款方式，来自「支付方式管理」配置表）；
   差价 = 0 → 不选方式，直接完成；
6. 提交后**只有一句 toast「信息提交成功」**（不跳成功页、不新增成功页）；
7. 后台异步写库（同退货：重试 3 次，最终失败弹失败 toast）。

### 2.4 钱（只看差价；换货**不复制退货的退款/留存记录**）

| 场景 | S交易明细 |
|---|---|
| 换尺码 | **完全不动**（无差价） |
| 换款式·无差价 | **完全不动** |
| 换款式·补差价（新 > 原） | 新建一条：收支方向=**收入**、钱款状态=**已收款**、金额=差额、支付方式=她选 |
| 换款式·退差价（新 < 原） | 新建一条：收支方向=**退回**、钱款状态=**已退款**、金额=差额、支付方式=她选 |

- 差价 = 新鞋金额 − 原明细金额；
- 差价行的交易明细ID：补差价用 `{单号}-收款-NN`、退差价用 `{单号}-退款-NN`。

### 2.5 原销售主表

- 「售后类型」多选：**累加「换货」**；
- 「售后次数」：**+1**。

## 3. 不做 / 占位

- **赔货**：前端保留按钮但**灰置不可点**，不开发任何功能（后端旧实现保留可回退）。

## 4. 幂等与失败处理

- 页面每次提交生成 `requestId`（UUID），重试复用同一个；
- 服务端按 `requestId` 分片记录进度（JSON 任务记录），每个阶段写完落盘 ⇒ 重试/断点续做不重复写；
- 异步任务状态：`queued / running / succeeded / failed`；前端轮询；
- 失败分类：她填错（400）不重试；API 临时错误重试 3 次；最终失败弹失败 toast。
