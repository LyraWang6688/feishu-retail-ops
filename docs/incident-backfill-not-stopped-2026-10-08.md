# 事故记录：批量脚本「以为停了、其实在跑」（2026-10-08）

## 发生了什么

1. 我在服务器上启动「标签二维码」存量回填（`server/scripts/backfill-product-tag-qr.js --write --concurrency=2`），
   意图是**先只跑 1 条**验证；
2. 业务负责人在此时说「**先看下样式，没问题你再跑全量**」；
3. 我**中断了我这一侧的调用**（工具调用被 abort），并据此向她汇报「全量没跑」；
4. ⚠️ **事实是：服务器上的进程没有被中断**，从 **20:19 跑到 20:33**，写入了 **275 / 562 条**；
5. 我 20:34 才真正 kill 掉进程。她发现表里出现了大量二维码，来问「怎么还有人还在生成？」。

## 两个错误（都记下来）

1. 🔴 **「我中断了调用」≠「服务器上的进程停了」** ——
   通过 SSH 起的后台进程，**客户端断开不会终止远端进程**。
   ⇒ 跑生产批量之前，必须先明确「怎么停」（`pgrep -f <脚本名>` + `kill`），
   或者**只跑明确的小批（`--limit=` / `--only=`），观察确认后再放开**。
2. 🔴 **结论性的话（"没跑""没写"）必须先核事实表再说** ——
   我当时只是看到自己的调用被中断，就当成了"没跑"。
   ⇒ 正确做法：**读表/读报告核实**（本次是 `listAll('product')` 数「标签二维码」非空条数 = 275）。

## 业务负责人当时的处置（2026-10-08 20:4x）

- 已生成的 **275 条「保留」**（内容按规范、正确可用）；**剩下 287 条不生成**，等她说「继续生成」；
- 两个隐患（群话题把售后件当未交付 / 退货复制明细行导致应收重复计入）与团购券卡面问题：
  **"先不管"**（暂缓，不做）。

## 下次跑生产批量的硬规则（写死）

1. **先 dry-run**（脚本默认就是 dry-run），把清单与 URL 给她看一眼；
2. **先小批**：`--only=<1 条>` → 读回验证 → 再 `--limit=5` → 再放开；
3. **开跑前先写好"停"的命令**（`pgrep -f` + `kill`，且 `pgrep` 模式不要匹配到自己的 SSH 会话）；
4. **跑完/停掉后，一定读表核对实际条数**，再汇报；
5. 涉及生产写入的批量：**Batch 越大越要先跟她确认时间窗**（她在现场操作时不要跑）。
