## 一、要解决的现象

| 现象 | 例子 |
|---|---|
| 一次提交被**拆成好几张图** | 「一次提交 3 条，全是采购申请 → 出了 **3 张**采购单」 |
| 她一次只提交一次，看到的图却是分开的 | 报货、退货两边都出现过 |
| 更糟的一种（还没在生产踩到，但有踩的窗口） | 一批退货里**第 2 条写失败** → 第 1 条已经扣了库存、**图一张都没发** |

## 二、一句话方案

> ⭐ **到齐就发**：飞书一个 action 里拆成几条，**就等这几条的处理动作跑完**，出一张图。
> ⭐ **读不到就重试**：读表遇「数据还没准备好」，**最多 3 次、间隔 1 秒 → 2 秒（共约 3 秒）**。
> ❌ **不设超时兜底**（她 2026-10-06 明确：「不需要兜底」）；
> ❌ **不考虑拆包**（她明确说：「现在不考虑拆包的问题」）。

⚠️ 这不是「多等几秒」的调优，而是**判据换了**：
现在是「猜一个时间够不够」，改成「数这一包**进了链路的条目**，处理动作跑完了没有」。
⭐ 好消息：**「这次有几条记录」不用问她、也不用读表**——
飞书推事件时把这个包裹里**每一条记录的动作都列出来了**；
我们要等的就是**其中进了链路的那几条**，把处理动作跑完。
所以这个改动**不需要新增任何表字段**，也不改表结构。
⚠️ 注意别数错：飞书给的"动作总数"里混着我们自己回写造成的"修改"，
要认的是**其中「新增」的条数**（第三节 ① 详说）。

### ③ 配置先行（她定的「重中之重」）

阈值一律进配置，不写死在逻辑里：

| 配置 | 作用 | 取值 |
|---|---|---|
| **重试次数** | 读表遇「数据没准备好」重试几次 | **3 次**（复用 `batchReadMaxRetries`；按配置先**挪到 `.env`**） |
| **重试间隔** | 两次重试之间等多久 | **1 秒 → 2 秒（共约 3 秒）**（复用 `batchReadRetryDelay`；同样挪到 `.env`） |

| **是否提示** | 少了记录时，群里要不要说一句 | ⚠️ **待她定**（见第三节 ④ / 第六节） |

⚠️ 沿用项目既有取值风格：**显式取值，不写 `process.env.X || 默认值`**
——那个写法会让「清空变量」变成「回落到默认值」，于是**关不掉、改不动**（属静默失效）。

⚠️ **顺带两个小缺口**：

## 五、验收标准（先写"应该是什么效果"，再实现，再逐条对照）

| # | 验收标准 | 怎么判 |
|---|---|---|
| ① | 一包 N 条（N 条「新增」）→ **只出 1 张图** | 整批只渲染 **1** 张图，图上明细含**全部 N 个货号** |
| ② | 一包里先到了 M 条（M < N）→ **第 N 条处理动作跑完前，一张图都不发** | 到齐前：**0 次**远端写入（没有单据、没有图、记录状态不变） |
| ③ | **到齐 → 立刻**出图 | 第 N 条处理动作跑完 → **立即触发**（日志里能看出是"到齐触发"而不是"窗口到点触发"）；从触发到发图的耗时与单条链路一致 |
| ④ | ⭐ **两层互相独立**：某条**没有内容可画**（行为不是退货 / 货品查不到 / 尺码数量算不出来）→ **它不进图，但不挡整批出图** | 第一层照常算「跑完」→ 出图；图上**不含**那条 |
| ⑤ | **采购申请 / 采购退货两侧行为一致** | 两条链路各跑一遍，②③④ 判据相同 |
| ⑥ | 单条写失败**不拖死整批** | 第 2 条失败 → 第 1 条照常出图；群里提示**哪几条没成** |
| ⑦ | **幂等**：重复投递 / 重试 / 补发 → 不重复写 | 单据、库存流水、实时库存、图**一个都不多** |
| ⑧ | 「数据慢一拍」→ **自动重试 3 次（1 秒 → 2 秒）**，不落失败 | 第一次读表抛错 → 重试后照常处理，不留失败终态 |
| ⑨ | ⚠️ **跨批不误合**：不同批次号的两次提交**不能合成一张图** | 两个不同批次号 → **2** 张图 |
| ⑩ | ❌ **判据里没有时间**（没有超时兜底） | 把窗口时长改成任意值，出图时刻**只由「处理动作跑完」决定**，不再由窗口到点触发 |
