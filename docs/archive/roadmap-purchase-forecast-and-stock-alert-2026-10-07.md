# 未来规划：采购预测 + 库存预警（业务负责人 2026-10-07 提出）

> 她的原话（逐字）：
> 「然后你**加两个未来的规划**，一个是**采购预测**，根据用户的**实时库存和销售情况**，
>  给到用户**采购建议**，以及给到**库存预警提示**」

⚠️ **本文件只记"要做什么"，不写"怎么做"** —— 动手前要先把下面的待定口径问清楚（见第 3 节）。

## 1. 采购预测（采购建议）

**目标**：根据**实时库存** + **销售情况**，主动给她**采购建议**。

已知口径（本仓既有、可直接作为输入）：
- 实时库存：`实时库存` 表（只读查询；工作台「实时库存」页现在也只做查询）
- 销售情况：`销售明细`（履约状态 = 已交付的条数 = 卖的"单数"，一条明细 = 一双鞋 = 一个单子）
  + `收款明细`（已收款且收款时间为当天的金额）
- 采购侧现状：供应商报单 → 采购申请（免确认）→ 发采购群（@经办人）→ 对话到货 → 入库

## 2. 库存预警提示

**目标**：库存异常（如低于某阈值 / 某尺码缺货）时**主动提示**。

## 3. ⚠️ 待定口径（动手前必须问清楚，别自己猜）

1. **建议/预警在哪儿出现**？群推送（哪个群）／工作台页面／两者都要？
2. **触发时机**？定时（几点）／有新销售就重算／库存变动即触发？
3. **预警阈值谁定、怎么配**？按货号？按尺码？（本仓"配置先行"：阈值一律可配，不写死）
4. **"建议采购多少"的算法**口径：看最近 N 天销量？看安全库存？还是她给经验值？
5. 采购建议要不要**直接生成采购申请**（免确认），还是**只提示、等她确认**？
   ⚠️ 本仓现状：**"采购申请"是唯一免确认的链路**（她的既有决定）；新链路要不要继承这条，必须她拍板。
6. 数据来源的**表与字段**：以生产真表为准（动手前只读核一遍，别凭记忆）。

## 4. 与现有架构的关系（改代码时的自检）

- 解耦：预测/预警**不许绑死**在某条会变的链路上（例如拍照识别已退场）
- 模块化：建议新建独立 service（例：`purchaseForecastService` / `stockAlertService`），
  **不要**往 `PurchaseWebhookService` 这种"什么都管"的大类里继续加
- 配置先行：阈值 / 触发时间 / 目标群 → 全部可配（显式布尔，不用 `process.env.X || fallback`）
