# 「硬编码中文」守门测试的一次性改造（业务负责人 2026-10-13 批准「做吧～」）

## 一、为什么现在老出事（根因）
现有实现 = `test/support/hardcodedChinese.js`（扫描 `src/services|routes|views`）
+ `test/fixtures/hardcodedChineseWhitelist.json`（**存量清单**）+ `test/noHardcodedChinese.test.js`。
它**两个方向都会红**：
1. **新增**中文（不在清单）⇒ 红 ✓（**这是它该有的作用** ✓ 保留）
2. ⚠️ **清单里有、代码里已没有**（"搬走文案"或"两个分支合并顺序不同"）⇒ **也红** ✗ ← **今天拦了我们三次 ✗**
⇒ 结果：**任何"搬文案 / 合分支 / 行数变化"都要手工重生成清单** ✗，每次都有人忘、每次 CI 红 ✓

## 二、改造目标（她批准的口径）
⭐ **只拦"新增"，不拦"存量"** —— 也就是说：
- 存量中文：**不管**（清单与代码不一致也**不许红** ✗）
- 新代码里冒出的硬编码中文：**照旧红** ✓
- ⭐ **不再需要"每次重生成清单"** ✓（这是"一次性解决"的关键 ✓）

## 三、方案（两步走，先 A 后 B）
### A｜立刻做（小改，先解燃眉之急）
1. `hardcodedChinese.js`：比较逻辑改成**只看"代码里有、清单里没有"**这一向 ✓
   ⇒ "清单里有、代码里没有" ⇒ **降级为一条 info 日志**（不红 ✗）
2. 保留"生成清单"的命令（供有意新增时用 ✓），但**不再要求**每个 PR 都同步它 ✓
3. AC：`搬走一句存量文案（清单不同步）⇒ 测试仍然绿` ✓ · `新增一句硬编码中文 ⇒ 测试红` ✓
   （**先红后绿**：后者必须先在改动前的代码上跑红 ✓）

### B｜接着做（真正的"不会再拦"）
4. **改成基于 diff 的扫描**：CI 里只扫 `git diff <base>...HEAD` 的**新增/修改行** ✓
   ⇒ **清单文件可以整个删掉** ✓（不再有"清单与代码不一致"这回事 ✓）
   ⇒ ⚠️ 前提：CI 能拿到 base（`origin/main` ✓ `fetch-depth: 0` ✓）
5. AC：`在"未改动的旧代码"里放一句中文 ⇒ 不红（存量豁免 ✓）` ·
   `在本次改动的新增行里放一句中文 ⇒ 红 ✓` · `删掉清单文件后全套仍绿 ✓`

## 四、红线（改造过程中不许放宽的）
- 🔴 **"新写的用户可见文案必须进配置"**这条目标**不变** ✗（只是判定方式变 ✓）
- 🔴 不许为了让 CI 绿而**关闭整个守门测试** ✗ · 不许加 `retry` / 全量豁免 ✗
- 🔴 既有 `AC-2`（新增中文必红）等断言的**语义**必须保住 ✓（换实现不换语义 ✓）
- ⚠️ 改造要**分批**：A 先合（解燃眉之急）⇒ B 再合（删清单）✓ 每批都全量 0 失败 ✓
