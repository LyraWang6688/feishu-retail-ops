# 到货核对：去掉「先说一句核对完毕」这道闸门（2026-10-07）

## 一、业务负责人的口径（逐字）

> 「那个现在的采购到货路径是说，用户需要收到"核对完毕"才会启动，是吗？
>  **这个链路是多余的。用户一般一句话就能够说清楚这个事情，
>  所以收到用户关于到货情况的反馈时，直接处理就可以。**」

**要改成的样子**：收到用户关于到货情况的反馈 → **直接处理**（解析 → 算核对计划 → 出核对卡片）。
**不再要求她说「核对完毕」这类完成信号。**

> ⚠️ 本文件与已合并的 `docs/arrival-trigger-and-prompt-2026-10-07.md` 是**同一件事的两半**：
> 那一份是她 2026-10-07 的**第二段口径**（「就以这个事件去触发 AI 识别，不用再等用户说
> "核对完毕"了」+ 她批准的两条**提示词**改动）；本文件是**这次实现**的验收标准与逐条对照。
> 那一份里写明"代码里的 `complete` 闸门 **+ 提示词里对应的那两条要求，一起改**" ——
> 所以本 PR **把提示词也改了**（见下面 A12）。

## 二、改之前的现状（代码事实）

`PurchaseArrivalConversationService.handleTopicMessageLocked` 里：

- 调 `recognizer.parseArrivalReconciliation(...)` 拿 `{ complete, same, differences }`；
- `if (!parsed.complete)` → 记 `purchase.arrival.reconcile.collecting`，**只记录、不回话、不发卡片**；
- 只有 `complete === true` 才继续 → `buildPlan` → 出「是/否」核对卡片。

⇒ 她说清了实际到货、但没说「核对完毕」时，链路**停在那里不动**。

## 四、⭐ 五个边界逐条怎么处理

### 1. 还照样要她**点确认**才入库吗？ —— **要。**（与业务负责人的理解一致）

她否掉的是「**必须先说一句完毕**」，**不是**「确认卡片」本身。卡片确认是既有流程，
也是**防写错账的唯一闸门**（点「是」才写「采购到货」+「采购入库」+ 库存）。
本次**没有动** `confirmLocked` / `rejectLocked` 的任何一行业务逻辑。

### 2. 解析对不上明细 → **保留 `unmatched` 回问路径**（原样）

这跟"说完没说完"是两件事。`plan.reason === 'difference_unmatched'` → 回 `replies.unmatched`；
负数 → 回 `replies.negative`。两者都不发卡片、不入库。

### 3. ⭐ 重复 / 追加反馈（**本次的关键**）

| 情形 | 处理 | 理由 |
| ---- | ---- | ---- |
| 已经有**一张等待确认的卡片**，她又补充/修正 | **重算 → `updateCard` 更新那一张**；更新成功后再回一句「我按你刚说的重算了一遍」（可配文案）。**不发第二张。** | 话题里两张都能点的卡片会让她不知道该点哪张；更新那一张 = 她眼前那张始终是最新的 |
| 卡片**更新失败**（权限/撤回/网络） | 记 `card_update_failed` + **补发一张新卡** | 旧卡上是**过期数字**，让她点它就是让她确认错的数量。补新卡是唯一能让她继续的出口 |
| **已经确认入库**（`status=posted`）→ 她再说话 | 走既有 `after_posted`：**零业务写入** + 「这一批已经入过库了，我没有再动任何表。要改请告诉我该改哪一条。」 | ⭐ **选"不自动重开、不自动改账"**：自动重开 = 自动反向写库存，是这里**最危险**的选项（她最在意的就是"写错账"）。明确告知 + 让她给指令，才是安全默认 |
| 同一条 `message_id` 重复投递 | 既有 `duplicate_message` 短路（在调模型之前） | 一句话不能被算两遍 |
| 她说「否」之后又补充 | 卡片还在 → 按上表第 1 行走「更新那一张」 | 「否」不是终态（代码注释里她没说过否完不能改主意），更新那张卡最省事 |

> ⚠️ **残留风险（如实记下）**：`after_posted` 那句「要改请告诉我该改哪一条」目前**还没有配套的"改"入口**——
> 真的说"要改"，现在不会自动发生任何事，得人工在库存上做调整（工作台盘点调整）。
> 本句文案保持**逐字不变**（它已表达"没有静默处理"），但这个缺口需要她拍板要不要做。

### 4. `complete` 这个字段怎么办

**不再作为"要不要处理"的闸门**。它现在的用途只有两个，都是**诊断/体验**，不参与业务判断：

1. 进 `last_parse.complete` 与日志字段 `parse_complete`（排查时能看出"模型当时判断她说完了没有"）；
2. **仅**在 A2 那个"什么可核对内容都没有"的角落里，决定**要不要回一句**教她怎么说
   （`complete===true` 才回；`complete===false` 保持静默，避免在群里刷屏）。

**判据不是关键词**，全部来自模型；代码里没有 `includes('完毕')` 这类匹配。

### 5. 文案（配置先行）

`server/src/config/arrivalConversation.js` 里改的：

| 键 | 改前 | 改后 |
| -- | ---- | ---- |
| `replies.notConfirmedYet` | 「我还没听你说**「核对完了」**，你补充完再说一声。」 | 「我这边还没算出这一批的核对结果，你再说一句实际到货，我重算一遍。」 |
| `replies.noArrivalContent`（**新增**） | — | 「这句里我没听出到货的变化。跟单子一样就说一句「都到了」；有多的少的，说一下货号、尺码和双数。」 |
| `replies.updatedCard`（**新增**） | — | 「我按你刚说的重算了一遍，上面那张卡片已经更新 —— 你看一眼，点「是」我就按新的数量入库。」 |

`unmatched` / `negative` / `rejected` / `alreadyPosted` / `afterPosted` / `card.*` / `summary.*` **一个字都没动**。
卡片标题（「本次到货核对完毕，确认入库吗？」）**保持不变** —— 那是**我们对她的结论**的陈述，
不是要求她说的一句口令（且它是既有用户可见文案，没有理由动）。

## 八、⚠️ 已知残留风险（如实记下，没有默默按"我的理解"处理）

1. **已入库之后的"改"没有自动入口** —— `afterPosted` 那句「要改请告诉我该改哪一条」
   目前**没有配套的自动实现**；真要改得走人工库存调整（工作台盘点调整）。
   本次**有意**只做"如实告知 + 零写入"，因为自动重开 = 自动反向写库存，是最危险的做法。
2. **她先说了到货、卡片出来后又说了一句"对不上明细"的话** → 会回 `unmatched`，
   而**旧卡片仍留在话题里**（数字是上一轮的）。点那张卡仍是按上一轮的计划入库 ——
   这个行为**改动前就存在**（不是本次引入），本次没有动它。要与不要收紧，请她拍板。
3. **`same === true` 的语义完全交给模型**（提示词规则 2 要求她说了「完全一样 / 都到了 / 一件不差」才填 true）。
   若模型把一句闲聊误判成 `same: true`，就会出一张"全部到货"的卡片 ——
   但**入库仍要她点「是」**，且卡片上写着具体数字，所以不会自动写错账。
   本 PR 已经按她批准的口径改过提示词；"提示词级断言"只能钉住**文字**，
   **模型真实行为没法在 CI 里验证** —— 要真验证得在测试 Base 上跑一次真模型。
