# 采购退货「归批 + 话题」验收标准（2026-10-06 业务负责人拍板）

> 状态：**目标行为，随本 PR 实现**（不是历史记录）。
> 规矩：**先写"按我们的链路应该实现的效果"，再实现，再自测，最后逐条对照**
> （AGENTS.md《与业务负责人的协作纪律》第 2 条）。
>
> 两个改动都是业务负责人 2026-10-06 当面拍板的：
> ① 采购退货**按「报货批次号」归批，窗口 30 秒**（她定的值）；② 发群改成
> **一条开话题 + 后面的回复它**。

## 背景（2026-10-06 生产实测，已核实）

她在生产提交了一次**采购退货表单**（2 条记录：货号 `2070-9` 6 双 / `66851` 7 双，
**同一个报货批次号 `202610061`**）。链路本身是通的（单据信息 / 库存流水 / 实时库存都对），
但暴露两个问题：

| # | 现象 | 根因（日志实证） |
|---|---|---|
| ① | 两条记录被当成两批 → **出了 2 张单、发了 2 次群** | 飞书**有时打包推、有时分条推**：本次 2 条**分两次推**（`action_count: 1` + `action_count: 1`，相隔 **16 秒**）；昨晚 3 条是**一次打包推**（`action_count: 6`）。项目现有「归批」窗口只有 **4 秒** → 16 秒兜不住 |
| ② | 群里变成 **4 条消息**（2 张图 + 2 条文字 @，各自形成 **4 个话题**） | 每条都发**顶层消息**；飞书里「话题 = 一条消息 + 它的回复」，顶层消息各成一个话题 |

## 输入（验收用的形状 = 今天实测那个形状）

一次表单提交 **2 条**采购退货记录，**同一个「报货批次号」**，**相隔 16 秒**到达
（飞书分条推）。每条：编号（货品）+ 数量（无尺码），行为 = 采购退货。

## 应该发生（验收标准 8 条）

| # | 验收标准 | 判据（自动化测试怎么判） |
|---|---|---|
| ① | ⭐ **只出 1 张「采购退货单」**（两个货号列在同一张表里） | 整批只渲染 **1** 张退货单图，且图上的明细**同时含两个货号** |
| ② | ⭐ **群里只有 1 张图 + 1 条文字 @**，且**挂在同一个话题下**（1 个话题、2 条消息） | 发到群的消息**恰好 2 条**：第 1 条是顶层图片（`im.message.create`），第 2 条是**对第 1 条的回复**（`im.message.reply` → `path.message_id` = 第 1 条的 message_id）；两条记下来的 `thread_id` **相同** |
| ③ | ⭐ **「库存流水」按实际数扣**，粒度不变：**一尺码一行**，行为 = 采购减少 | 每个尺码一行 `inventoryLedger`，`库存行为` = 采购退货（`STOCK_PURCHASE_DECREASE`），数量与实际退掉的双数一致 |
| ④ | ⭐ **「实时库存」按实际数扣到 0**（扣完的行消失） | 被退掉的 `liveInventory` 行**全部消失**；没有多扣、没有漏扣 |
| ⑤ | ⭐ **「单据信息」**：1 张单（含两个货号） | 这一次提交只出 **1 张退货单**（同 ①）；「单据信息」的写入粒度与现状一致（**一尺码一行**，幂等键 `purchase_return:<记录id>:<尺码>`），两个货号的单据都挂在同一批里。⚠️ 口径解释见文末「判断口径」 |
| ⑥ | ⚠️ **跨批不误合**：不同「报货批次号」的两条**不能合成一张单** | 两个不同批次号的记录（窗口内先后到达）→ **2** 张单、**2** 张图、各自扣各自的库存 |
| ⑦ | ⚠️ **超时不漏**：单独一条（窗口内没有同伴）→ **窗口到点后照常出单** | 单条记录：窗口到点前**一次远端写入都没有**（记录处理状态不变、没有单据、没有图），到点后照常出单、出图 |
| ⑧ | ⚠️ **幂等**：同一条记录**重复投递** → **不重复出单、不重复扣库存** | 同一批的两条 webhook 重投（含顺序颠倒）→ 批次、单据、流水、库存、图**一个都不多**；已到终态的记录被跳过 |

## 硬性边界（验收时一并检查）

- **不改「采购报货」那条链路的行为**：报货的归批窗口仍是 **4 秒**
  （`REPORT_BATCH_WINDOW_MS`），报货不走退货这套窗口。
- **不改 schema / 不加字段**。
- **配置先行**：退货窗口是独立配置文件 `server/src/config/purchaseReturnBatchWindow.js`，
  默认 **30000**，`PURCHASE_RETURN_BATCH_WINDOW_MS` 可覆盖；取值风格显式，不写 `|| fallback`。
- **持久化**：等窗口的退货任务落在 `JsonTaskStore`（`status: batch_waiting` +
  `batch_no` + `batch_kind: purchase-return`），**PM2 重启后自动重开窗口**继续处理。
- **幂等**：沿用现有的四道防线（任务终态 → 批次串行锁 → 记录终态 → 单据幂等键 +
  库存 operationId），不新增、不削弱。

## 判断口径（写下来免得日后扯皮）

1. **窗口起算点**：从这一批的**第一条**记录起算，固定 30 秒；后来的记录**并进同一批但不重置**
   计时。理由：飞书可能持续分条推，滑动窗口会让她永远等不到图。代价：第 31 秒才到的同伴
   会另起一批（她已知情并接受"最多等 30 秒"）。
2. **⑤ 的「1 张单」**：飞书里「单据信息」一行只能关联**一个**货品（关联字段），
   而库存流水/单据信息的既定粒度是**一尺码一行**（本 PR 不改粒度）。所以「1 张单」
   实现为：**一次提交 = 一张退货单（同一张图列出两个货号）**，单据信息行仍是
   一尺码一行、分属同一批。若业务上要的是"单据信息表只留一行"，需要改字段结构，
   超出本次口径（需她再拍板）。
3. **话题归属**：本 PR 的假设是「回复同一条消息 = 挂在同一个话题下」，据此
   后续消息一律 `im.message.reply` 到**第 1 条**（不是回复上一条）。
   ⚠️ 该假设**未在真机验证**（本 PR 不部署、不连线上），部署前建议先在测试群看一眼。
