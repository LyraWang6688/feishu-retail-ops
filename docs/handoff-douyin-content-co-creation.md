## 5. 她要的共创：三层能力

### 5.1 内容层 —— 不依赖任何平台授权，可以马上开始

| 交付物 | 说明 |
|---|---|
| 口播稿 | 30s / 60s，含开场钩子、痛点、产品、促单、节奏标注 |
| 标题 + 话题标签 | 结合她自己总结的「数字/规格驱动 + 时令性」规律 |
| 封面文案 / 封面图 | 她能接受脚本批量生成（中文渲染已验证可行）；「模特 + 商品合成」更适合她现有的图像工作流 |
| 分镜脚本 | 按秒拆解 |
| 选题库 | 30–50 条，素材来自她的初心 / 优势 / 劣势 / 顾客故事 |

> 一个**待验证的假设**（不是结论）：目标用户写的是「中老年人及其子女」，而抖音主力用户偏年轻 —— **买鞋的决策者往往是子女，穿鞋的是父母**。如果成立，钩子要同时打两代人（子女的孝心 + 父母的舒适）。请让她确认。

### 5.2 数据与经营层 —— 取决于数据在哪

| 数据位置 | 能做什么 | 前提 |
|---|---|---|
| 她自己的飞书 Base | 库存预警、补货建议、日报周报看板、销售可视化 | 字段定义与阈值 |
| 抖音后台（订单 / 库存 / 直播） | 写代码 / MCP 连接器对接 | ⚠️ **抖店 / 抖音开放平台的资质与授权**（需调研核实，见 5.3） |

> 💡 **值得优先核实的假设**：本仓库的 Base 里已经有「实时库存 / 销售明细 / 采购入库」等数据。
> 那么**库存预警与补货建议很可能可以基于现有表做只读聚合**，不必等抖店 API —— 请先核实数据是否足够，再谈是否需要平台接口。

### 5.3 平台层：必须写明的边界（和微信公众号完全不同）

- **抖音没有「个人可用的发布 API」**。微信公众号能做到「一条命令进草稿箱」，是因为微信开放了个人可用接口；抖音的发布通常要么手动，要么需要企业 / 开发者资质（抖店 / 开放平台）。**（具体能力与门槛尚未核实，属于待调研项）**
- **「自动补货」若直接改平台库存 = 写操作**，需要授权与风控。推荐路径：**先在她自己的 Base 里做「预警 + 建议」，人工确认后再动平台** —— 与仓库现有的幂等哲学一致（先落盘、再动外部、读回核验）。
- agent 看不到实体库存与真实成交，除非数据进到可访问的地方。
