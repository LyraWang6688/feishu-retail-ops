# 扫码销售口径（业务负责人 2026-10-09 定）

## 1. 可卖 = **样品 + 门盒**；仓库不算可卖
她说：「系统能够给出目前**样品加门盒**的尺码」。⇒ 判断"有没有货"只看**样品 + 门盒**；
「仓库」仍显示（作参考），但**不参与"现货/预订"判定**。

## 2. ⭐ 现货 / 预订 **由系统自动判定**（不用她选）
- 她原话：「如果选的是**库存里面的**，就是**现货**；如果选的是**非库存里面的**，就是**预订**」
- ⇒ 扫码销售建单时：**所选尺码在（样品+门盒）有货 ⇒ 交易类型 = 现货**（`SALE_CASH`）；
  **没货 ⇒ 交易类型 = 预订**（`SALE_PREPAID`）
- ⚠️ 这条**取代**之前"扫码单不写交易类型"的保留状态；**群聊链路一个字不动**（那里仍按它自己的判据）

## 3. 缺码要**按组**看
- 二维码里只有**编号**（`货号|颜色|类别`）—— **尺码扫不出来** ⇒ 尺码必须在页面上选
- 页面要给：**该款各尺码的（样品+门盒）库存** + **缺哪些码**，并按 **A 组（男 38–48）/ B 组（女 34–43）** 分组
- 已知事实：编号第 3 段就是**类别**（A=男、B=女）⇒ 该款属于哪一组，扫出来就定了；
  另一组要作为参考也列出（她 2026-10-09 提出后确认）

## 4. 「原话 / 解析状态」这类列**不适配扫码**
- 她原话：「**解析状态就是我们对于原话的解析**。当前这个状态下，现有的一些字段已经不太适配我们当前的决定了，
  也就是我们要用**扫码**」
- ⇒ 扫码单**没有"原话"、也没有 AI 解析** ⇒ `原话` / `解析状态` / `解析结果摘要` / `失败原因` / `消息链接`
  这些"为语音/文字录入而生"的列，在扫码时代**理应退场**
- ⚠️ **但现在不许删**（两条原因）：
  1. **群聊入口还没下线**（现为"冻结"）—— 那些列**群聊还在写**，删列会让群聊链路**当场报错**（"未配置语义字段"）；
  2. 飞书**删列 = 删数据、不可恢复** ⇒ 等群聊真下线后再统一清理。
- ⚠️ 核对事实：销售主表 19 列里**没有叫「验收」的列**（她 2026-10-09 提到的名字需再确认）。

## 5. 为什么必须扫码（她的理由，记下来）
> 「群聊…为了方便，我们之前都是让大家**语音录入**。但语音录入的问题在于**识别不准**，
>  而我们又要求**准确性**，所以还是需要**扫码录入**。扫码录入能确保**货物信息的准确性**。」
