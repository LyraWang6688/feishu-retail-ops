## 1. 判定「假绿」的清单（复核时逐条打勾）

### A. 「跳过却说通过」

- **A1** 缺凭证 / 缺表 ID / 缺前置数据 ⇒ 必须**明确打印"跳过 + 原因 + 影响哪条链路"**；静默跳过 = ❌。
  ⚠️ 但"打印了"还不够 —— 见 A2/A3。
- **A2** 跳过项必须进**报告产物**（`report.json` 里有 `skipped: [{id, reason}]`）。
  只在控制台滚过去的一句 ⚠️ ⇒ **不算**：报告是发版证据，控制台不是。
- **A3** 汇总行**不能只数"跑了的"**。反例：8 个场景里只跑了 2 个，最后打"场景：2 个，未达标 0 个 ✅"
  ⇒ 读的人会当成"全覆盖且全绿"。汇总必须打 **`跑 x / 跳过 y / 未达标 z`**，且分母是**全量**。
- **A4** "入口已经不存在了"（不可达 / 已退场）**不能算通过**，必须显式标 `stale` 或跳过 + 原因。

### B. 「断言没真的验到东西」

- **B1** 断言必须**验到关键字段值**（金额 / 状态值域 / 数量 / 关联 id / 流水方向）。
  只断言"有一条记录" ⇒ 指出。
- **B2** 断言必须**能证伪**：我会做一次**变异验证**——临时把某个期望值改错（或把产品代码某一步短路），
  确认脚本会**红**。红了才说明这条断言有效；仍绿 ⇒ 这条断言是摆设。
- **B3** 断言里的"实际值"必须是**本次运行产生的**（见 C 组），不是读来的存量。
- **B4** 脚本的**退出码**必须反映失败：`未达标 ⇒ exit ≠ 0`。
  ⚠️ 只用"看终端最后一行"判绿的自动化，遇到恒 0 的脚本会**假绿**。

### C. 「旧数据 / 缓存冒充本次真写」

- **C1** 断言用 **before → after 差值**（记录数 / 实时库存 / 库存流水条数），不是"存在某条记录"。
- **C2** 必须能证明"这条记录是本次 run 产生的"：本次 run id / 新批次号 / 新 message_id /
  本地任务文件 mtime。**报告里带 `ran_at`（含 +8）**。
- **C3** 每次运行必须换 key（消息 id / 幂等提交键 / 批次号）；复用上一次的 key ⇒ 命中幂等短路
  ⇒ 第二次跑"什么都没写"却报 ✅（典型假绿）。
- **C4** 本地任务目录必须**每次独立**（`fs.mkdtempSync`），不得复用上次 `status=posted` 的任务库。

### D. 「绕开项目代码」

- **D1** 业务写入必须经**项目入口**（service / route），不许自己拼 `bitable.record.*` / `im.*` 造结果。
- **D2** **回读验证**也必须走项目代码或项目网关的只读方法；**禁飞书 CLI**（含"用 CLI 读表验证结果"）。
- **D3** 新脚本必须落在 `e2eHygiene.test.js` 的静态扫描范围内（`server/scripts/**/*.{js,cjs,mjs}`）；
  否则闸门（禁硬编码凭证 / 禁 CLI）扫不到它。

### E. 「清理与幂等」

- **E1** 重复运行**可重复**：第二次跑必须要么真跑（新 key）、要么明确"跳过 + 原因"，
  **不许**第二次因为幂等而"跳过却报通过"。
- **E2** 运行之间**不得互相污染**：独立任务目录 / 独立会话 / 不复用上次的草稿。
- **E3** 测试 Base 的记录**可以留**（业务负责人明确批过，不用清理）；**生产表只读**，不许删/改。
- **E4** 幂等本身要有断言：同一提交键连点两次 ⇒ **只建一单、只扣一次库存**。

### F. 「安全闸门」

- **F1** 目标 token 逐字等于 `FEISHU_V1_E2E_TEST_APP_TOKEN` 且 `FEISHU_TARGET_ENV=test`，否则拒绝运行。
- **F2** **不得使用 `--force-env`**（我这一侧一票否决：它同时旁路 F1 的两道闸门，见 §5 F-4）。
- **F3** 飞书外发默认**拦住**（记录型 IM 替身）；**不许 `--real-im`**——
  本机 `.env` 里配了**真实** `PURCHASE_CHAT_ID` 与 `LARK_BOT_OPEN_ID`（见 §5 F-9）。
- **F4** 不许打印 token / secret / open_id 明文；只允许**指纹**（`前 4 位…(len=, sha8=)`）。
- **F5** 真 IM 消息、真实群、真实收款——**E2E 一次都不许发/收**。

## 2. 我的独立执行流程（每次发版前，9 步）

0. ⭐ **跑 `env-selfcheck`**（§0 0.0）：**退出码 0 才往下走**；有 `ID 过期` ⇒ 先改 ID，
   **不许**当成"表结构不对"下结论。
1. **对齐**：主工作区 `git fetch origin --prune && git pull --ff-only origin main`；
   记录 `git rev-parse --short HEAD` 与 `HEAD..origin/main`（必须 0）。
2. **锁定被测对象**：记下脚本的 commit / 分支 / 文件 sha256 —— 报告里的"版本"指**这个**。
3. **读源码复核**（≡ §1 的 A–F 逐条打勾）：**先读、后跑**；不做"照抄着跑"。
4. **自证**（§0 四行）→ 不成立就拒绝运行。
5. **只读体检**：脚本的 `inspect` / dry-run（不写任何表）。
6. **真写跑一遍**（测试 Base），保存完整 stdout/stderr + `report.json` 到本 worktree 的证据目录。
7. **变异验证**（B2）：至少 1 次"故意改错期望值 ⇒ 必须红"，把这次输出也留档。
8. **出报告**（§3 模板）＋ 附「只能人工测」清单（§4）＋ 跳过项与原因。

**证据留存**（我自己建，不写进 main）：`.local/e2e-verify/docs/reports/e2e-verify-<日期>/`
（stdout.txt / report.json / mutation-check.txt）。

## 4. 「只能人工测」清单（**每次报告都带上**）

> 这些**代码测不了 / 测了也不算数**，必须请业务负责人（或店里）亲眼过一遍。

1. **真打印机的那张纸**：实际出纸、选的哪台打印机、切纸/留白、二维码能否被手机扫出来、
   打印失败时屏幕上给没给提示（`labelPrint*` / `print-helper/` 那条线）。
2. **手感 / 易用性**：手机上扫码 → 选尺码 → 加入本单 → 提交，全流程**手指点得顺不顺**；
   字号够不够大、要不要滚动、会不会误点、页面是不是她说"太慢"的那种。
3. **飞书公式列延迟**：改完货号/颜色后「编号」「齐备」等**公式列**在表里**多久才刷新**
   （`e2e-product-tag-qr.js` 注释里实测 1~10 秒）——这条只能人工看表，代码只能"等"。
4. **飞书客户端里的真实打开**：网页工作台 / 扫码页在**飞书桌面端与手机端内**能不能打开
   （H5 可信域名、AppLink 格式）——浏览器里能开 ≠ 飞书里能开。
5. **权限**：非白名单账号打开扫码页/工作台**被拦住**的样子对不对（她说的是不是那句文案）。
6. **钱到没到**：收款/退款**真实到账**（微信/现金/团购券核销）——E2E 只验记录，验不了账户。
7. **群里的"人看着对不对"**：若还有群/话题消息，@ 的人对不对、会不会刷屏、卡片排版会不会乱。
8. **数据合理性**：脚本用的输入数据**合不合业务常理**（例：不会报 0 双、不会一双 2.5 双）；
   用真实数据时**客户姓名/电话要脱敏**。
