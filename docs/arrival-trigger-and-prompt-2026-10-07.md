# 到货核对的触发方式与提示词（业务负责人 2026-10-07 拍板）

> 她的原话（逐字，两段）：
> ①「那个现在的采购到货路径是说，用户需要收到"核对完毕"才会启动，是吗？
>   **这个链路是多余的。用户一般一句话就能够说清楚这个事情，
>   所以收到用户关于到货情况的反馈时，直接处理就可以。**」
> ②「**行，那如果这个能做到的话，就以这个事件去触发 AI 识别，不用再等用户说"核对完毕"了。
>   这个事件触发 AI 识别后，再把最终核对到的到货明细给到用户确认就可以了**」

## 触发方式（改后）

```
采购单发到群里 → 图 + 文字落在【同一个话题】→ 该话题 ↔ 批次 写入本地映射
        ↓
【那条话题里收到任何一条新消息】  ← 触发点（topic message 事件）
        ↓  （不需要 @ 机器人、不需要引用、不需要说"核对完毕"）
AI 识别她说的到货情况（差异 / "没到" 等）
        ↓
算出这批的【最终到货明细】→ 发成核对卡片给她确认
        ↓  她点「是」
按实际数量入库；实际 0 双的行不入库（见 arrival-zero-arrived-rule-2026-10-07.md）
```

- ⭐ **触发点 = 话题里的新消息**（`thread_id` 有值的群消息；现在代码已经能收到，
  2026-10-07 真机 14:57:26 有日志：`lark.event.received` → `lark.group.message.accepted`
  → `purchase.group.batch.located source=thread_id`）。
- 🔴 **去掉**：「必须她说一句表示"完了"的话（完毕 / 核对完了 / 就这些）才启动」这层前提
  （代码里的 `complete` 闸门 + 提示词里对应的那两条要求，**一起改**）。
- ⭐ **保留**：核对卡片 + 她点「是」才入库（防写错账的闸门）。

## 提示词要补/要改（业务负责人同日批准）

在她读完整段提示词后，她确认「这两点可以加上」：
1. ⭐ **补**：「她说某尺码『一双都没到 / 没到 / 没来 / 一双没来』→ 这一行按【实际 0 双】，
   也就是 `type="less"`、`quantity` = 该行申请数量」。
   ⚠️ 不补的后果：模型可能不输出这一行 → 该行**按申请数量入库**（明明没到却入库 = 写错账）。
2. ⭐ **保留**：「她说『都到了 / 一件不差』→ `same=true`」（提示词里已有）。
3. 🔴 **改**：把「她明确表示说完了才 `complete=true`；没说完了 → `complete=false`」改掉 ——
   不再要求"完毕"信号；改为**信息足以算清差异就处理**，
   同时**保留**"不确定就不要输出这一行"的保守原则（宁可让她再说一遍，也不要写错账）。

## 边界（照既有口径，未变）

- 真「对不上明细」（货号/尺码不在单据里）→ 回一句让她重说，**不入库、不猜**。
- 差异三类（一样/多/少）与「入库数量 = 实际数量」不变。
- 「单据信息」（`purchaseRequest`）表**一个字都不改**。
