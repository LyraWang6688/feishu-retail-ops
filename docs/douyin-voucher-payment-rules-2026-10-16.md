## 2. 三个数各用各的（一张券 = 两个金额口径）

| 数 | 是什么 | 落在哪 |
|---|---|---|
| **面值** | 券能抵多少钱 | 算**差额（未收款）**：差额 = 货品 − Σ面值 |
| **平台结算款** | 平台真给店里的钱（抽佣后） | 写**收款明细那一笔的金额** |
| **待平台结算** | 收款状态（钱还在平台上） | 写那一笔的**状态** |

她给的例子：**货品 300 ＋ 面值 100 的券 ⇒ 未收款 200** ✓（收款明细那一笔记的是平台结算款，
如 47.40 / 85.40，**不是面值** ✗）。

## 3. ⚠️ 落地时必须把这三个数"错开"（这一条口径里没写，是我们按既有代码推出来的）

> ⭐ **业务负责人 2026-10-16 晚亲口补的例子（逐字，最硬的依据）**：
> 「**300元里有一张面值100元代49.9的团购券，那么就是收款明细是记账47.7，
>   然后销售明细里是收了200+47.7=247.7**」

⇒ 从她这句**直接读出**的公式（不用猜 ✗）：

| 数 | 算式 | 她的例子 |
|---|---|---|
| **收款明细**那一笔 | =【**平台结算款**】 | **47.7** |
| **销售明细「实收金额」** | = (**成交额 − 面值**) ＋ **平台结算款** | (300 − 100) + 47.7 = **200 + 47.7 = 247.7** |
| **【未收款】差额** | = 按**面值**抵扣后 | **200** = 300 − 100 |
| 校验 | 未收款 = 实收 − 已收 = 247.7 − 47.7 | **200** ✓ 与她要的一致 ✓ |

⭐ 等价写法（本刀实现用的那个）：
　 `实收金额 = 成交额 − (面值 − 结算款)` ⇔ `(成交额 − 面值) + 结算款` —— **同一个数** ✓（300 − 52.3 = 247.7 ✓）

差额的算法**全仓只有一个**（不存在第二处）：

- `services/scanWriteService.js:1053`　`owedCents = itemsCents − paymentsCents`
  （`itemsCents` = Σ**销售明细.实收金额**；`paymentsCents` = Σ**收款行金额**）
- `services/salesOrderService.js:309`　`outstandingCents = totalCents − paidCents`（落那条【未收款】）

⇒ 而收款明细那一笔的金额**必须**是【平台结算款】（口径②），
　 若货品那一侧照她填（300）不动，差额就会被算成 **300 − 47.40 = 252.60** ✗（口径①要的是 **200**）。

⇒ **货品那一侧必须扣掉券的「面值 − 结算款」那一截（平台抽佣）**：
　 `销售明细.实收金额 = 成交额 − Σ(面值 − 结算款)`。
　 例：300 − (100 − 47.40) = **247.40** ⇒ 差额 = 247.40 − 47.40 = **200** ✓

⭐ **这个算式与群聊那条先例逐字同形**（`services/groupBuyVoucherPolicy.js:83`）：
　 `netCents = cashCents + settlementCents` ≡ `成交额 − 面值 + 结算款` ≡ `成交额 − (面值 − 结算款)`
　 ⇒ 「实收金额」在这里的含义 = **店里实际拿到的净额**（客户补的 + 平台结算的）——与群聊那条链路同一个口径 ✓

⚠️ **为什么不能"照她填 300"**（⭐ 她 2026-10-16 晚**亲口否掉了**这一版）：
　 读侧「还差多少钱」= `实收金额 − 已收 − 待平台结算`
　（`services/salesProgressService.js:78`，销售卡 / 待处理推送 / `addPayment` 的上限都用它）。
　 记 300 ⇒ 读侧算成 **252.60**，比真实的 200 **多 52.60** ⇒ 她可能**多收**客户的钱 ✗，
　 而且与表里那条【未收款 200】**自相矛盾** ✗。

⭐ **裁决留痕**：Lead 2026-10-16 裁定走**这一版**（甲）——**不许**解冻 `scanWriteService.js`（丙 ✗）、
　 **不许**让实收照她填（乙 ✗，就是上面那条"会多收"）；见本刀 PR 说明。
