# ADR-004：入口 · 状态 · 路由 · 出口 的分层（新增「扫码」入口的接入原则）

- **日期**：2026-10-08
- **状态**：提议（业务负责人当天批准方向；实现分两步走）
- **相关**：ADR-001（AI 只做解释、确定性代码执行）· ADR-002（机器人入口分诊与解耦）·《转型记录》"原则四：机器人入口按有没有副作用分三类"

## 背景（业务负责人 2026-10-08 的口径）

- 销售 / 采购 / 售后 / 库存 都要支持**新入口：扫码**（供应商二维码、一维条码、我们自己的二维码、**手机摄像头**；扫码枪暂不采购）；
- **现有入口（群聊 / 卡片 / 工作台）一律保留，做兜底与替代选项，不许删**；
- 她担心的事（逐字意）：**"新增入口"会不会把好不容易跑通的中间处理逻辑改坏**；
- 她给的分层（逐字）：「不同的模块，其**入口**以及入口之后确定的**状态**，然后由状态指向不同的**路由**。路由之后的输出就是**出口**……核心就是我们**中间的处理规则**。」

## 决策（四条原则）

1. **入口可变** —— 群聊 / 卡片 / 工作台 / 扫码 都是"入口适配器"，产出**同一种形状**的输入；
2. **状态不变** —— 入口**不许自己发明状态**；状态取值仍由各模块既有状态机决定；
3. **处理规则不变** —— 中间处理层（销售入账 / 收款 / 履约 / 售后 / 采购 / 库存）**一行不改**；
4. **出口按"来源"选** —— 同一状态因**入口不同**而出口不同：
   - 群聊来的 → 回那条话题 / patch 那张卡；
   - 扫码来的 → 扫码页响应（＋需要跟进时：飞书待办 / 群卡）。

## 现状（2026-10-08 代码事实，完整证据见 `docs/state-and-prompt-matrix-2026-10-08.md`）

- **状态枚举"三有、七无"**：只有 `PROGRESS_TASK_STATUS` / `CONFIRM_DEAL_TASK_STATUS` / `AFTER_SALES_TASK_STATUS` 有集中枚举；**销售草稿本身的 11 个状态是 `larkMvpService.js` 里的字符串字面量**，采购报单 / 到货核对 / 库存操作 / 9 点推送 / 补样品同样散落；
- **"有状态、没提示"真实存在**：`received`/`parsing` 期间只有表情没有文字；售后 `RUNNING` 零回话；到货 `posting` 无"正在入库"反馈；库存操作 3 个状态**完全没有面向用户的提示**；
- **入口三套各自为政**：群聊在 `larkMvpService.acceptMessage`、卡片回调在 `handleCardAction`（**顺序敏感的一串 `if`**）、工作台是纯 HTTP（无群上下文）、表事件在 `routes/larkEvents.js`；
- **出口只有"群话题"一种**，判据只有 `task.chat_type === 'group'`；采购单只发 `PURCHASE_CHAT_ID`、9 点推送只发 `PENDING_DEAL_PUSH_CHAT_ID` ⇒ **"按来源选出口"今天不存在**；
- **卡片动作路由的同步响应全局固定**为「已收到，正在处理」（`routes/larkEvents.js`）⇒ **只做 toast、不做 patch 的失败路径 = 用户什么都看不到**。

## 落地（两步走，风险最低）

| 步骤 | 做什么 | 好处 |
| --- | --- | --- |
| **第一步（快，先上线）** | 扫码模块**自己产出与"群聊解析"同形的草稿**，**直接调现有 service**（不重构） | 几天能跑；**不动任何现有链路**（群聊继续可用） |
| **第二步（渐进收口）** | 新增 **入口适配层** ＋ **状态路由表**（配置驱动）＋ **出口适配层**，把群聊 / 扫码 / 工作台统一进来 | 以后**加一个入口或出口只改一层**；从根上避免"第二条链路" |

## 约束：不得被碰的中间处理逻辑

见 `docs/flow-status-audit-2026-10-08.md` 第八节清单 —— `afterSalesService` / `afterSalesFlowService` / `inventoryService`（含 `STOCK_MOVEMENTS` 注册表）/
`salesOrderService` / `salesProgressService` / `salesDeliveryService` / `secondDeliveryService` /
`purchaseWebhookService`（退货那 17 个方法）/ `groupBuyVoucherPolicy` / `idempotencyKey.createOnceByKey` 等。
**入口层与出口层的改动只能在外层做**，且每次改动都要给出"这些文件零 diff"的证据。
