# ADR-003：AI 的定位是「不确定性收口器」；未来宿主只能接管无副作用的域

- **状态**：已接受（2026-10-05）。决策一、决策二描述**当前架构**；**决策三标注为「未来方向 · 当前不实施」**——本 ADR 只固定它的边界，不落地任何实现。
- **相关**：[ADR-001](ADR-001-separate-ai-interpretation-from-deterministic-business-execution.md)（AI 负责理解与结构化，确定性后端负责正式业务执行）、[ADR-002](ADR-002-robot-entry-triage-and-decoupling.md)（入口按副作用三分、入口与执行解耦、不做自主智能体）—— 本 ADR 把这两条边界从「系统之内」延伸到「系统之外」。

> **本 ADR 不做的事**：不改任何代码、不新增部署形态、不引入 MCP / Skill 的任何实现。决策三是**写给未来的约束**，不是待办事项。

## 背景

ADR-001 已经定下「AI 理解、代码执行」；ADR-002 已经把入口按副作用分成录入 / 查询 / 回答三类，并把 AI 的职责上限写成「意图枚举 + 参数」。但还有两个问题没有被正面回答：

1. **AI 在这套系统里到底是什么角色？** 「AI 不写表」只说了它**不做**什么，没说它**做**什么。边界只以否定句存在时，新需求很容易被顺手塞给模型。
2. **如果将来把它挂到别人的 AI 宿主上（豆包工作一类），哪些能力可以交出去、哪些绝对不行？** 这个问题不回答，一旦真有宿主可接，就会临时拍脑袋决定——而拍错的地方恰好是账。

本 ADR 回答这两个问题。答案本身不改变今天任何一行代码。

## 决策

### 决策一：AI 在本项目中的角色是「不确定性收口器」

AI 承担的是**三种翻译**：

| 翻译 | 输入（不确定） | 输出（确定） |
| --- | --- | --- |
| ① 文字 → 结构化字段 | 店员怎么说都行的一句话 | 货号 / 颜色 / 尺码 / 数量 / 金额 / 支付方式等字段 |
| ② 图片 → 结构化明细 | 鞋盒照片、供应商到货单照片 | 一行行明细（款号 / 颜色 / 尺码 / 数量 / 单价） |
| ③ 对话 → 意图分类 | 同一句自然语言 | 有限枚举（`sale` / `sale_query` / `return` / `exchange` / `account_query` / `qa` / `unsupported`） |

三者的共同点只有一条：**输入是不确定的（人的表达，怎么说都行），输出是确定的（有限枚举 / 字段）**。

「收口」指的就是这件事：把不确定的东西收敛到一个**有限、可枚举、可校验**的形态，然后**交回确定性代码**。收口之后，写哪张表、按什么顺序写、要不要写，全部不由 AI 决定。

**AI 不承担决策**：

- 不决定写哪张表；
- 不由它判断「要不要写入」；
- 不由它判断任务是否完成。

结论：本项目做的是「**自然语言前端 + 确定性后端**」，**不是智能体**。这与 ADR-001（AI 不拥有最终业务事实）和 ADR-002（AI 职责上限是「意图枚举 + 参数」）一脉相承——本 ADR 的增量是把这个上限总结成一个可复述的**定位**：AI 是**不确定性收口器**。有了这个名字，才能一句话判断一个新需求该不该给模型做：**它是在收口，还是在做决策？**

### 决策二：与通用型自主智能体的区别，以及为什么不做后者

| 维度 | 通用型自主智能体（豆包工作 / WorkBuddy 一类） | 本项目 |
| --- | --- | --- |
| 谁决定下一步 | **AI 自己**：自己拆步骤、自己选工具、自己判断完成 | **规则与人**：意图枚举决定走哪条链路，人点确认决定是否写账 |
| 出错的代价 | 重新说一遍即可，大不了重来 | **一笔错账**：库存、资金、应收应付都要人工冲正 |
| 因此能容忍 | 灵活，偶尔错 | 死板，但不能错 |
| 价值落点 | **广度**：什么都能干一点 | **正确性 + 可审计**：这几件事绝对不错 |

原则：**宁可不懂，不可猜。** 认不出的意图收敛成 `unsupported` 并回一句「当前只支持商品销售录单」，**绝不猜成 `sale` 去写单** `[Repo]`。

**明确不做**：自主智能体（AI 自行规划 / 自行选工具 / 自行判断完成）。理由只有一条，但足够：账目要求行为**可复现、可审计**——同一句话两次执行应当走同一条路，出错要能定位到是哪一步。自主智能体的执行路径不可复现，与账目场景不兼容。

> **与 ADR-002 的分工**：ADR-002 已经记录过「不做自主智能体」这个结论及其理由，本 ADR **不重复论证**；这里只补两件它没写的——**对比的判据**（谁决定下一步、错了的代价）和**价值落点**（广度 vs 正确性），用来说明「不做」不是能力不足，而是**风险偏好不同**。

### 决策三：把这套系统包成 Skill + MCP 挂到成熟 AI 宿主上（**未来方向 · 当前不实施**）

> 本节记录的是**约束**，不是进度。当前不实施、不排期、不动代码。

**设想**：系统稳定后，把能力包成 **MCP 工具**（每个意图一个 tool）+ **Skill**（教宿主何时调用），挂到「豆包工作」这类成熟宿主上。由宿主负责语义识别与对话编排，真正干活的是我们 MCP 后面**确定性的脚本**。

**为什么代价低**：

- **契约同构。** MCP 的工具契约 = 「工具名 + 参数」；本项目入口的契约 = 「意图枚举 + 参数」。**一个意图就是一个 tool，参数就是已经收敛好的字段**——不需要设计新契约，只需要把现有枚举映射出去。
- **业务逻辑无需改写。** 注入点只有一个：意图从「我们自己模型的输出」换成「宿主传来的 tool call」，后面全部不变。
- **Skill 层本质是提示词搬家。** ADR-002 里「提示词与注册表两处保持一致」的那份提示词，换成宿主的 Skill 描述即可。
- **兑现 ADR-001 的「AI 能力可替换」。** 连模型带宿主一起换，核心业务规则不随之外漂。

**接管的边界（本 ADR 的核心结论）**：宿主**只能接管 ADR-002 中「无副作用」的两个域**——**数据查询**与**信息回答**；**有副作用的域（信息录入）原地不动**，仍然只走我们自己的机器人流程与确认卡片。

**依据**：ADR-002 的入口三分法**本来就是按副作用划分的**。因此这条边界是**架构自带的**，不需要为了接宿主新增任何机制——把三分法里「副作用 = 有」的那一格圈起来不外放，就是全部。

**必须同时满足的约束（否则不接）**：

1. **MCP 层不提供「直接写入」的工具**——只提供「提交待确认」；确认一律回到我们自己的卡片，由业务负责人点击确认。这样「**不确认不写账**」在架构上无法被绕过：宿主的语义理解再准，也只能把草稿送到确认卡片前面。
2. **幂等键必须作为参数传入**（不依赖宿主会话状态）。宿主会重试工具调用；幂等键放进参数里，重试才会命中同一条记录，而不是写第二遍。
3. **每个工具自己校验参数**：把宿主当**不可信的外部调用者**——它可能传错、传漏、传重复。不信任调用方，与本项目在正式入账上已有的做法一致（业务层重新校验，不采信上游结论）`[Repo]`。
4. **审计日志带来源**：能区分「本人说的」与「宿主调的」。两者出错时的责任归属不同，日志里必须可分辨。
5. **配置先行**：换宿主不改业务配置。宿主是可替换的前端，不是业务规则的载体。

这五条是**接入前置条件**：任一条不满足就不接。写在这里，是为了将来真要接的时候不必重新论证一遍。

## 附带记录：业务负责人的三条底层逻辑

本项目的第一性要求由业务负责人给出 `[Owner]`：

1. **配置先行**——行为差异尽量落到配置，而不是散在代码分支里。
2. **做到解耦**——入口、意图、域、执行层各管一段，互相不越界。
3. **做到可迭代、可拓展**——新增一类诉求尽量是「加一格」，不是「改一片」。

这三条不是审美偏好。它们的具体作用是**把「上生产」的代价压低** `[Owner]`：配置改得动、边界分得清、扩展不用推翻旧结构，意味着每次变更的**验证范围**和**回滚成本**都更小。

因此在**「改错成本高」**的场景（公司 / 需要担责的业务：账目、库存、资金）里，这三条**比在个人项目里更值钱**——个人项目改错了重来一次，账改错了要走冲正和解释。

本 ADR 的决策三正是这三条的一次兑现：**宿主可以换、入口可以加，业务配置和业务规则不动。**

## 后果

### 正面

- **未来接宿主时，只需要「搬走两个无副作用的域」。** 查询域与回答域本来就不写账，交出去不需要给它们补任何安全机制——ADR-002 的三分法已经把这件事做完了。
- **红线在架构上自动成立，而不依赖约定。** 「不确认不写账」由「MCP 层没有写入工具」保证，不是靠文档提醒，也不是靠评审盯人。
- **系统价值不依赖模型选型。** 换模型、换宿主、甚至把语义识别整体外包，都不触及入账规则（ADR-001 已立此原则，此处是它在宿主层的复用）。
- **对外可复述。** 「我们做的是不确定性收口，不是智能体」是一句话能讲清的定位，能减少被「你们怎么不做得更智能一点」反复拉扯的成本。

### 代价 / 负面

- **接受「不如通用智能体灵活」。** 用户不能对系统说一件没被枚举过的事并期待它自己想办法；多轮跳步、临时组合工具都做不了。
- **意图能力受限于有限枚举。** 每加一类诉求都要显式加枚举、加域、加测试；枚举之外的表达一律 `unsupported`。这是刻意的取舍，但确实是能力的硬上限。
- **需要维护提示词与注册表两份一致性。** 这个代价 ADR-002 已记录，本 ADR 不重复论证，只确认一点：它**不会**因为「以后接宿主」而消失——宿主把提示词搬走了，一致性要求也跟着搬走。
- **决策三在落地前不产生任何收益。** 它是约束，不是进度；在真正接宿主之前，这一节的唯一作用是防止将来接错。

## 不确定处

1. **决策三没有实现，也没有排期。** 本 ADR 只固定边界；「同构」「提示词搬家」是对契约形状的判断 `[Owner]`，**不是已跑通的结论**，因此无法证明「将来一定能接」或「接入代价真的低」。
2. **「宿主只能接管无副作用域」是设计判断，不是实测结论。** 它的依据是 ADR-002 的入口三分法，而该三分法本身仍在逐域抽出过程中（`larkMvpService` 里「入口 / 意图 / 销售链路」仍混在一起），所以这条边界的彻底性受制于抽出进度。
3. **交叉引用依赖尚未合入的分支。** 本 ADR 引用的 ADR-002 与 `saleLookupService` 都还没有进入 `main`。若 ADR-002 先合入，需要一次 rebase 确认索引顺序与相对链接仍然成立。
4. **「宁可不懂，不可猜」有明确例外，本 ADR 不假装它不存在。** 意图判定严格遵守该原则；但**交易类型不在此列**——说不清时按「现货」处理，代码注释写明这是**业务前提而非猜测** `[Repo]`（`server/src/services/doubaoService.js:140-144`）。
