# ADR-002：机器人入口按「录入 / 查询 / 回答」三分，入口与执行解耦

- **状态**：已接受（2026-10-05）
- **相关**：[ADR-001](ADR-001-separate-ai-interpretation-from-deterministic-business-execution.md)（AI 负责理解与结构化，确定性后端负责正式业务执行）—— 本决策是它在「入口层」的延伸。

## 背景

机器人入口从「只录销售单」扩展到多类诉求：销售录单、查销售记录、退换货录单；规划中还有账目查询（我欠供应商多少 / 客户欠我多少）与业务规范问答。

如果不加区分地把这些塞进同一条流程，会立刻出现三个问题：

1. **只读诉求被迫走重量级流程**——只是查一笔交易，却要经过「解析 → 生成草稿 → 等确认」，既慢又给用户多余的确认负担。
2. **意图与执行耦合**——意图判断写在某条业务链路里，新增一类诉求就要改动入口和既有链路，越加越乱。
3. **无法回答「这类诉求要不要人确认」**——因为系统本身没有区分「有副作用」和「无副作用」。

## 决策

### 1. 入口按「有没有副作用」三分

| 类别 | 副作用 | 流程骨架 |
| --- | --- | --- |
| **信息录入**（销售 / 退换货 / 赔货） | **有**（写账） | AI 解析 → **人确认** → 确定性写入 |
| **数据查询**（销售记录 / 账目应收应付） | **无**（只读） | AI 解析条件 → 查询 → 展示 |
| **信息回答**（业务规范 / 流程咨询） | **无**（只读知识） | 检索 → 生成 |

**判据是副作用，不是话题。** 「查一笔销售」和「退一笔销售」说的是同一件事的两个面，但一个有副作用、一个没有，因此必须走不同的骨架。

### 2. 意图层与路由层从业务链路中抽出

- **意图层**：只把自然语言收敛为**有限枚举**（`sale` / `sale_query` / `return` / `exchange` / `account_query` / `qa` / `unsupported`），契约只在一处定义。
- **路由层**：**纯分派**，不含 AI。
- **域层**：录入域、查询域、回答域各自独立、各自可测。
- **执行层**：状态机、幂等、写表——**只有录入域有执行层**。

**验收标准**：新增一个域时，入口层与路由层**不需要改动**。

### 3. 状态以表为准

飞书多维表格是**唯一真相**；本地任务状态（`data/lark_mvp_tasks/`）只是**缓存**。

任何多轮状态都必须能**从表恢复**（重启、将来多实例都不丢）。反例：把「用户正在退哪一笔」只存在内存里。

### 4. AI 的职责上限

AI 只做一件事：把自然语言收敛为「**意图枚举 + 参数**」。

**不得**决定：写哪张表、按什么顺序、是否写入、要不要确认。

## 明确不做的：自主智能体

**不做**「AI 自行规划、自行选择工具、自行判断任务完成」的自主智能体。

理由：本项目承载**账目**。自主智能体的行为**不可复现、不可审计**——同一句话两次执行可能走不同路径，出错了无法定位。我们选择的是**受约束的意图路由**：把 AI 关进一个可测的盒子里，让确定性代码负责所有写入。

**这不是「更弱的智能体」，而是「对账目系统正确的架构」。** 它没有通用的规划/工具编排能力，因此也**不是**豆包 / DeepSeek / WorkBuddy 那类通用型智能体；它替代的是**交互方式**（原来人手动填表单，现在人说一句自然语言）。

## 后果

**正面**

- 新增一类诉求 = 意图层加一个枚举 + 新增一个域；入口与既有链路不动。
- 每个意图可**单测**；日志能看出走了哪条路；出错**可复现**。
- 「**不确认不写账**」在架构上可证明：写入只可能发生在录入域，且必须有人确认。
- 查询 / 回答域天然**无副作用**，可以放心让模型发挥。

**代价 / 负面**

- 多轮对话需要**显式**状态管理（上下文、有效期、从表恢复），比"跑一次就走"复杂。
- 意图边界要在**提示词**与**注册表**两处保持一致，是双份维护成本。
- 现状 `larkMvpService` 里「入口 / 意图 / 销售链路」仍混在一起，需要**逐域抽出**——按项目纪律**不一次性重构**，而是在每次新增域时顺势抽出。

## 证据

- 退换货第一期把「查询」抽成独立只读 service（`saleLookupService`：无 `create/update/delete`，测试断言零写入），查询与录入从此分属两个域。
- 到货链路的**告警从表重建**（`bootstrapReportAlerts` 以表里的报单时间为准）体现「状态以表为准」。
- 各链路「AI 解析 → 卡片 → 人确认 → 确定性写入」的一致骨架，是 ADR-001 在四条链路（销售 / 报货 / 到货 / 退换货）上的落地。
