## 一、现场（业务负责人 2026-10-07 16:30 真机，逐字）

> 「26002-52 37 码，定金微信交了 100 元，下次欠 128 元」

解析结果（**完全正确**）：

```
payments     = [{ amount: 100, method: "微信" }]
agreed_total = 228      （= 100 + 128）
owed         = 128
trade_type   = "预付"
```

但缺项判定同时报了两条 ⇒ 她收到的是「要你补充」，**没有确认卡片**，一单卡住：

```
missing_fields = [
  "请明确已经收到的定金金额",                            ← BUG#1：她已经说了、也解析出来了
  "库存里没有 26002-52 37码（这个货号现在一双都没有）"    ← BUG#2：预付本来就没货（要调货）
]
```

她的口径（逐字）：

> 「**为什么我们会判定为预付？预付的原因是因为库存里没有，所以需要调货。
>  既然已经判断为预付，系统实际上就不应该再去库存里面找了。**
>  对，因为库存里面确实是没有的。…**其实成交额就是 228 元。因为定金是 100 元（是这次收的），
>  下次是 128 元。为什么这个逻辑我依然理解不了呢？**」
>
> 「**因为它实际上还是要写销售明细的，所以这个时候需要提供颜色信息，
>  也就是要以这个货号去找它的颜色，然后只不过是它就不需要再去实时库存里面查有没有这个库存了。**」

## 二、BUG#1 的确切位置与根因

### 位置：**后端**，不是模型提示词

`server/src/services/doubaoService.js` 的 `normalizeSalesResult` → **`depositTerms()`**。

两处证据：

1. **提示词里根本没有 `missing_fields` 这个字段。** 销售提示词（同文件 `parseSalesText` 的
   prompt，规则 1–13）从没让模型输出它；模型输出里就算带了，也会被**整个覆盖**：
   ```js
   normalized.missing_fields = [...missing];   // normalizeSalesResult 末尾
   ```
   `missing` 集合的来源是 `voucherPolicy.issues` / `deposit.issues` / 必填字段检查 —— 全是后端算的。
2. 那句逐字的文案就在后端：
   ```js
   if (depositAmount == null) return { issues: ['请明确已经收到的定金金额'] };
   ```

### 旧正则为什么认不出她的话

```js
// 改动前
const deposit = source.match(/定金\s*[¥￥]?\s*(\d+(?:\.\d{1,2})?)\s*(?:元|块)?|[¥￥]?\s*(\d+(?:\.\d{1,2})?)\s*(?:元|块)\s*定金/);
```

两个分支分别要求：

- 「定金」**紧贴**数字（`定金100`）—— 她写的是「定金**微信交了**100元」，中间夹了收款方式 + 动词；
- 或「100元」**紧贴**「定金」（`100元定金`）—— 也不成立。

⇒ 两个分支都匹配不上 ⇒ `deposit` 为 null ⇒ 无条件报「请明确已经收到的定金金额」。
**这是"无中生有"，不是保守**：她已经说了，`payments` 里也已经有 100。

### 怎么改（后端判定）

以「定金」为锚点，先看**它后面那一小句**、再看**它前面那一小句**：

```js
const DEPOSIT_CLAUSE_BOUNDARY = /[，,。；;、！!？?\n]|尾款|余款|下次|欠|剩余|剩下的|还差|再付/;
const DEPOSIT_MONEY  = /[¥￥]\s*\d+(?:\.\d{1,2})?|\d+(?:\.\d{1,2})?\s*(?:元|块)/g;  // 「像钱」
const DEPOSIT_NUMBER = /(\d+(?:\.\d{1,2})?)(?!\d)(?!\s*[码号])/g;                   // 任意数，但不许跟「码」「号」
```

- 后面：先认「像钱」的数（`100元` / `¥100`），认不出再退回"离定金最近且不跟码/号的那个数"
  （`定金100微信` 这种把「元」省掉的写法）。
- 前面：**只认「像钱」的数**，并从后往前取。
  这一条是**必须**的：写「`26002-52 37码 定金微信交的`」时，前面那串 `26002 / 52 / 37`
  一个都不是钱；放宽就会把货号里的 `52` 当定金，于是**明明没说金额却"认"出一个来**。
  （这条边界是写测试时才暴露出来的，已单独钉了一条用例。）
- 找不到就返回 null ⇒ **仍然**报「请明确已经收到的定金金额」，**这一条没放宽**。

同时把**余额**的说法补全（她的原话是「**下次欠 128 元**」，不带「尾款」二字）：
老写法「尾款以后付 140」一个字没动；新增两条**只在「定金」之后**找的余额说法
（`下次/以后/之后…欠/付/差 X`、`还欠/还差/还需要再付 X`）。
**只在定金之后**是关键：写「上次还欠 200 元，这次定金微信交了 100 元」时，
不能把上一句的 200 当成本单尾款（已钉用例）。

> ⚠️ **提示词不用改**：模型本来就不输出 `missing_fields`，而「定金 100 + 下次欠 128 ⇒ 228」
> 与提示词规则 9 / 9.1 是自洽的（见第四节）。

## 四、「成交额 228 怎么来的」—— 判断与依据

**结论：228 是既有口径允许的算法，依据是"她**同时**说了两件事"（收了多少 + 还欠多少）。**

- 既有口径（提示词规则 9 / 9.1，`doubaoService.js` 注释与代码）：
  · 只有定金、**没说欠** ⇒ 定金**不能**当成交金额（测试里钉着：`agreed_total === ''`）；
  · 她**明说还欠 X** ⇒ 成交金额 = 实收 + 欠款。
- 本例她说了「定金微信交了 100」（实收）+「下次欠 128」（明说欠）
  ⇒ `agreed_total = 100 + 128 = 228`，`owed = 128`。
  这与 `normalizeSalesResult` 里那条 `named = covered + owed` 是同一个算法，
  也是模型这次给出的值 —— **两边一致**。
- ⚠️ 与 `AGENTS.md` 第 16 条不冲突：那条禁的是"仅有定金就当成交金额"，
  而这里成交金额不是从定金单独得出的。
- 我**额外**钉了一条用例：即使模型漏给 `agreed_total` / `owed`，
  后端也能从「定金 100 + 下次欠 128」自己推出 228 / 128（确定性兜底）。

## 六、新增 / 更新的测试钉住了什么

**新增（`server/test/salesTradeTypePolicy.test.js`，5 条）**
配置覆盖且**只**覆盖三个交易类型编码（漏一个就是静默失效）· 预付不跑 B、现货/未付都跑 B、
三者都跑 A · 空/未知编码一律按"该跑的都跑" · 「中文标签 → 编码 → 策略」串起来仍是配置说了算 ·
交付规则不受本配置影响（预付仍「未交付」）。

**新增（`server/test/larkMvpService.test.js`，7 条）**
① 真机原话（预付 + 完全没库存）→ 无缺项 + 出卡片 + 三个值对 + 颜色来自 A + `delivery_status=未交付`；
② 没说定金金额 → 仍要求补充（且 `stockLookups===0`，两个修复互不掩盖）；
③ 预付 → **B 一次都没跑**（`stockLookups===0`），颜色由 A 给（故意让实时库存里那条是「白」的，
   断言拿到的是货品信息里的「黑」——证明走的确实是 A）；
④ 预付 + 货品信息里多个颜色 → `needs_color` + 候选（销售明细要写全）；
⑤ 现货 → A/B **两个都跑**（`stockLookups===1`），且 **B 赢**（拿到实时库存那条记录）；
⑥ 现货 + 没库存 → 仍被拦（文案逐字）；
⑦ 未付 + 没库存 → 仍被拦。

**更新（`server/test/doubaoSalesParser.test.js`）**
- 原来标 `[当前行为·待修复]` 的特征化用例（「100元微信定金」被判"没说定金金额"）——
  该提交自己写明「特征化用例断言的是今天的（不合理）结果，修复后它们会失败，
  **届时按新行为更新**」⇒ 按新行为改写：`agreed_total=240`、`missing_fields=[]`、`owed=140`。
- 「绝不把已收的那笔当成交金额」那条守卫：前提（正则认不出）已消失，但**它守的东西没变**
  ⇒ 保留并**加强**为 `assert.notEqual(agreed_total, 100)` + 240 / `total_paid=100` / `owed=140`。
- 新增：真机语序 → 无缺项；后端自己推出 228（模型漏给也算得对）；没说金额仍报；不许从货号/鞋码猜。

## 八、不确定 / 需要你拍板的地方

1. **⚠️ 实时库存的"整表预取"没有解除（只解除了 B 的判定）。**
   `loadLiveInventoryIndex()` 在**等到 AI 结果之前**就与 AI 并行发起（既有架构：把读表时间
   藏在 AI 后面）。所以预付单虽然**不判定、不查询**库存，那张表还是被读了一次（结果不用）。
   真要"连读都不读"，得把预取挪到解析之后 —— 那会改变现货单的耗时结构，
   **属于架构改动，本次没动**。要不要做，等你定。
2. **类别（A 的第三个输出）没有被消费。** 设计里 A 输出「颜色 / 类别 / 商品记录 id」，
   但销售明细的写入只用「商品关联 + 尺码」（`salesOrderDetails` 的字段里没有"类别"），
   `product_number` 也只拼「货号+颜色」。所以我没有把类别存进草稿 ——
   **如果它要落库/上卡片，请说一声，那是一处新增写入**。
3. **A 会给现货 / 未付多一次「货品信息」整表读。** 设计说 A 所有交易类型都跑；
   对现货/未付 来说 B 本来就会给出颜色与货品记录，所以这次 A 的读**结果用不上**（只是并行发起了）。
   我按设计实现（A 恒跑），代价是每件多一次 `listAll('product')`。
   若你想省掉，最干净的做法是"A 只在 B 不跑时读"，但那与设计文档的表格不一致 —— 你定。
4. **未付要不要也放过库存？** 我按你定的默认：**未付仍然查**（鞋已经被拿走了，必须确实有这双鞋）。
   读代码也没发现"未付不该查"的依据 —— 原话只说预付。
5. **定金余额的正则口径**（本次为让「下次欠 128」也能确定性推出而新增的两条分支）
   属于我**主动扩大**的一点点范围：严格按 brief 只需要修"定金金额"那一支。
   扩大的理由：① 她的原话就是「下次欠 128」，不带「尾款」；② 仓库里那条特征化用例
   自己写明修复后应是 240/无缺项。如果你认为这属于越界，**单独回退这两条分支即可**
   （`depositTerms` 里 `tail` 的第 2、3 个分支），其余改动不受影响。
