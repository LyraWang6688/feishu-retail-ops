# 项目进展与迭代路线

> 最后更新：2026-09-24  
> 文档性质：持续更新的项目状态记录。用于区分“已经实现”“当前决策”和“未来方向”，避免讨论中的设想被误认为已上线功能。

## 1. 产品定位

通用产品名：**零售数智经营助手**。  
邯美部署名称：**邯美数智经营工作台**。

项目面向线下零售和小型企业，以飞书作为统一入口：

- 飞书机器人负责自然语言和图片交互；
- 飞书多维表格负责配置、业务记录、流水和实时结果；
- 后端负责解析、校验、确认、可靠入账和跨表联动；
- 网页工作台后续负责配置、查询和分析，并复用同一套后端业务规则。

## 2. 当前架构共识

```text
机器人 / 网页工作台 = 用户入口
后端代码             = 解析、校验和可靠入账引擎
飞书多维表格         = 数据底座
飞书工作流           = 审批、提醒和通知编排
```

涉及库存和资金的正式入账必须由后端统一执行。飞书工作流可以负责提醒、审批和状态通知，但不独立复制扣库存、加库存或记资金流水的核心规则。

## 3. 当前 V1 的真实状态

### 3.1 已形成的能力

- 飞书私聊机器人是 V1 主入口，群聊字段和群聊流程不再作为当前设计前提。
- 销售文字可解析为销售草稿，并通过卡片确认后联动销售明细、库存流水、实时库存和资金流水。
- 采购到货图片可按私聊用户归集，确认后联动采购入库、库存流水、实时库存和供应商往来款。
- 入账过程支持按阶段恢复和重复提交保护，避免失败重试时重复扣减库存或重复记账。
- 微信小程序链路已冻结，可通过 `ENABLE_LEGACY_WECHAT=false` 停用；当前暂不删除。
- 新飞书应用、新租户和新多维表格使用独立配置，不回退到旧租户凭证。

### 3.2 尚未完成的部分

- 当前代码明确支持的是**飞书私聊文字销售**和**采购图片**。
- 飞书语音消息下载、语音转文字（ASR）、转写结果确认和失败回退尚未实现，因此不能把“语音录单”标记为已上线。
- 当前分支尚需完成服务器部署、新应用配置、Schema 校验和真实飞书端到端验收。
- 网页工作台尚未进入本阶段实施范围。

## 4. 2026-09-24 当前业务决策

### 4.1 暂不接入支付平台数据

当前版本不接入微信支付、支付宝或抖音支付的交易 API，也不建立支付回调、渠道流水同步或自动对账流程。现有微信支付经营账户静态码继续照常使用，但它暂时不与本系统直接通信。

### 4.2 商品和资金信息由人一起提供

销售录单时，用户一次性向飞书机器人提供：

- 商品编号或足以识别商品的信息；
- 尺码和数量；
- 实收金额；
- 收款方式，例如微信、支付宝、现金或抖音；
- 必要时提供优惠等补充信息。

示例：

```text
8088-26 灰色 36 码 1 双，收 245 元，微信。
```

系统解析后必须先展示确认卡片。只有用户确认，才写销售明细、扣减库存并生成资金流水。缺少商品、尺码、数量、金额或收款方式时，系统必须追问，不得猜测后直接入账。

用户希望最终通过语音完成上述输入。V1 的业务口径已经确定为“语音中同时包含商品和资金数据”，但技术上先复用现有文字解析和确认入账链路：

```text
飞书语音消息
→ 下载音频
→ 语音转文字
→ 复用销售文字解析器
→ 确认卡片
→ 销售、库存和资金联动
```

在语音链路完成前，使用等价的文字内容录单，不阻塞销售、库存和资金先运转起来。

## 5. 当前最优先的实施顺序

1. 在服务器部署当前飞书 V1 分支，保持 PM2 单实例运行。
2. 配置新飞书应用、新租户和新多维表格的环境变量。
3. 执行 Schema 校验，确认核心表名、字段名、字段类型和关联目标符合代码配置。
4. 用一笔真实但可人工复核的销售文字完成全链路验收。
5. 用一批真实但可人工复核的采购图片完成全链路验收。
6. 核对销售明细、采购入库、库存流水、实时库存、资金流水和供应商往来款是否一致。
7. 在文字链路稳定后增加语音转写入口；转写后的业务解析与入账规则不得另写一套。

当前阶段的目标不是扩展更多渠道，而是先让以下闭环稳定运行：

```text
销售确认 → 销售明细 → 库存减少 → 资金收入
采购确认 → 采购入库 → 库存增加 → 供应商应付
```

## 6. 当前阶段验收标准

- 相同飞书消息重复投递时，不产生重复销售、库存或资金记录。
- 必填信息不完整时只生成待补充草稿，不正式入账。
- 用户未点击确认时，不改变库存和资金。
- 成功后可以通过消息 ID、任务 ID、来源单号和飞书 `record_id` 追溯整笔业务。
- 任一跨表步骤失败后可以安全重试；已经成功的步骤不重复写入。
- 入账后回读多维表格，库存流水变化后数量与实时库存一致。
- 销售确认后的资金收入等于用户确认的实收金额和收款方式。
- 采购确认入库形成应付；只有实际付款时才形成资金支出。
- 语音功能上线前，至少覆盖转写成功、转写失败、关键信息缺失和重复语音消息四类测试。

## 7. 未来支付方向（已记录，当前不开发）

### 7.1 渠道流水与业务账对账

未来如果需要接入微信、支付宝或抖音，应新增独立的“渠道交易流水”，保留平台真实交易记录；现有“资金流水”继续表示系统业务账。两者通过自动或人工对账建立关系，渠道数据不得直接覆盖业务账。

```text
销售确认                 → 资金流水（业务账）
支付平台 API / 账单      → 渠道交易流水（平台账）
资金流水 + 渠道交易流水 → 对账结果
```

### 7.2 自开发 JSAPI 固定收款码

未来可以把自开发 JSAPI 收款码作为正式支付方向：顾客扫码打开商户页面，后端先创建具有唯一商户订单号的支付订单，再由微信支付完成收款。支付成功后，微信支付向商户配置的回调地址发送通知；系统验签、解密并确认订单状态后，再通过飞书机器人提醒用户补充或确认对应商品。

这一方向的价值是把每笔支付、销售、商品、退款和资金记录准确关联起来，同时保留顾客扫码付款的使用体验。

进入该阶段前必须同时满足：

- 当前销售、采购、库存和资金人工闭环已稳定运行；
- 商户号、合适的 AppID、JSAPI 权限和授权目录已准备完成；
- APIv3 密钥、商户私钥和微信支付公钥使用服务器密钥配置，绝不写入代码、多维表格或日志；
- 已设计商户订单、渠道交易流水、支付通知幂等和对账结构；
- 支付回调只确认“钱已收到”，不能在商品未知时直接扣库存；
- 对回调进行验签、解密、幂等处理，并在漏收回调时通过查单恢复状态。

## 8. 给后续开发者和 AI 的边界

- 不要把支付平台接入当作当前任务，也不要现在安装支付运行时 SDK 或新增支付数据表。
- 不要把“计划使用语音”写成“语音已经实现”；以代码和端到端测试为准。
- 不要让支付通知绕过确认流程直接生成销售或扣减库存。
- 不要复制一套语音专用销售入账逻辑；语音只负责转成文字，后续复用现有销售服务。
- 不要让网页工作台、飞书工作流或机器人分别维护不同的库存和资金规则。
- 不要因未来支付规划影响当前销售、采购、库存和资金闭环的上线优先级。

## 9. 状态更新规则

每次重要决策或上线后更新本文件，并为功能使用以下状态之一：

- **设想**：仅讨论过，尚未形成正式方案；
- **已决策**：方向已经确认，但尚未开发；
- **开发中**：已经开始改代码，但未通过验收；
- **待部署**：本地代码和测试通过，尚未在服务器验证；
- **试运行**：已部署，正在用真实业务观察；
- **已上线**：真实链路通过验收并稳定运行；
- **已冻结**：保留但不再新增能力；
- **已退役**：不再运行并已经清理。
