> 最后更新：2026-09-29

### A. 数据结构对齐（与库存、采购保持一致）

**A1 尺码关联改造** — 状态：**已完成**

尺码字段已从数字改为关联「尺码管理」（只读核对：`type=18`、指向尺码表、非多选），
库存线和采购线都改完了，**销售是最后一条**。这是硬前提：不做的话销售链路在新的表结构上跑不通。

已完成：

- `salesOrderService.js`：写入前用 `SizeReferenceService.resolveByNumber` 解析出关联记录 ID，
  明细写 `relation(sizeRecordId)`；幂等比对改用 `singleLinked` 按关联记录比
- `salesDeliveryService.js`：交付读尺码改走 `resolveLinkedCell`
- `salesFollowupService.js`：待交付/待收款列表的尺码改走共享解析

**为什么测试之前没发现**：本地假 Base 不校验字段类型，"写数字、读数字"在测试里是自洽的，
掩盖了真实表已改成关联。所以这次给测试加了**写入形态的断言**（明细的尺码必须是关联记录 ID），
delivery 与 followup 的夹具也迁移到关联形态并补上尺码表。

**A2 配品纳入销售** — 状态：**开发中**（数据层与写入层已完成，解析层待做）

「其他配品」表（腰带、鞋油、袜子、包等）的商品要能记进销售明细。

- 配品**不跟踪库存**、**没有尺码**、**当场结清**；只记一条销售明细 + 一条收款记录
- 配品既能**单独成单**，也能**和鞋混在同一单**——两种情况用同一套结构，差别只是明细里有几行
- 需要在飞书里给「销售明细」加一个 **`配品`（关联「其他配品」）** 字段，与 `编号` 二选一
- 代码侧用**可售品配置**声明属性，不写 `if (是配品)`：

```js
const SELLABLE_KINDS = {
  shoe:      { requiresSize: true,  tracksInventory: true,  requiresFulfillment: true,  allowsVoucher: true,  allowsDeposit: true },
  accessory: { requiresSize: false, tracksInventory: false, requiresFulfillment: false, allowsVoucher: false, allowsDeposit: false },
};
```

已完成（代码在 `src/config/sellableKinds.js`，运行配置为前三个属性）：

- schema 加 `accessory: '配品'` 映射；「销售明细」字段快照测试同步更新
- `salesOrderService`：按可售品属性走——鞋解析尺码并写尺码关联，配品写「配品」关联、
  **不写尺码**、履约状态直接写「已交付」（不跟踪交付，也不会进待交付列表）
- 幂等比对：配品行要求尺码关联为空，鞋行要求尺码关联正好是那一条
- `salesDeliveryService`：先判交付状态再解析尺码，配品不会被当成待交付去扣库存
- 未声明的可售品类型直接报错，不会静默按鞋处理

**待做**：解析层——让 AI 能把「39元腰带」这类说法精确匹配到「其他配品」表（不做模糊匹配，
匹配不上就交给确认卡片让用户选，复用 B1 那套）。

**部署依赖**：生产表的「销售明细」必须也已加上 `配品` 字段，否则部署门槛会拦（已在生产表加好）。

### B. 匹配与解析

**B1 颜色从必填变为可选** — 状态：**已完成**（代码与测试完成，**待真实飞书实测卡片点击**）

用户现在**不说颜色**了，所以这不是兜底，是主路径：

```
用货号去匹配
  ├─ 货号能确定唯一颜色 → 确认卡片里直接显示（用户不用动手）
  └─ 货号有多个颜色     → 确认卡片里给候选颜色，让用户点选
```

数据依据：357 个货号里 **78% 只有一个颜色**（自动定），22% 有两个颜色（需要选）。
多个候选时**按明细逐条**给一组颜色，不是整单一个选择。

**判定规则（已定，零颜色逻辑）**：

```
只看货号：
  ├─ 库里没有这个货号   → 回文字要求核对，不发卡片
  ├─ 该货号只有一个颜色 → 自动定，卡片明细行直接显示最终编号
  └─ 该货号有多个颜色   → 卡片给候选按钮，让用户选
```

**用户说的颜色完全不参与判定**：不比对、不提示、不做一致性判断。
颜色卡片只在「该货号有多个颜色」时出现。

为什么这么定：卡片上的候选是**每次从库里实时读的**，库里颜色改名也不会失效；
而任何"匹配规则"都建立在对说法的假设上，假设一定会过期（而且模糊匹配天然有不准的时候）。

**没有任何容错性的"猜"**：货号对不上就明确报错让用户核对。以前有过一条"剥掉货号尾部的
汉字再找一次"的容错，已删除——它服务的是"用户说颜色"的场景，而那个场景我们已经决定不存在；
而且出问题时吵闹一点，比静默替用户"修好"更容易发现 AI 的字段提取在退化。

**已实现**：解析器在颜色未定时返回候选而不是抛错；录入流程照常发确认卡片；
卡片按明细渲染颜色按钮（`choose_sale_color`）；确认前校验每条明细颜色已定。
解析器契约从「抛错」改为「返回候选」，原有 6 条断言相应更新——**不猜、不跨货号**这两条不变。

**待真机验证**：单色货号不用选、多色货号能选、多双订单每条都能选。

**卡片交互形式**（已定，方案 B）：颜色按钮**横排**，颜色多时由飞书卡片自动换行。
使用场景以移动端为主。已经定的颜色只展示、不出按钮——
单色货号（78%）和用户说清颜色的情况都不需要动手，所以按钮只在少数订单上出现。

**B2 定金语序** — 状态：**已决策**（并入 B3，不单独修）

用户说「交了 100 块钱定金，下次还要再给 140 元」时，系统识别不了——
现在的正则只认「定金 100 元」或「100 元定金」，中间夹「块钱」就失效，
于是判成「没说定金金额」。

**不单独改正则**：那是「用户换个说法我们加一条正则」，没有终点。
并进 B3 的结构化交接一起解决。

**B3 结构化交接** — 状态：**已决策**（根治解析不稳定）

现在的规则层用正则去解析用户原话（`depositTerms`、`voucherMentions`、
`explicitCashPayments`），遇到没预想到的说法就失效，而且表现为"信息不完整"。

改为让 AI 只输出结构化事实，规则层只做查表、算账、校验：

```js
{
  items:    [{ item_no, color, size, quantity }],
  deposit:  { amount, method },
  balance:  { amount, when },
  vouchers: [{ count, purchase, face }],
  cash:     [{ amount, method }],
  gifts:    [{ text }],
}
```

规则层从此不再认识「定金」这两个字长什么样。

### C. 状态模型

**C1 销售动作注册表** — 状态：**已决策**

现货 / 预付 / 未付 / 团购券**不是四条流程**，而是同一个状态机的四种初始组合。
三个要素各有载体：成交（销售主表）、交付（明细的履约状态）、收款（收款明细）。

```js
const SALES_MOVEMENTS = {
  SALE_CASH:      { delivery: 'immediate', receipts: [{ kind: 'full', status: '已收款' }] },
  SALE_PREPAID:   { delivery: 'deferred',  receipts: [{ kind: 'deposit', status: '已收款' }, { kind: 'balance', status: '未收款' }] },
  SALE_UNPAID:    { delivery: 'immediate', receipts: [{ kind: 'full', status: '未收款' }] },
  SALE_GROUP_BUY: { delivery: 'immediate', receipts: [{ kind: 'customer', status: '已收款' }, { kind: 'platform', status: '待平台结算', expectDays: 5 }] },
};
```

**C2 第二次确认只有两件事** — 状态：**已决策**

预付、未付、团购券都有"第二次确认"，但拆开看只有**交付确认**和**收款确认**两个动作，
两个入口都已经存在（`salesDeliveryService.deliver`、`paymentService.record`）。
现货只是"创建时把两件事一次做完"。

**C3 混合订单的金额规则** — 状态：**已决策**（"定金多行明确拒绝"部分已完成）

- 券和定金**只作用于鞋行**，配品当场结清
- 配品的优惠是**行内优惠**（15 元鞋油卖 10 元 → 这一行成交额就是 10），不参与整单分摊
- 整单应收 = 各行成交额相加
- ✅ **定金遇到多行明细已改为明确拒绝**：以前 `items.length === 1` 会把尾款整块跳过，
  应收金额被静默算丢且不报错；现在改成提示「定金单暂只支持一条明细；多双请分开说明，
  或逐双给出成交金额」。尾款归属无法判断时，宁可让用户重说，也不猜。

**C4 退换货** — 状态：**已决策**（最后做）

退货 = 反向动作（库存 +1、资金 −1、引用原单）；换货 = 退货 + 一笔新销售。
「退换赔货交易」表已存在，但 `原销售单号 / 原销售明细` 是文本字段，建议改成关联，
否则将来追溯和对账很脆。另外它现在是鞋形（只有 `编号` + `尺码`），退配品要加 `配品` 字段。

## 3. 已确认的关键业务规则

这些是讨论中敲定的，改动前先看这一节：

| 规则 | 内容 |
|---|---|
| 颜色判定 | **只看货号**：唯一颜色直接定，多个颜色交给卡片让用户选；**用户说的颜色不参与判定**（不比对、不提示） |
| 颜色说不清 | 单色货号自动定（78%）；多色货号在确认卡片上让用户选 |
| 货号写错 | 直接拒绝并提示核对，**不发卡片**——货号错了，给颜色候选也没意义 |
| 券与定金 | **只针对鞋**，不能用在配品上 |
| 配品优惠 | 行内优惠，不参与整单分摊。配品不单独记单价，所以只记成交金额、不算折扣额度 |
| 一单几张券 | **暂按一单一张**（一单两张券的场景先不做，已在测试里标注为待修复） |
| 成本与利润 | **暂不计算**。当前目标只到"把销售明细和收款明细记对、知道今天卖了多少钱、卖了什么" |
| 多双报价 | 必须逐双说明成交金额；只给总价时要求补充，**不猜测拆分** |
