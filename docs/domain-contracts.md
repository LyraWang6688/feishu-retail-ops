## 0. 怎么用这张表

- **一行 = 一条业务事实**（不是每个字段）。粒度按"一次会写错的事"来切。
- 每条事实回答四个问题：**输入是什么 / 输出写哪张表 / 失败了算什么 / 重试用什么键防重**。
- 「**谁在写**」这一列最有用：**出现两个以上来源的地方，就是将来会长成巨文件的地方。**

## 1. 总图：谁在写哪张表（"解耦"体检表）

| 表 | 写入口 | 涉及服务 | 评价 |
|---|---|---|---|
| **实时库存**（liveInventory） | **3 处，1 个服务** | `inventoryService` | ✅ **单一写入口**（新增/删除/改状态都只在这一个服务里） |
| **库存流水**（inventoryLedger） | **3 处，1 个服务** | `inventoryService` | ✅ **单一写入口** |
| **采购入库**（purchaseInbound） | **1 处** | `purchaseWebhookService` | ✅ 单一 |
| **客户往来货款**（customerCredit） | **1 处** | `afterSalesService`（走 `createOnceByKey`） | ✅ 单一，且**有远端幂等键** |
| **收款明细**（paymentRecord） | **4 处，2 个服务** | `paymentService`（3 处）+ **`afterSalesService` 直接写（1 处）** | ⚠️ 销售侧有中间层，**售后绕过中间层自己写** |
| **销售明细**（salesDetail） | **4 处，3 个服务** | `salesOrderService`（建）、`salesDeliveryService`（交付）、`afterSalesService`（建售后行 / 改原行履约状态） | ⚠️ 写入点分散，但语义不同（建单 / 交付 / 售后） |
| **销售主表**（salesEntry） | **8 处，5 个服务** | `larkMvpService`（建单/单号/解析结果）、`salesOrderService`（失败原因）、`salesStatusWriter`（四个状态列）、`afterSalesService`（建售后新主表）、`salesMessageLinkService`（消息链接） | ⚠️ **最"多人写"的一张表**；其中**状态列已收口到 `SalesStatusWriter` 单一入口** ✅ |

> **一句话**：库存那两张表收口得最好（这正是"销售/采购都不许直接改库存"的落地）；**主表和收款明细是"多人写"的地方**。

## 2. 货那条线：逐条契约

### 2.1 销售出库（卖货交付）

| 纵轴 | 内容 |
|---|---|
| **输入** | `InventoryService.applySale({ salesDetailRecordId, productRecordId, size, quantity })`。**销售只说"这条要出库"**；先扣门盒还是先扣样品由库存自己决定（`consumes: ['门盒','样品']`），**不扣仓库** |
| **输出** | 库存流水 **1 行** + 实时库存**删掉 N 行**；成功后销售明细写「已交付」 |
| **失败语义** | **逐条隔离**：一条失败不影响其它条，进 `failures`；明细的「已交付」只在扣减成功后才写 |
| **幂等键** | `inventory_STOCK_SALE_DECREASE_<sha256(销售明细id)[:20]>`（按**来源明细**，不按人、不按单） |
| **谁在写** | 库存两张表**只有 `InventoryService`** |
| **洞** | ① 群话题通道会把**失败的双数当成"已交付"**报给她（`salesThreadProgressService`）；② `runForStock` 的互斥**只在单进程单实例内成立**（PM2 多实例/双机就会失效） |

### 2.2 售后退货入库

| 纵轴 | 内容 |
|---|---|
| **输入** | 售后执行器 → `applyChange({ kind: SALE_RETURN, state: 她选的回库状态 })` |
| **输出** | 库存流水 **1 行（增加）** + 实时库存**新增 N 行**；原明细改「已退货」；**售后另建一张主表**（引用原单号，原主表不动） |
| **失败语义** | 闸门分片：同一分片已完成 → **整次跳过**；库存那一步失败 → 主表写 `库存状态=写入失败` |
| **幂等键** | `after_sales_task_<taskId>_<原明细批次哈希>` ⚠️ **taskId 每条消息不同** |
| **谁在写** | 库存两表仍只有 `InventoryService` ✅（售后走 `applyChange`） |
| **洞** | ① **同一批明细从两条消息进来 → 两个分片 → 会各写一遍**（重复退款 + 重复加库存）；② `markOriginalDetails`（改原明细）排在钱和库存**之前**，中途失败会出现"原单显示已退货、但钱和库存都没动" |

### 2.3 售后换货

| 纵轴 | 内容 |
|---|---|
| **输入** | 售后执行器（`EXCHANGE`） |
| **输出** | **两行流水**：旧鞋回（`SALE_RETURN`，增加）+ 新鞋出（`SALE_CASH`，减少·门盒）；实时库存一增一减 |
| **幂等键 / 谁在写 / 失败语义** | 同 2.2 |
| **洞** | 与 2.2 同（分片键）；**两行流水方向相反但数量都写正数**，靠「库存行为」区分方向 |

### 2.4 售后赔货

| 纵轴 | 内容 |
|---|---|
| **输入** | 售后执行器（`COMPENSATION`） |
| **输出** | **只有出货一腿**（`SALE_COMPENSATION`，减少·门盒），**坏鞋不回库** |
| **幂等键 / 谁在写 / 失败语义** | 同 2.2 |
| **洞** | 与 2.2 同 |

### 2.5 采购入库

| 纵轴 | 内容 |
|---|---|
| **输入** | `InventoryService.applyPurchase({ purchaseInboundRecordId, productRecordId, size, quantity, state })` ⚠️ **`state`（门盒/样品）是由采购侧决定的** |
| **输出** | 库存流水 1 行 + 实时库存**逐双新增 N 行** |
| **失败语义** | 逐件尝试；入库单创建失败会抛（可重试）；**出图/发群失败被吞掉**（采购事实已写、图不补发） |
| **幂等键** | 操作级 `inventory_STOCK_PURCHASE_INCREASE_<sha256(采购入库id)>` + **每一双** `<操作id>:<序号>` ✅ 设计好；⚠️ **但「采购入库」这张表自己没有远端幂等键**（靠 批次+货品+尺码 内容回扫防重） |
| **谁在写** | 采购入库只有 `purchaseWebhookService`；库存两张表只有 `InventoryService` |
| **洞** | ① **采购替库存决定货物状态**，而且查不到时**默认按门盒、不报错**；② 入库单无唯一标识；③ 出图失败不可补发 |

### 2.6 采购退货出库

| 纵轴 | 内容 |
|---|---|
| **输入** | 退货执行器 → `applyChange` |
| **输出** | 库存流水 1 行（减少）+ 实时库存删行 |
| **失败语义** | 退货有自己的归批窗口与核对计划（`return_plan` 冻结，重试不重算） |
| **幂等键** | 批次哈希（退货自有窗口） |
| **谁在写** | `InventoryService` ✅ |
| **洞** | **库存流水没有"来源关联"列**（代码注释自认待办）→ 账上少掉的货**追不到是哪张退货单** |

### 2.7 手工盘点调整

| 纵轴 | 内容 |
|---|---|
| **输入** | 工作台 `POST /api/workbench/inventory/adjustments/count`；行为 `STOCK_MANUAL_INCREASE` / `STOCK_MANUAL_DECREASE` |
| **输出** | 库存流水 + 实时库存增/删 |
| **失败语义** | ⚠️ **批量里单条失败，HTTP 仍返回成功** |
| **幂等键** | 界面侧 `requestId` —— ⚠️ **只存在浏览器内存，刷新页面即丢** |
| **谁在写** | 库存两张表只有 `InventoryService` ✅；⚠️ **「操作人」从不写到表里**（只记在服务器文件 + 日志） |
| **洞 / 待定** | ① 操作人不落账（人和系统在账上分不出）；② requestId 刷新即丢；③ 单条失败返回成功；④ **【需拍板】手工调减要消耗哪些状态**（代码里明写 TODO：`MANUAL_DECREASE_CONSUMES = null` 最保守，等她定） |

### 2.8 冻结 / 释放（换季）

| 纵轴 | 内容 |
|---|---|
| **输入** | 工作台 `POST /api/workbench/inventory/adjustments/season`；`STOCK_FREEZE`（门盒/样品→仓库）/ `STOCK_UNFREEZE`（仓库→门盒/样品） |
| **输出** | 实时库存**只改「所属状态」这一列**（不新增"冻结状态"列）；数量不变 |
| **幂等键** | 同 2.7（界面 requestId） |
| **谁在写** | `InventoryService` ✅ |
| **已知代价（代码注释自认）** | ⚠️ **记录进了「仓库」以后，原来在门盒还是样品就查不到了**（流水里既没有操作人也没有来源列可以翻回来）→ **所以"释放"必须由她在界面上选"回门盒还是回样品"** |

### 2.9 补样品（门盒 → 样品）

| 纵轴 | 内容 |
|---|---|
| **输入** | 卖掉的如果是样品 → 从门盒转一双回去当样品 |
| **输出** | 实时库存**只改状态**（门盒→样品），数量不变；库存流水 1 行（变动数量 = 0） |
| **幂等键** | `inventory_sample_<sha256(销售明细id)[:20]>` |
| **谁在写** | `InventoryService` ✅ |
| **洞** | 补选失败不阻断入账（库存已扣，只影响展示样品）→ 需要工作台兜底 |

## 3. 销售主表四个状态列：谁在什么时候写

| 状态列 | 含义 | 谁写 | 什么时候 |
|---|---|---|---|
| **确认状态** | **用户**在卡片上的操作 | `salesOrderService` | 入账开始 / 失败 |
| **销售状态** | **货**（= 销售明细） | `salesOrderService` | 明细写完 → 「已写入」 |
| **资金状态** | **钱**（= 收款明细） | `salesOrderService` | 收款写完 → 「已写入」 |
| **库存状态** | **库存流水 + 实时库存** | `salesDeliveryService` | 交付写库存之后 |
| （售后自己的新主表） | 同上四列 | `afterSalesService` | 写在**售后新建的那张主表**上 |

**两条硬约束（代码里写死的）**：
1. **唯一写入口** `SalesStatusWriter`（白名单：`userAction` / `sales` / `funds` / `stock`）；旧字段（`confirmStatus` / `orderStatus`）**已无任何写入口** ✅
2. ⚠️ **状态列写失败只记 warning，决不影响业务写入** → 取舍是对的（不能让"记进度"带崩"记账"），**但这意味着这些列不能当审计依据**：你看到的「未写入」有可能是"写失败"

## 5. 需要业务负责人拍板（不从代码推断）

| # | 待定的事 | 现在代码怎么做 | 影响 |
|---|---|---|---|
| 1 | **手工调减**要消耗哪些状态的实时库存？ | 最保守：只消耗指定状态（`MANUAL_DECREASE_CONSUMES = null`，代码 TODO） | 盘亏时会不会顺手吃掉样品 |
| 2 | 售后退货的明细行**要不要写「销售日」**？ | 不写，报表按原单录单日兜底 | **退款会被算成正向销售 → 当天销售额反向变大** |
| 3 | 退款要不要在报表里**冲抵**？ | 未冲抵 | 同上 |
| 4 | 预付只说了定金、**没说尾款**时，收款明细几条？ | 只有她说"欠/尾款"时才挂第二条 | 不挂 → 差额永远收不掉 |
| 5 | 「**压根没提钱**」（例：卖一双 230）算现货，还是拦下来问？ | 按现货，且不挂应收 | 该收的钱不会出现在账上 |
| 6 | **一条消息里会不会出现两笔不同交易类型**？ | 一条消息 = 一张主表、交易类型**整单级** | 混合类型必错一双（交付决定只能有一个） |
| 7 | 确认卡片要不要**回显**「交付后果」与「未收款占位」？ | 只显示交易类型名与实际收到的钱 | 她看不到"会不会扣库存""还会挂一笔未收款" |
