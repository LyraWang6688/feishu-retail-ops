## ② 问题①：提示词改了什么

**改前实测**：`「1 双」「一双」「10 双」→ 模型返回 {"items":[]} → 采购报单解析失败: 未识别出有效尺码数量`，
整条报单 failed、单据信息 0 行。
**根因**：规则 1 的"没有提到的已选尺码…不需要输出"被模型套到了**她明确说了数量**的「1 双」上；
规则 2 的"全部按默认一双"例子只列了「各一双」「每个码一双」「都是一双」。

**改后原文**（`doubaoService.js:469-489`；`${...}` 是运行期填充）：

```text
你是鞋店采购数量说明解析助手。表单已经明确勾选尺码：${allowedSizes.join('、')}。
请只从数量说明中识别“数量不是默认一双”的例外，不要补充未勾选尺码，也不要输出没有特别说明的尺码。
输出格式：{"items":[{"size":39,"quantity":1}]}
规则：
1. 数量说明没有提到的已选尺码由后端保持默认一双，不需要输出。
   ⚠️ 但“她明确说了数量”时必须输出，哪怕数量就是 1，也不许当成“没提到”：
   例如“1 双”“一双”都是**明确说了数量**，必须输出这一条；
   只有“完全没提数量”（例如只说“38 码”）才算没提到。
   ⚠️ 前提是那个数量确实是**正整数**：0 双、2.5 双这类不是正整数，按规则 5 处理。
2. 如果说明是在确认“全部按默认一双”（例如“各一双”“每个码一双”“都是一双”“1 双”“一双”“按默认来”），
   必须输出全部已选尺码且数量都是 1，不能返回空数组——这种情况数量是明确的，不是语义不明确。
3. “40两双”只输出40码数量2；“每个码两双”输出全部已选尺码数量2。
   ⚠️ 两位数要**看全**：“10 双”= 10、“12 双”= 12、“20 双”= 20；
   数字里有 0 **不等于**数量是 0，也不许看漏 0 当成 1。
4. 只能输出已选尺码列表中的正整数尺码；禁止输出42.5等小数尺码。
5. 数量必须是正整数。**只有**说明里那个数量本身就是 0 或小数时（例如“0 双”“2.5 双”“一双半”），
   **不要四舍五入、也不要替她猜一个整数**，返回空数组 {"items":[]}——由后端拒绝整条报单；
   “10 双”“20 双”是正常的两位数，**必须正常输出**，不要当成 0。
   只有在完全无法判断数量时才返回空数组，不得猜测。
6. 只输出 JSON，不输出 Markdown 或说明。
数量说明：${originalText}
```

四处改动（`git diff` 可核对）：

| # | 改哪 | 内容 |
|---|---|---|
| 1 | 规则 1 | 追加"她明确说了数量就必须输出（哪怕 1）"＋"0/小数不算（按规则 5）" |
| 2 | 规则 2 | "全部按默认一双"的例子补上「1 双」「一双」 |
| 3 | 规则 5 | 追加"0 或小数**不许四舍五入、不许猜**，返回空数组" |
| 4 | 规则 3 / 5 | 追加"两位数要看全（10 双 = 10，数字里有 0 不等于数量是 0）" |

⚠️ **第 3、4 处都不是拍脑袋加的，是实测逼出来的**（都被她写进了验收标准）：

- **第 3 处**：只改前两处之后，`C10「2.5 双」` 变成**写单成功**——
  模型返回 `{"items":[{"size":38,"quantity":3}]}`（四舍五入成 3），
  违反验收标准第 2 条（证据 `runs/run-20261006081308`）。
- **第 4 处**：补了第 3 处之后，`C9「10 双」` 又出现**空数组**（证据 `runs/run-20261006082521`）——
  在这之前它 **4/4** 次都正常解析出 10。最可能是规则 5 里"0 双"这个例子被模型套到了"10"上
  （数字里有 0）。所以按她定的"先重跑看它到底修没修好再决定要不要加"，**加了**两位数那一条，
  并把规则 5 改成"**只有**数量本身就是 0 或小数时…"。
  姊妹报告（`docs/reports/purchase-report-quantity-2026-10-06.md` §4）也实测到
  **两位数裸总数（10/11/12 双）连续 5 次全空**，与这里的判断一致。

## ④ 问题②：归批路径用哪个尺码集合 —— **真相：逐条解析是设计如此，不是 bug**

**结论：不合并。B1 那种用法（同一条说明同时提到两个尺码、却拆成两条各勾一个尺码的记录）
系统不支持，也不该支持。**

依据（**四条都是实测/权威口径，不是推断**）：

1. ⭐ **权威业务口径**（`docs/purchase-intake-batch-spec.md`，业务负责人 2026-10-06 逐字）：
   > 「一个单子的提交它就是一个行为……我之所以说它会有多条记录，原因是因为**它会有多个编号**。」
   ⇒ **一次提交 = 一个行为 + N 个编号（货品）**：多条记录是**多个货品**，
   **不是**同一个货品的多个尺码。尺码集合是**挂在货品上的**，
   跨记录合并等于让 A 货品的说明去改 B 货品的数量——那不是修 bug，是造新 bug。
2. **测试 Base 里与生产同构的记录**（只读）：一个「报货批次号」下每条记录对应**不同货品**，
   每条有自己的尺码集合（常常多选）。例：批号 `202609271` 12 条 →
   `[45] / [41,42] / [43,44] / [43] / [38,41,42] / …`，货品各不相同；
   `202609201`（7 条）、`202609231`（7 条）同理。
   ⚠️ 同批号下"同货品出现两次"的，在真实形态里**一条都没有**；只有自测脚本自己造的
   `SELFTEST-QTY-*` 批号才是那样。
3. **代码与既有用例都按"每条记录自己解析"写**：`parseReportQuantities`
   只读**本条记录**的 `尺码` 字段（`purchaseWebhookService.js:307-316`）；
   `buildPurchaseQuantities` 只接受本条的 `selectedSizes`，说明里出现未勾选尺码即抛错
   （`purchaseQuantityPolicy.js:53-55`）。既有用例
   `同一个批次的多条报单合成一个批次任务…`（BATCH-CONF：两条记录、同货品、各一个尺码、
   各自写自己的说明）→ 2 行单据、数量各自正确 ✅。
4. **同一个货品的多尺码是支持的，而且实测通过**：用例 **C4**（一条记录勾 38+39，
   说明 `38 码 2 双，39 码 3 双`）→ 2 行 / `{38:2, 39:3}` ✅；
   真机同构数据里也有 `[38,41,42]` 这种一条记录多尺码。
   另外，归批的改造方案（`docs/purchase-intake-batch-plan-2026-10-06.md`）明确写着
   「**只改「什么时候出图」，不改解析、不改数量口径**」。

**建议她怎么用**（不改代码）：

- **一个货品一条记录**：把该货品的**所有尺码**勾在这一条上，说明里写这些尺码的数量
  （只写例外，没写的按 1 双）。
- 同一次提交里的**多个货品**才拆成多条记录 —— 归批合并的是**单据/出图**，不是尺码集合。
- **不要**把一条同时提到多个尺码的说明复制到多条记录上。

**顺带记一笔（观察，本次未改）**：这种"说明提到别的尺码"会让**整批**落成可重试的 failed
（`purchase.batch.failed_retryable`），报单记录的「处理状态」**保持为空**——这是刻意的
"不丢单、不写错"口径（`process()` 的 catch 有注释），但运营上表现为**"提交了没反应"**，
只有日志能发现。要不要给它一个**可见反馈**（例如可重试的失败提示）是另一个需求。
姊妹报告 §7 也把"失败后无自动重试"列为建议项。
