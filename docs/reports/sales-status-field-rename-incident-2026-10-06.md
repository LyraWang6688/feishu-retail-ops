## 4. 为什么闸门没拦住（**这次事故的核心教训**）

### 4.1 闸门只比对【字段名在不在】

`server/src/services/v1BitableGateway.js:103`：

```js
async validateTable(tableKey) {
  const table = this.table(tableKey);
  const actual = await this.listFields(tableKey, { refresh: true });
  const actualNames = new Set(actual.map((field) => field.field_name));
  const missing = Object.values(table.fields).filter((name) => !actualNames.has(name));
  if (missing.length) throw new Error(`“${table.tableName}”缺少 V1 字段: ${missing.join('、')}`);
  return { tableKey, tableId: table.tableId, fieldCount: actual.length };
}
```

**它只做一件事：`table.fields` 里的每个名字，在真表里查得到吗。**
⇒ 不看**字段值**、不校验**单选项**、不校验**字段 id**、也不看这个**名字背后是不是换了另一列**。

### 4.2 闸门的另外两条腿**也只读字段元数据**（本次核过）

`sales` 范围的闸门 = `validateTables` + 尺码关联校验 + 幂等键校验（`server/scripts/validate_v1_schema.js`）。三条腿分别是：

| 腿 | 实现 | 读什么 |
|---|---|---|
| ① 字段名 | `v1BitableGateway.validateTable` | 字段**名**在不在 |
| ② 尺码关联 | `SizeReferenceService.validateSchema`（`sizeReferenceService.js:34`） | 字段**类型/关联目标**（`type===18`、`property.table_id`、`multiple`） |
| ③ 幂等键 | `validateIdempotencyKeyFields`（`infrastructure/idempotencyKey.js:102`） | 字段**在不在** + `type===1` |

⇒ ⭐ **三条腿没有一条读过任何一条记录的值。** 所以「字段名还在 + 字段类型没变」= **闸门必然全绿**。

### 4.3 ⭐ 「同一个表里：旧字段改名 ＋ 新建同名字段」闸门**完全看不见**

- **字段被删** → 老的闸门会红（`missing` 非空 → `throw`）。**这种情况我们是安全的。**
- **字段被改名** → 名字还在（只是**指向了另一列**）→ 闸门**绿**，而代码的取值**悄悄换了一个字段**。

🔴 **这比「字段被删」更危险**：删了会当场拦下来，**改名的不会** ——
**失败方式从"报错"变成了"静默读到空值"，一路走到门店点不动才被人发现。**

### 4.4 实测原文（闸门绿的样子）

部署闸门 `server/scripts/deploy_build.sh:17` 跑的就是 `pnpm run v1:schema-check:all`，成功时逐表打印
（格式见 `server/scripts/validate_v1_schema.js:45`：`` `OK ${item.tableKey} ${item.tableId} fields=${item.fieldCount}` ``）：

```
OK salesEntry tblLjFe3NjU61xKB fields=18
```

⚠️ **`fields=18` 是【真表的列数】**（`fieldCount: actual.length`，来自线上飞书返回），
⇒ 这一行**恰好证明**闸门看到了真表、而且**认为一切正常**：18 列里包含「确认状态」这个名字，检查通过。
（本报告核过这行的**格式与 tableId** 与源码一致；**18 这个数值本身是引用实测**，见 §8。）

## 5. 两条恢复路径（**都已验证可行**）

### 5.1 路径 A —— 改回名字（**几十秒 · 不用部署**）

**动作（她在生产表里做）**：

2. 把**新建的那个**先改名为 **「确认状态（新）」**（腾出名字，避免重名）。
   ⚠️ 顺序要先腾名字，否则飞书不允许重名。

| 项 | 内容 |
|---|---|
| ⭐ **依据** | **旧字段里 76 条「已入账」的值完好无损**（§3.1）—— **改名即可恢复** |

| **适用** | 门店正在营业、要**立刻**恢复打卡 |

> ⚠️ 注意 A 的两步之间**存在一个仍然坏的瞬间**：先改旧字段名 → 此刻表里会短暂出现两个「确认状态」的意图。

## 6. 改进建议

> ⚠️ 本节是**建议**。`AGENTS.md` 的修改**不在本报告范围内**（另开、且当前有别的 agent 在跑），
> **要不要改进 `AGENTS.md` 由父代理定。**

### 6.1 ⭐ 给闸门加「取值自检」（**首选**）

现在闸门只回答「字段名在不在」。建议**再回答一句：「值取得回来吗」**：

- **做法（示意，不是最终设计）**：`v1:schema-check:*` 里**读一条真实记录**（或按 tableId 取最近一条），
  对**关键字段**断言「**取到的值不是全空**」——例：`salesEntry.confirmStatus`（或其双读来源）在 89 条里有值；
  `parseStatus` 落在代码认识的值域内。
- ⚠️ **必须只读**：这一步**只调 `appTableRecord.list`（或 search）**，**一个字段都不许写**。
- ⚠️ **要能容忍合法的空**：新表、刚上线的维度字段本来就可能是空的 → **自检的输出应该是「分布」而不是硬失败**，
  或**只对"这一列 89 条全空、而它的前身有值"这种形状报警**。
- ⭐ **为什么这条最值**：它拦的正是本次这种**"名字还在、值没了"**的静默失效 —— **删字段会被名字检查拦住，改字段名只有值检查能拦住**。

### 6.2 ⚠️ 或者至少：「改生产表的字段名/字段」必须先同步代码 ＋ 跑闸门 ＋ **真启动一次**

- 生产表里**任何**改动（**改建名 / 加字段 / 改选项 / 改行为编码**）→ **先同步 `v1BitableSchema` 与相关映射**，
  **再跑 `v1:schema-check:*`**，**再真启动一次**（`app.js` 加载顺序那类问题只有真启动看得见）。
- ⚠️ `AGENTS.md` 里**已经有类似的一条**（"生产表里的任何更改都要同步到代码"）——
  **只补一句**：**「字段被【改名】也会静默失效 —— 闸门按名字查，改名后名字还在、值却换了列」**。
  ⭐ 这句话是本次事故**唯一新增的知识**，其余纪律原文已经覆盖。
- ⚠️ **配套提醒**：`v1:schema-check` 是**独立进程**、自己按正确顺序读 dotenv，
