## 4. 每个场景的库存变化（流水 ＋ 实时库存）

| 场景 | 库存流水（行为 · 变动数量） | 实时库存（门盒） | 说明 |
| --- | --- | --- | --- |
| 现货 · 一单一笔 | 销售减少 ×1 | −1 | 卖一双扣一双 |
| 现货 · 一单两笔 | 销售减少 ×2 | −2 | 两条明细各扣一双 |
| 现货 · 一单两笔支付方式 | 销售减少 ×1 | −1 | 支付方式不影响库存 |
| 预付 · 首次 | —（无） | 0 | 未交付不扣库存 |
| 预付 · 收口后（已完毕，微信） | 销售减少 ×1 | −1 | 交付那一刻才扣 |
| 未付 · 首次 | 销售减少 ×1 | −1 | 现货/未付当场交付，**第一次就扣** |
| 未付 · 收口后（成交，微信） | —（无） | 0 | **不重复扣**（重要：这就是"只补钱不交货"） |
| 销售退货 | 销售退货 ×1（增加） | **+1** | 退回的鞋回门盒 |
| 销售换货 | 销售退货 ×1 ＋ 现货销售 ×1 | 旧鞋 **+1**、新鞋 **−1**，**净 0** | 两条流水方向相反 |

⚠️ **口径提醒（我也是踩过才校准的）**：「库存流水.变动数量」写的是**正数**（这里都是 1），
**方向由「库存行为」那一列表达**（销售减少 = 减少、销售退货 = 增加），**不是用正负号表达**。
所以别把"退货 +1"理解成负数。

### 6.2 ⚠️ 测试 Base 与生产不一致的两处（我**只补了测试 Base**）

售后执行器在「退回的鞋回库」那一步会读**行为管理**的两个闸门（方向 + 是否启用）：
`SALE_RETURN` 在**测试 Base** 里**两列都没配**（方向空、未勾启用）→ 退货/换货必然失败。

- 我在**测试 Base**（不是生产）补齐了：`行为管理「销售退货」(SALE_RETURN) 库存方向 (空) → 增加`、`是否启用 未启用 → 启用`。
  脚本每次跑都会体检并打印，改了什么一目了然（生产 Base 一个字都不写）。⚠️ 最后一轮体检时它已经是"已补齐"状态（`behavior_fix: []`）——即测试 Base 里那两列现在就配好了。
- ⚠️ **顺带发现测试 Base 还有 5 条不对齐**（我**没动**它们，只在日志里列出来）：
  `销售赔货`（方向空、未启用）、`手工调增`、`手工调减`、`转冻结`、`转释放`（都缺方向 + 未启用）。
  → 这几条对应的功能在测试 Base 上**必然失败**；要测它们得先把测试 Base 补齐
  （**生产表的这两列是什么值，需要在服务器上只读核一遍**——本机够不着生产）。

### 6.3 🔴 只在测试 Base 见过、但需要业务口径确认的一条

**「钱退现金」时，退款记录里的「交易方式」写的是原单的方式（微信），不是现金。**
`afterSalesService.settleCash` 的口径是"现金/微信/支付宝都走收款明细这条腿，**方式取原单**"（代码里有注释，
是有意为之）。但她的原话是「退一双 …，**钱退现金**」——她说的方式和账上记的方式**不一致**。
→ 要么把她说的方法名写进退款记录，要么明确告诉她"方式沿用原单"。**这条我没改，等她拍板。**

### 6.4 可诊断性上的两个小观察（非阻塞）

1. 卡片确认被前置条件挡住时（例如"这条明细还没选颜色"/"还有样品要补"），
   `handleCardAction` **只回一个 toast、不落任何日志**。⚠️ 真实部署里路由层会打
   `lark.card.handled … result`，所以线上是看得见的；但**直接调 service 的自测/排障场景**下会像"点了没反应"。
2. `handleTaskFailure` 用任务快照发消息，那条文本回复**不带 `sales_entry_record_id`**，
   于是话题映射会记成空销售 id（本轮 s1 第一次跑时见过）。不影响主链路，但排查时容易困惑。
