## ⚠️ 未达标：差在哪 + 建议

### 差在：她只回「已完毕」/「成交」时，**只要这一单还挂着「未收款」，就一个字都不写**

- **实测（未付）**：首次入账后是 `未收款 269`。她在话题里说「**成交**」→
  日志 `sales.thread_progress.detected kind=complete reason=complete_cue:成交`，
  任务终态 `progress_applied` —— 但**收款明细仍是 `未收款 269`（无收款时间）**，
  四字段不变，库存也不变。**表里没有任何变化**，只是她收到一句问话。
- **实测（预付）**：首次是 `已收款 45` + `未收款 44`。说「**已完毕**」→ 同样是
  `kind=complete` / `progress_applied`，**明细仍「未交付」、`未收款 44` 仍挂着、门盒不扣**。
- **根因（代码位置）**：`server/src/services/salesThreadProgressService.js` 的 `applyComplete`
  （第 318-338 行）：
  ```js
  const hasPending = (await this.payments.recordsForSale(id)).some(r => 状态 === '未收款');
  const method = hasPending ? await this.resolveCompletePaymentMethod(task) : '';
  if (hasPending && !method) {
    await this.reply(task, this.config.replies.needMethod);   // 「这笔钱是怎么收的？微信还是现金？」
    return { replied: true, reason: 'payment_method_missing' };  // ← 什么都没写，但调用方当成"做完了"
  }
  ```
  `resolveCompletePaymentMethod` 只在「她这句话里说了方式」或「收款方式表里**只有一种**」
  时才有值；「成交」「已完毕」里没有方式，而测试 Base 有多种收款方式 → 返回空 →
  **只问不做**。
- **第二个问题（同一个 bug 的另一面）**：这条"只问不做"的返回被上层
  `SalesThreadProgressService.handle` 记成 **`progress_applied`**（成功），
  排查时看起来像"成交做完了"，实际一个字节都没写。
- ⭐ **链路本身完全能做**（同一单上已实测）：
  「**那双拿走了**」→ `kind=delivery` → 明细**未交付→已交付**、门盒 **-1**、库存状态→已写入；
  「**收到微信 44**」→ `kind=payment` → **同一条** `未收款 44` **原地翻转成 `已收款`** 并写
  `收款方式=微信`、`收款时间`（PR #165 的 BUG 2 修复，实测有效）。
- **建议**（不动业务口径、只补一处）：
  1. **「整单完成」不要因为缺收款方式就整条不做** —— 至少把**货那一半先做掉**，
     再用一句话问她"这笔钱收的微信还是现金"（现在的做法是钱货**都没动**）；
  2. 或者按她这句话里**已有的信息**推断：这一单若已有一笔「已收款」，
     收款方式通常与上一笔相同（预付那单就是 `已收款 45` 微信 + `未收款 44`），
     可以拿它当默认值，而不是回问；
  3. **状态如实**：只问了没写 → 记 `progress_asking`（或复用 `progress_reason`），
     **不要记 `progress_applied`** —— 这一列是"到哪一步了"的排查依据。

### 顺带：她原话的另一种问法（**建议确认口径**）

> 她的原话是「未收款**变为**已收款」。实测 PR #165 之后，收款那条是**原地翻转**的
> （不再新增第二条）✅。但「**已完毕**」这个词在她的语义里到底是"**钱货两清**"
> 还是"**货拿走了**"（= 只交付）？**未付**单说「成交」更像"钱收了"，
> **预付**单说「已完毕」更像"货拿走了"。现在代码把两个词统一当"整单完成"，
> 所以**必须凑齐钱+货**才算 —— 这也正是上面那个"缺收款方式就全不做"的直接原因。
> **建议业务负责人确认这两个词各自的意思**，再决定要不要拆成两种处理。

### 4（**仍然存在**，摩擦点）· 颜色已经说了，还要她再点一次
`server/src/services/larkMvpService.js` 第 1303 行：只要「货号 + 尺码」在库里有 **>1 个颜色**，
就无条件 `needs_color: true` 把选择推给卡片 —— **不看她说没说颜色**。
而且 AI 会把「绿色」归一成「绿」，`draft.color='绿'` 对不上候选 `'绿色'`，**自动匹配也救不回来**。
**实测**：她原话写了「黑色」，点确认时被拦下并弹
`{"toast":{"type":"warning","content":"还有明细没选颜色，请先在卡片上选择颜色，再确认订单"}}`。
→ 不是崩溃，但**多一次交互**；建议：**原话里的颜色能唯一匹配到某个候选时就直接采用**，
匹配不上再问（匹配规则放 `config/`，别写死在逻辑里）。

### 5 · 首次入账「未收款」占位行的语义
预付/未付首次入账会写一条 `未收款` 占位。它**不是经营事实**，只是"还差多少"的占位；
`salesProgressService` 算待收时 `status === '未收款'` 直接 `continue`（不计入已收）。
建议在「收款明细」上给她一条可区分的标记（或文档里写明），否则她看表会以为这单还没收钱。
