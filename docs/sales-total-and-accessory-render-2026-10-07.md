# 销售：总额 + 分项金额同时出现时的解析口径 · 配品行不渲染「码」

- **日期**：2026-10-07
- **起因**：业务负责人真机案例（逐字原话 + 她本人的澄清）
- **范围**：销售提示词（`services/doubaoService.js` 的 `parseSalesText` prompt）＋ 后端
  `normalizeSalesResult` 的确定性校验 ＋ 卡片渲染（`utils/larkCards.js` 的 `itemLines`）
- **🔴 不动**：`pendingDealPush*` / `dailyReport*` / 战报 / `app.js`；交付 / 扣库存 / 入库 /
  收款方式口径；「用户会主动说收款方式」那条规则

---

## 一、真机案例（逐字）

她的原话：

> 「**400 元微信卖了一双 6A637-7，43码（赠了一双袜子，260 元），然后 140 元微信卖了一条 158 元的腰带**」

她的澄清（逐字）：

> 「**其实是这笔一共成交 400 元，鞋是 260 元，腰带是 140 元，为什么理解不了呢？**」

⇒ **真相**：一笔共收 ¥400 = 鞋 ¥260 + 腰带 ¥140（腰带档位价 158）；赠品「袜子一双」不参与金额。

系统实际解析（错）：

| 字段 | 实际（错） | 应为 |
| --- | --- | --- |
| 鞋 `actual_amount` | 400 | **260** |
| 腰带 `actual_amount` | 140 | 140 |
| `agreed_total` | 400 | **400**（= 260 + 140，自洽） |
| `payments` | 微信 400 + 微信 140 | **微信 400 一笔** |
| 成交总额 | 540 | **400** |

卡片上的两个毛病：

1. 配品行渲染成「**腰带 码 × 1**」——配品没有尺码，模板仍然硬拼了「码」；
2. 金额错位——鞋 400（应 260），又把 140 算成第二笔付款 ⇒ 总额 540。

## 二、⭐ 验收标准（动手之前先写死）

> 她的纪律：**先写「按我们的链路应该实现的效果」→ 再跑 → 逐条对照。**

### A. 解析口径（核心）

| # | 验收标准 | 判据 |
| --- | --- | --- |
| A1 | 一句话里**同时**给了整单总额与各分项金额 ⇒ **每个件用它自己的分项金额** | 鞋 `actual_amount = 260`、腰带 `= 140` |
| A2 | 成交总额 = **各分项之和** | `agreed_total = 400`（= 260 + 140） |
| A3 | 后端**不许**把整单实收覆盖成单件的成交金额（真机错位就是这么来的） | `items[0].actual_amount !== 400` |
| A4 | **分项之和 ≠ 她说的总额** ⇒ 走既有「缺项」路径**问她**，**不入账** | `missing_fields` 里有一句「总额 … 与各件金额之和 … 对不上」；任务 `status = needs_info`；不写销售明细 / 收款 / 不扣库存 |
| A5 | 与既有口径自洽：**只给总额、没给分项** ⇒ 分项留空、要求补充（现状保持） | `items[*].actual_amount = ''` 且 `missing_fields` 含 `items[i].actual_amount` |
| A6 | **只有定金**不能当成交额（既有规则不动） | 定金用例逐字不变 |
| A7 | 既有正确路径**不许**被这条例外改坏：「多件逐件金额已知时可求和」照旧 | 既有断言全绿（不放宽） |
| A8 | 单件 + 她明说「收到 X」的**还价**口径不变（鞋 230 收 200 → 成交 200） | 既有用例 `A100黑38，230的鞋，收到了200微信` 全绿 |
| A9 | 赠品不参与金额（「赠了一双袜子，260 元」里的 260 不是袜子的价） | 袜子只出现在 `gift_description`，不进 `items`、不进金额 |

### B. 提示词（她既有规则 6 / 9 / 9.1 的自洽性）

| # | 验收标准 | 判据 |
| --- | --- | --- |
| B1 | 提示词把「总额 + 分项」这条口径写进去，且**不与规则 6 打架**（规则 6 管"只给整单金额"） | 提示词里能读到「同时给了总额和每件金额」的写法 |
| B2 | 与规则 9 的「成交金额 = 她说的收款额」自洽：**多件**时整单实收不再覆盖单件金额 | 提示词里能读到这句边界 |
| B3 | 与规则 9.1（只有她明说欠才填 `owed`）自洽 | `owed` 口径逐字不变 |

### C. 配品渲染（只改渲染）

| # | 验收标准 | 判据 |
| --- | --- | --- |
| C1 | **配品**（`kind: 'accessory'`）行**不出现「码」**，也不出现「码 × 1」这种残句 | `腰带 × 1`，且渲染串里不含「码」 |
| C2 | 没有尺码的件（含配品）都不硬拼「码」 | 无 `size` 时只写 `× N` |
| C3 | 有尺码的鞋**逐字不变** | 既有断言 `1. 66356 42码 × 1 ￥99` 全绿 |
| C4 | 配品 + 鞋混在一单时，两者都对 | 鞋 `42码 × 1`、配品 `腰带 × 1` |
| C5 | **只改渲染**，写库 / 业务逻辑一个字不动 | `salesOrderService` / `v1PostingService` 无 diff；配品不写尺码、不产生库存动作（既有用例全绿） |
| C6 | 同类排查清单（别处对"没尺码的件"硬拼「码」） | 见第四节；有尺码才拼「码」的地方**不改** |

## 五、不确定处（如实记）

1. **真机那一次模型到底输出了什么，我无法在本机重放**。按任务书给的「系统实际解析（错）」
   （items 两件：鞋 400 / 腰带 140；payments 两笔：微信 400 + 微信 140；总额 400）复现时，
   **现有代码本来就会**报 `missing_fields`（各件之和 540 ≠ 总额 400），也就是本来就会问她。
   ⇒ 真机上她看到"540 的卡片"，最可能是那次**模型没有给 `agreed_total`**
   （后端就会把它求和成 540，两件之和与它相等 → 校验通过、不报缺项），
   或者模型**只给了一件**（把腰带并进鞋里/丢掉）。
   这两种都只能在**模型输出**那一侧修 ⇒ 所以本次把主改动放在**提示词**，
   后端只做"错输入不许被做平"的加固（守卫 + 更清楚的追问文案）。
   ⚠️ 这里如实标注：**模型侧的效果没法用本机单测证明**，需要真机再发一次她那句话验证。
2. **「一笔微信 400」后端该不该合并付款**：付款笔数由模型从原话结构（她说了一次收款方式）；
   后端**不做**付款合并（合并会动到"用户会主动说收款方式"那条既有口径）。
   所以真机用例按"模型给一笔微信 400"钉住解析结果，payload 侧由提示词第 7 条保证。
3. **没做的一件事（刻意）**：没有加"把整单实收按比例/标价摊到各件"的任何逻辑 ——
   那是她明令禁止的；对不上就只有一条路：**问她**。
