## 一、⭐ 销售链路 —— 核心变化

### 1.1 链路本身【一个字不变】，只是【承载场所】从私聊 → **群聊**
```
识别原话 → 发【销售卡片】→ 她点 确认 / 取消 / 修改 → 入账 → 交付
```
- ⭐ **销售卡片【照发】** —— 群里也发，不是不发了。

### 1.2 ⭐ 一条销售记录 = 一个话题
- **该记录的所有交互，都在【同一个话题】里完成。**
- 三种入口：
  1. ⭐ **主群里她新说一笔** → **建销售记录 ＋ 在那条消息下开话题 ＋ 回卡片**
  2. ⭐ **话题里收到消息** → **按话题定位到那笔销售** → **走和私聊完全一样的处理**
  3. ⭐ **话题里她同步"未付 / 预付进展"** → **直接更新那笔销售**
     - ⚠️ **机器人【不用】去查"最近的销售"** —— **话题本身就是上下文**

### 1.3 ⚠️ "话题不用存"（她的原话）—— 别理解错
- **不用建「话题 ↔ 销售记录」的映射表**，**也不用给业务表加列**。
- ⭐ **要存的是【业务内容】**：她说的那些话 ——
  「**某某货号、多少钱、收到微信多少钱**」→ 落在
  **【销售主表·原话】＋【收款明细】**。
- ⭐ **话题标识由飞书事件自带，机器人当场认。**

## 二、采购链路（现状 ＋ 一点补充）

- ⭐ **采购申请 ＋ 采购退货 —— 都是【提交表单】**（工作台里那两个飞书表单链接）。
- ⭐ **提交完 → 内部流程走完 → 发图片到群里**（**已实现**）。
- ⭐ **采购退货【没有后续流程】**。
- ⭐ **采购申请【有后续：到库核对】**：
  - **相关人员主动在【对应的采购申请图片】下【创建一个话题】**；
  - **在话题里同步实际到货情况**；
  - ⭐ **机器人靠"话题挂在哪条消息下"反查是哪张采购申请。**

## 三、工作台（**已上线**）

- ⭐ **PC 端不做 —— 专注【移动端】**（"PC 显示 7 个 tab"的需求**作废**）。
- 三个一级 tab：**常用功能 · 销售查询 · 实时库存**。
- **常用功能**里两个：
  - **库存手工调整** —— **在工作台里自建、写多维表格**
  - **采购和退货** —— **两个飞书表单外链**

### 六.② 二次处理识别（**落地**）

- **判据全部在配置里**：`config/salesProgressIntake.js`（进展词表 / 新原话词表 /
  金额遮罩正则 / 收款方式说法 / 文案），逻辑里**一个关键词都没写死**。
- **服务**：`services/salesThreadProgressService.js` —— 只干"认出这是哪一类进展 + 落到那笔上"，
  收钱复用 `PaymentService`、交货复用 `SalesDeliveryService`（全仓唯一的销售扣库存入口），
  进度只算不写（`SalesProgressService`）。
- **接线**：`larkMvpService.processSalesTask` 开头；**判据是"群 + 话题 + 已定位到那笔销售"**，
  私聊任务两个字段都没有 → **一次都不会执行**。
- **闸门**：话题里已定位到销售时，入口闸门放宽成"像销售 **或** 像那笔的进展"——
  否则「那双拿走了」这种没有数字、也没有业务关键词的交付进展会被静默挡掉。
- **判不清 → 回一句问她**（"这是在说这笔的收款进展吗？"），**绝不**回退去当新原话解析。

### 六.③ 售后回话题（**落地**）

- **入口**：话题里说退换货 → 走原售后链路（意图 → `afterSalesFlowService`）。
- **上下文**：候选查询带上 `salesEntryRecordId`（= 话题定位到的那笔销售）→
  **同一笔的售后**，绝不跨单去捞（`saleLookupService.findCandidates` 新增只读筛选）。
- **回复**：`afterSalesFlowService` 的三个消息端口改成**渠道感知**
  （`replyCardToTask` / `sendCardToTask` / `sendTextToTask`），由 `larkMvpService` 注入：
  群话题 → `im.message.reply` + `reply_in_thread: true`（销售卡片那条路同一个出口）；
  私聊 → **与改动前逐字相同的** `replyCard(message_id)` / `sendCard(open_id)` / `sendText(open_id)`。
- **售后结束**：见下面 §七 —— 回写原单「销售状态」这一步做成**显式开关**
  `AFTER_SALES_WRITE_ORIGINAL_SALES_STATUS`，**默认关**（= 售后不影响原单），
  **等业务负责人拍板**。

### 六.④ 采购到货同步回话题（**落地**）

- `PurchaseArrivalConversationService` / `GroupPurchaseFlowService` 把 `threadId` 当**上下文**
  交给发送端口；飞书语义（`reply_in_thread`）只留在
  `larkMvpService.replyPurchaseText / replyPurchaseCard` 两个适配器里。
- 判据：`threadId` 有值 → 回到**那个话题**；没有（主群 @ 进来）→ 与改动前逐字相同。
- 采购的定位不变：靠 `PurchaseBatchLocator`（`thread_id` → `parent_id` → 正文批次号）。

## 七、🔴 一个待她定的【真矛盾】：售后要不要写原单的「销售状态」

**背景**：售后回话题这条链路在售后退货完成后，要不要往**原销售主表**的「销售状态」
写「已退货 / 部分退货」。

**它的理由**：`saleLookupService` 的判据一「排除已经退过的单」**读的就是这一列**，
而在此之前**全仓没有任何写入点** —— 判据一形同虚设。

**矛盾所在**：
- ⭐ `afterSalesService.js` 的**原注释**写着：「（原主表**一字不动**，业务负责人明确要求）」
- ⭐ 但「排除退过的单」**又读这一列** → 两件事自相矛盾。

**当前实现（PR #148，`feat/thread-resolve-everything`）**：
- 能力与判据**都写好、都有测试**，但做成**显式开关**
  `AFTER_SALES_WRITE_ORIGINAL_SALES_STATUS`，**默认 false**：
  - **关（默认）**：售后退货执行完，原销售主表**一个字节都不动**（= 现有口径不变）；
  - **开**：退货 → 原单「销售状态」= 已退货（整单全退）/ 部分退货（只退一部分）；
    换货 / 赔货**仍然不写**（表里只有这两个与售后有关的选项，写别的字会自动新建选项）。
- 开关关着时兜底的仍然是**判据二**（销售明细.交易类型 = 销售退货）—— 它不依赖开关。

**要她定两件**：
1. **售后（退货）要不要顺便把原单的「销售状态」标成「已退货 / 部分退货」？**
   - **要** → 把开关打开（一行配置）；「原主表不动」这条口径随之作废；
   - **不要** → 开关保持关；「排除退过的单」只靠**判据二**，
     并考虑**把判据一删掉**（免得那一列永远空着误导）。
2. **换货 / 赔货不写** → 「被换过的那一双」在查单里**仍可能被当成可退**。要不要禁止？
