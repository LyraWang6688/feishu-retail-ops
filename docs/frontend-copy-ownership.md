# 前端「静态文案」与「动态交互」的分工章程（2026-10-16 · 业务负责人定的）

> 业务负责人的决定：**另一个 AI 专职做前端静态页面的优化**（按钮文字、说明文案、注释类 ✓）
> **动态交互仍归 Lead**（本会话的 AI）✓
> 本页是**给那个 AI 看的规矩**，也是我们两边**不打架**的依据 ✓

## 一、分工（按"改什么"分，不是按"哪个页面"分 ✗）

| 归**静态**那位（A） | 归 **Lead**（B） |
| --- | --- |
| 按钮/标签/占位符（`placeholder`）/说明文字的**用词** ✓ | 任何**行为**：校验、提交、跳转、写入、接口 ✓ |
| `config/**` 里的**文案值**（不改键名语义 ✗） | `routes/**` 的分支逻辑 · `services/**` ✓ |
| `public/workbench/**` 的**静态 HTML/样式/文案** ✓ | `public/workbench/**` 的 **JS 交互逻辑**（`features/**` 的行为部分）✓ |
| 页面上的**注释**（`<!-- -->` / 代码注释）✓ | 判据（`server/test/**`）的**口径**（放不放宽 ✗）|

## 二、🔴 最重要的一条：**同一个文件，同一时刻只许一个写入者** ✗

今晚真实踩过两次坑（两个 AI 在同一 worktree / 同一文件上写 ⇒ 差点互相覆盖 ✗）。
⇒ 规矩：
1. **热点文件清单**（谁动它谁就要在共享任务板上**认领**一张卡 ✓）：
   `routes/scanPage.js` · `views/scanPageRenderer.js` · `config/scanPage.js` · `config/scanWrite.js` · `public/workbench/**` · `routes/workbench.js`
2. **一张卡一个 owner** ✓；**A 和 B 不许同时改同一个文件** ✗（要改就排队 ✓）
3. 各自用**独立 worktree** ✓；只 `git add` **自己改的显式路径** ✓；**不许** `stash` / `checkout .` / `reset --hard` / 碰别人的未提交改动 ✗

## 三、🔴 文案在这个仓库里是**承重的**（不是随便改的字 ✗）

1. **判据钉着文案**：改用户可见文案 ⇒ 必须**成对迁移**那些判据，写成
   「**改前逐字 → 改后逐字 → 依据**」（依据 = 业务负责人哪句逐字 / 哪张截图 ✓）✗ **不许删 / skip / 放宽** ✗
2. **中文必须在 `config/**`**：`server/test/noHardcodedChinese.test.js` 会把 `routes/**`、`views/**` 里**新增的中文**判红 ✗（白名单也不许私自扩 ✗）⇒ 文案要落在 `config/**` 的既有键上 ✓
3. **一条文案一个真源**：别在渲染处再写一份 ✗（否则两边会不一致 ✓）
4. **她点过的文案不许自作主张改** ✗（例：「退货」「已提交成功，数据会更新」「输入货号，例如 XHB8095」「整单金额（必填）」「跳过」）
   ⇒ 改这类**必须先经业务负责人点头** ✓
5. **占位符/说明也要跟"真实行为"一致**（例：它要是说"可不填"，但校验是必填 ⇒ 就是 bug ✓ 今晚就修过一条这样的 ✗）

## 四、每个 PR 的硬门槛（和 Lead 同一套 ✓ 不许松 ✗）

```
· 只开 PR，**不合并** ✗（合并由 Lead 复核后做 ✓）
· **严禁自行部署** ✗（`deploy_*.sh` / `pm2` / 改线上 `.env` / 回滚 —— 都要业务负责人**当次**点头 ✓）
· 严禁飞书 CLI ✗ · 不许 `gh pr merge --admin` ✗
· 两遍全量 `EXIT=0 ×2`（取真 EXIT ✗ 别接管道）· 两遍之间 `git diff | shasum -a 256` 自证未改 ✓
· **变异 ≥2 组真红 + 还原逐字节一致**（改"整行/整句"，别用子串锚点 ✗）
· **CI 四件全绿**（test / CodeQL / Analyze ×2）✓
· 🔴 `server/src/services/scanWriteService.js` **一个字不加/删/改**（余量 0 的冻结文件 ✓）
· 生产 Base **只读** ✓（唯一例外：业务负责人的「项目推进表」✓）
· 同一把判据最多试 2 次 ⇒ 超了**停下报"卡在哪/现象/已排除什么"** ✗ 不许留半红 PR ✗
```

## 五、协作方式（推荐）
1. 静态文案的活**都放共享任务板**（一张卡一个 owner ✓ 写清**写作用域**与**依据** ✓）
2. 那位 AI 的**页面标注能力**很好用 ✓ ⇒ 它的改动请求**尽量带上"点哪块 + 那块的 `data-view` / class 名字"** ✓
   （本仓页面上的块大多有 `data-view="…"` ✓ 那就是最准的定位 ✓）
3. 有任何**业务口径**疑问 ⇒ **问业务负责人**（别猜 ✗）；她答完 ⇒ 写进 `docs/owner-requests-backlog.md` ✓
4. 交接工具：Lead 这边已有一份 **`docs/dsh-sidebar-plugin-spec.md` 的替代方案**：`docs/pending-confirmations.md`（待她拍板清单 ✓）

## 六、Lead 这边对应的自查（我自己也照这个办 ✓）
- 我改动态逻辑时，**不碰** 归 A 的"纯文案值" ✗（要改就开一张卡给 A ✓ 或先跟她确认 ✓）
- 我合并 A 的 PR 前，**逐条核**：四件 CI ✓ / 有没有删/skip/放宽判据 ✓ / 有没有动冻结文件 ✓ / 有没有硬编码中文 ✓
