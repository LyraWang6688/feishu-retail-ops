# 二维码改用「记录 ID」+ 扫码页/工作台允许 JS（业务负责人 2026-10-12 定）

## 一、她新增了「记录 ID」公式字段，并提出映射问题
> 「1. 我已经在货品信息里面增加了一个公式字段，叫做**「记录 ID」**，这个就是关于这条记录的 ID。
>  2. 现在记录 ID 肯定是不变的，只要创建完之后，这条记录的记录 ID 就不会变。
>     那你要**怎么确保这个记录 ID 就是对应这个编号的**？这种**映射关系**你是怎么做好的？
>     以及，它**不需要去保持兼容**，所以你要**重打二维码标签**。
>  3. ……它没有 JS（也就是说它没有 JavaScript，对不对？），它就没有办法进行动态交互，对吧？
>     **这个我可没有说过，我们是能够进行动态交互的**。」

## 二、映射关系：**不需要维护映射表**（原理）
- 飞书里「记录 ID」(`record_id`) 是**记录自身的身份**；「编号」是**同一条记录上的公式列**算出来的字符串。
- ⇒ **两个都是"同一条记录"的属性** ⇒ 不存在"两张表要对映射"的问题 ✓
  - 生成二维码时：读该记录的 `record_id` ⇒ 写进二维码 ✓
  - 扫码时：拿 `record_id` ⇒ **直达那一条记录** ⇒ 它的编号/价格/库存怎么变都无所谓 ✓
- ⚠️ **但"公式列有延迟"**（今天那个二维码印了旧编号的 bug 就是它引起的）⇒
  **生成二维码一律用【接口读到的 `record_id`】**（即时 ✓）；她那个「记录 ID」公式字段**只作交叉校验**：
  两者不一致 ⇒ 记 `warn` 并**以接口值**为准 ✓（不要把公式值当准 ✗）
- ⭐ **兼容性**：她明确「**不需要保持兼容**」⇒
  - **新生成的二维码一律 `https://hm.bamamei.online/r/{recordId}`** ✓
  - 旧贴纸**重打**即可（`/s/{编号}` 那条路径**保留**，零成本，但**不再为它做额外功能** ✗）

## 三、JS：**她从未禁止 JS；扫码页与工作台都允许动态交互**
- 🔴 之前的「扫码页零 JS」是**我方（agent 侧）自己加的技术约束**，**不是她的口径** ✗（她 2026-10-12 当场纠正过两次）。
- ✅ **她的口径**：①「点击完之后一定要有交互：按钮置灰 / Toast / 改文案」②「**我们是能够进行动态交互的**」
  ⇒ 扫码页与工作台**都可以用 JS 做动态交互** ✓（当天已实现的"点击立刻置灰 + 计时"就是 JS ✓）
- ⇒ 以后**不许**再拿"零 JS"当理由拒绝动态交互 ✗；技术取舍要**标注来源**（agent 约束 / Lead 决定），
  **不许写成"她的要求"** ✗。
