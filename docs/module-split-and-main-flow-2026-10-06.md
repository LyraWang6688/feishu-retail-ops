# 主链路与板块划分（业务负责人 2026-10-06 逐字确认）

> 她的原话：「**因为后续就不用私聊了，后续就是在群聊里面沟通销售、采购的事情。**」

## 一、两个板块的职责

### 【工作台】= 看 + 摆弄（**不录入业务**）
| 项 | 形态 |
| --- | --- |
| 查询功能 | 工作台自己的页面（销售查询 / 实时库存） |
| 库存调整 | 工作台自己的页面（盘点调整 / 换季调整） |
| **采购申请** | ⭐ **多维表格表单链接**（`…/share/base/form/shrcnn4f9ZJzpm7JbT2rCH247xc`）—— **她填的** |
| **退货申请** | ⭐ **多维表格表单链接**（`…/share/base/form/shrcnjsqt4D5URseSSXgecYlqGd`）—— **她填的** |

⭐ 她明确：「**工作台里面的采购和退货申请，就是我们填的那个多维表格的链接**」
（代码 `server/public/workbench/config/links.js` 里就是这么做的，注释也写明是**外链**。）

### 【群聊（与机器人交互）】= 说 + 办
| 项 | 状态 |
| --- | --- |
| **初次销售** | ✅ 已做（主群说一笔 → 建记录 + 开话题 + 回卡片） |
| **售后** | ✅ 已做（退货/换货，回复回话题） |
| **二次交付** | ✅ 已做（"收到微信 500" → 更新那笔） |
| **采购到货情况** | ✅ 已做（人在图下开话题，回复回话题） |

＋ **私聊后续【不用了】** —— 见 `docs/channel-decoupling-2026-10-06.md`。

## 二、创建话题【只有两个入口】
1. ⭐ **初次销售**：群里说一笔 → 建销售记录 + **在【那条消息】下开话题** + 回卡片
2. ⭐ **采购申请单（图）发到群**：**人（她或采购的人）在图片下【手动开话题】** → 机器人在话题里回复
   - 🔴 **退货申请单**也发到群，但**没有后续链路** → **不开话题**

## 三、话题里的回复（就这两类）
- **采购端**：回复**到货情况**
- **销售端**：回复**售后（是否需要退换货）** + **预付 / 未付情况下的二次交付确认**

## 四、主群准入 —— 她 2026-10-06 确认「**这样可以**」
- 🔴 **主群里【不 @机器人】**，机器人靠**正文像不像销售**自己判：
  - **像** → 处理，回卡片
  - **不像** → **完全不搭理**（群里日常聊天绝不能被触发）
- **误判的兜底**：会建一张**卡片**，她点「**取消**」就行 —— **不会直接写数据**。
- ⚠️ **现状**：主群**必须 @ 机器人**才处理（`LARK_BOT_OPEN_ID` 判据）→ **这条要改**。

## 五、其他已确认的口径
- **被换过的那双可以再退** —— 她：「**不会啊，没有这些规定啊！**」→ **不做限制**。
- **卡片点按钮后不需要额外弹私聊文字** —— 她：「**我们的消息卡片会变化啊！**」
  → 卡片更新本身就是反馈；**那条多余的私聊 toast 要去掉**。

## 六、为什么是这个架构（业务负责人 2026-10-06 讲的"为什么"）

> 她的原话大意：
> 「**我爸妈是 70 后，而且一直在县城，可能没有太多的数字化思维**，所以更希望是这种
>  **傻瓜式或者一站式**的东西。这也是我**吸取了之前的教训，比如多个表单需要我爸妈填**。
>  所以现在就是**一个入口，那就是群聊**……而且**用话题的形式，其实能够解决我们之前的
>  售后和二次交付问题**。这个时候**系统不用去查，用户也不需要去记，直接在这个话题里
>  完成一个完整的生命周期**。」
> 「希望它是**一个入口**，我在这个群聊里面，就可以完成所有的操作。」

### ⇒ 用它来判断任何改动（四条设计原则）
1. ⭐ **一个入口**：群聊是用户主入口（销售 + 采购都在里面）
2. ⭐ **不要让用户填多个表单**（这是她的历史教训）
3. ⭐ **话题 = 一条记录的完整生命周期容器**：**系统不用猜、用户不用记**
4. ⭐ **傻瓜式 / 一站式** 优先于"功能多"

## 八、消息链接（话题深链）的格式（她 2026-10-06 给的真实样例）
```
https://applink.feishu.cn/client/thread/open
  ?open_chat_id=<群 chat_id>
  &open_thread_id=<话题 thread_id>
  &openchatid=<群 chat_id>
  &openthreadid=<话题 thread_id>
  &thread_position=-1
```
> 「**点开之后就直接可以看到那条消息的所有沟通内容**」

⭐ **这两个 id 我们手上都有**（群消息事件里有 `chat_id`；`im.message.get` 与事件里都有 `thread_id`）
⇒ ⭐ **不需要等发送响应的 `message_app_link`，自己拼即可。**

⚠️ 已实测：`message_app_link` **只在【发送响应】里出现**；**历史消息的深链官方接口取不回来**
（`get` 不填该字段、`list` 缺 scope、官方 34 条 AppLink 协议里没有"打开消息/话题"）。
⇒ 所以这条**她给的拼接格式**是"历史单也能给链接"的唯一途径。
（她 2026-10-06 说"**不需要历史消息的补拉**，只要后续能取回就行"，所以**不强制补老单**。）
