## 1. 口径原文（业务负责人 2026-10-06，逐字）

> 「首先我跟你说哈，**一个单子的提交它就是一个行为**，
> 要不然就是**采购申请**，要不然就是**采购退货**。
> 但是这一个单子里面，我之所以说它会有多条记录，
> 原因是因为**它会有多个编号**。」

> 「我在**一次提交里面如果有多个记录，我看到的图实际上是分开的**。
> 但是我们能看到，**飞书发给你的是一个压缩包，这个包里包含了我的提交记录数量**。
> 所以你在出图的时候，**应该确保把飞书给到你的这些数量全部处理完，再给我发图**。
> 像你刚才跟我说的，那个 action 里面有 7 个，
> 也就是说，**你需要处理完这 7 个之后才能发图**。」

> 「遇到的就是这种情况：**一次提交 3 条，全是采购申请 → 出了 3 张采购单**。」

## 2. 归纳成规则（本文件即以此为准）

| # | 规则 | 说明 |
|---|---|---|
| ① | **一次提交 = 一个行为** | 行为**二选一**：采购申请 **或** 采购退货。**同一次提交里不会两种混着**。 |
| ② | **一次提交 = N 个编号（货品）** | 一个「单子」里有**多条记录**，是因为她**填了多个编号（= 多个不同货品）**，不是因为她提交了多次。⭐ **N 条记录 = N 个【不同货品】**；**一个货品的多个尺码要勾在【同一条记录】上**，不要拆成多条记录 —— 依据与代码行为见 **第 5 节**。 |
| ③ | **N 个编号 = N 条记录 = 飞书一个包裹里的 N 条 `record_added`** | 飞书一个推送包（`action_list`）里**「新增」的条数**，就是她这一次提交的记录数。 |
| ④ | ⭐ **N 条全部处理完，才出图** | 不许「先到先出」——图必须等这一次提交的记录**齐了**再画。 |
| ⑤ | ⭐ **一次提交只出一张图** | 3 条采购申请 → **1 张采购单**（不是 3 张）。 |
| ⑥ | **图上怎么排** | **按货号分组**；每个货号下面**一个颜色一行**，格子写 **尺码×数量**。⚠️ 排版现状见下方「排版进度」——**只在 main 上的那半已经生效，另一半还没合进 main**。 |

## 3. 已核实的事实（日志与代码）

### 3.1 飞书事件长什么样

事件 `drive.file.bitable_record_changed_v1` → 日志事件名 `lark.bitable.record_changed`：

```json
{"event":"lark.bitable.record_changed","file_token":"QrXl***rnwh",
 "table_id":"tbl**********",
 "action_count":10,
 "actions":[{"record_id":"…","action":"record_added"},
            {"record_id":"…","action":"record_edited"}, "…"]}
```

| 事实 | 含义 |
|---|---|
| ⚠️ **事件里没有字段值**（代码没读 `after_value`） | 内容（编号 / 颜色 / 尺码 / 数量）**只能拿 `record_id` 重新读表**得到。 |
| ⭐ `action_count` 的实测取值：**2 / 4 / 4 / 4 / 4 / 5 / 5 / 6 / 6 / 10 / 20** | **没有一次是 1**——飞书几乎总是「一包多动作」地推。 |
| ⭐ 动作以**成对**为主：`record_added` + `record_edited` 交替 | 「修改」**不是她改的**，是**我们代码回写**造成的（写处理状态、关联采购申请）。 |
| ⚠️ 也出现过**奇数**（`action_count: 5`） | ⇒ 「这包里有几条记录」**必须逐条数 `record_added`**，**不能拿 `action_count ÷ 2` 估**。 |
| ⚠️ **飞书确实会拆包** | 退货链路 2026-10-06 生产实测：同一次提交的 2 条记录**相隔 16 秒**分两次推（`action_count: 1` + `action_count: 1`）。⇒ 上一版据此认为「等包裹到齐」**不能取代**时间窗兜底；⚠️ **她 2026-10-06 明确「现在不考虑拆包的问题」「不需要兜底」** ⇒ **这个风险已知、暂不处理**（见方案第三节 ①③）。 |

> ⚠️ 上面 `action_count` 的取值清单来自**父代理对生产日志的核对**（结论：「实测多次真实报货，
> 没有一次是 1」）；⚠️ **本文件的作者未重复核对生产日志**，这一栏按"转述 + 标注来源"看待。
> 机制与代码位置部分是**在本仓库源码里逐行核过**的（见 3.2）。

### 3.2 代码现在实际怎么做

| 位置 | 现在做的事 |
|---|---|
| `server/src/routes/larkEvents.js:87` | 事件分支 |
| `…:90` | 取 `action_list` |
| `…:95` | 日志只记 `action_count` + 每条的 `record_id` / `action` |
| `…:147` | `if (action !== 'record_added') continue;` ← **只要「新增」、跳过「修改」** ✅ 与口径③一致 |
| `…:174` | `service.purchaseWebhooks.acceptMany(intake.kind, recordIds)` ← **整包的 ID 数组一次交给处理逻辑，数量天然就有** |
| `server/src/config/reportBatchWindow.js` | 报货归批窗口 **4000 ms**（`REPORT_BATCH_WINDOW_MS`） |
| `server/src/config/purchaseReturnBatchWindow.js` | 退货归批窗口 **30000 ms**（`PURCHASE_RETURN_BATCH_WINDOW_MS`） |

⭐ **关键结论**：`acceptMany`（`server/src/services/purchaseWebhookService.js:419`）
**已经**一次收到整包的 ID 数组 —— **「N 是多少」这个数在入口就已经拿到了**，
只是**没有被当作「到齐」的判据**在用。
现在的处理时机完全由**窗口到点**决定
（`handleReportBatch` / `handleReturnBatch`，同上文件）。

> ⚠️ 所以「一次提交被拆成 N 张图」的**根因不是"数不到 N"**，而是
> **"没有拿这个 N 去等齐"**：窗口一关就发图，晚到的同伴只能另起一批。
> ⇒ 从「猜时间窗」改成「等包裹到齐」在**入口数据上是现成的**，不需要新增字段。

## 5. ⭐ 补充澄清（2026-10-06 追加）：编号 = 货品；一个货品的尺码只勾在它自己那条记录上

> 本节由业务负责人 **2026-10-06 追加确认**；「测试表里是什么形状」那一栏是
> **在测试 Base 上只读核对**出来的（走项目自己的 gateway，**不是飞书 CLI**，不写任何表；
> 测试 Base 与生产**同构**：表名一致、`table_id` 不同）。

### 5.1 ⭐ N 条记录 = N 个【不同货品】

- ⭐ **一次提交 = 一个行为 ＋ N 个【编号（货品）】** ✗
  → ⭐ **所以 N 条记录 = N 个【不同货品】** ✓。
- ⭐ **一个货品的多个尺码 ✗ 要【勾在同一条记录上】✗ 不要拆成多条记录** ✓。
  - ⭐ **依据**：**测试 Base 里与生产同构的记录，统统是这个形状** ✓。
    - **实测例**：报货批次号 **`202609271`**，共 **12 条**，尺码依次是
      `[45] / [41,42] / [43,44] / [43] / [38,41,42] / [41] / [43] / [39,43] / [40,41] / [40,44] / [39,41,44] / [41,42]`
      —— **12 条记录，货品各不相同** ✓；同一货品的多个尺码（如 `[38,41,42]`）**都在同一条记录上** ✓。
    - 另有 `202609201`（7 条）· `202609231`（7 条）· `202609232`（3 条）——同样是
      **「一条记录 = 一个货品 = 一个尺码集合」** ✓。
  - ＋ ⭐ **「同一批次号里同一货品重复」的，只有自测脚本造的 `SELFTEST-*`** ✓。
    - **只读核对**：22 个「记录数 ≥ 2」的批次号里 ——
      **4 个真实批次**（`202609271` / `202609201` / `202609231` / `202609232`）**货品各不相同** ✓；
      **17 个 `SELFTEST-*`**（其中 15 个同货品重复）；
      剩下 1 个是「**批次号为空**」的历史堆（113 条，批次号字段上线前的旧数据，**没有批次号、不成批**）。
    - ⇒ **凡是有批次号的真实数据，同批次的货品互不重复** ✓。

### 5.2 🔴 跨记录【不合并数量】

- 🔴 **跨记录不合并数量** ✗ —— **否则会写错**：
  **那等于让 A 货品的说明去改 B 货品的数量** ✓。
- ⭐ **代码行为**：
  - **解析层逐条读【本条记录的尺码】** ✗
    （`purchaseWebhookService.parseReportQuantities` → `purchaseQuantityPolicy.buildPurchaseQuantities`，
    `selectedSizes` 来自**这条记录自己的「尺码」关联**）；
  - **说明里出现未勾选尺码 → 拒绝** ✓
    （规则层：`数量说明提到了未勾选的 N 码`；AI 解析层同样拒绝：`数量说明包含未勾选或无效的尺码`）。
- ⚠️ **「两条记录各勾一个尺码」不是正常用法** ✗ → **改成【不支持、也不该支持】** ✓。
  - ⭐ **措辞要点**：**不是「暂时没做」✗ 而是【逻辑上就不对】** ✓
    —— 因为**尺码集合属于货品**，**跨货品合并会写错数量**。

### 5.3 ⚠️「说明里写了没勾的尺码」会发生什么（如实写）

| 环节 | 现在会发生什么 |
|---|---|
| **解析层** | **拒绝该记录** ✓（抛错，不猜、也不替她补一个尺码） |
| ⚠️ **归批路径下** | **整批 failed** ✗：报单「处理状态」**保持空白** ✓（代码刻意不写终态——写了终态，重收 webhook 也救不回来，等于静默丢单） |
| ⭐ **运营上表现为** | **「提交了没反应」** ✗：群里没有图、表里状态空着，**只能查日志** ✓（`purchase.batch.failed_retryable`） |
| ⭐ **待业务负责人定** | **要不要给它一个可见反馈（例如群里说一句）** ✗ —— **待业务负责人定** ✓ |

## 6. 一句话版本

> **一次提交 = 一个行为（采购申请 或 采购退货）+ N 个编号（货品）；
> N 条记录全部处理完，才发一张图。
> ⭐ N 条记录 = N 个不同货品；一个货品的多个尺码勾在同一条记录上，记录之间不合并数量。**
